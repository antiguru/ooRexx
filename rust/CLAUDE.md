# Working in this crate tree

A clean-room Rust reimplementation of ooRexx.
Correctness is defined **differentially**: a change is right when its output matches the C++ interpreter byte for byte, not when it looks right.

Each rule below has already cost this project a session, a wrong measurement, or a shipped defect.

## The oracle

* **The C++ tree is read-only.** Never modify `interpreter/`, `samples/`, `build/`, `ootest/`.
* **The oracle binary at `build/` is a 5.3 ooRexx matching this repository's own `interpreter/`, and it was swapped there on 2026-08-20.** Measured that day: `parse version` answers `REXX-ooRexx_5.3.0(MT)_64-bit 6.06 30 Jul 2026`, `bin/rexx` is 62,600 bytes and `lib/librexx.so.4` is 17,853,856, `/home/moritz/dev/repos/ooRexx` is checked out at `cb9563364` (2026-07-27), and `CMakeCache.txt` carries `CMAKE_BUILD_TYPE:STRING=RelWithDebInfo` with `CXX_FLAGS = -O2 -g -DNDEBUG -std=gnu++11 -fPIC`. `interpreter/` here is 5.3.0 and this crate answers 5.3.0, so **the differential is version-matched**, which for most of Phase 4 it was not.
  **What it replaced, and why a figure's date matters.** Until that day `build/` held a 5.0 interpreter -- 17,144 bytes against 3,801,176, the tree at `f975dde4`, ooRexx as of 2021 -- and the standing rule was that a difference between the two was not a defect here until the oracle's own source had been read. `docs/superpowers/plans/phase-4f-record.md`'s entry 62 holds that provenance and records one such difference read as a defect that was not one. **Any figure written down before 2026-08-20 was taken against the 5.0 binary and may not reproduce today.** Re-measure rather than reconcile.
  **The size of the gap**, measured 2026-08-20 at `05702b569` against an `-O3` 5.3 build, three descriptors raw over `corpus/` and `bench-programs/` with the three blocked programs skipped: **22 programs disagree with the 5.0 oracle and 9 with the 5.3 one.** Fourteen agree with 5.3 and not 5.0 -- `condition_traps`, `interpret_error_echo`, `loop_retest_blame`, the three `message_send_*`, `method_attribute_set_body`, `method_trace_invocation`, `method_trace_nested`, `mutation_controlled_order`, `raise_array_substitution`, `routine_dispatch`, `signal_forms`, `state_builtins` -- which is entry 62's "12 corpus programs have not been re-examined against this fact", re-examined. Eight disagree with both and are this crate's own not-implemented refusals. That separate `-O3` build is gone from this machine; `build/` is where 5.3 lives now.
  **One program agrees with 5.0 and not 5.3, and it is the corpus gate's only failure.** `corpus/lang/loop_control_rounding.rex`'s `NUMERIC FUZZ 1` loop: 5.3 applies FUZZ to a controlled loop's bound test and 5.0 does not, so 5.3 runs `do m = 1 to 10 for 20` at `DIGITS 2` out to 14 where this crate ends at 11. Measured 2026-08-20 at `5de2a8801`: `REXX_CORPUS_GATE=1` is **105 of 106**, this the one, everything else byte-identical. **Closing it is a change to this crate's loop control** -- the corpus file itself cannot be touched, for the reason on the next line.
  `corpus/lang/loop_control_rounding.rex`'s own comment still states the 5.0 answer as the rule, and was left that way on purpose: **editing any byte of a `corpus/lang/*.rex` reddens `sourceline_matches_the_interpreter_for_every_corpus_program`**, whose `crates/rexx-parse/tests/sourceline_oracle/<name>.txt` holds that file's line count and every line verbatim. Regenerating one is the `.Package~new` driver in that test's module comment -- the single sanctioned exception to the never-instantiate-a-repository-file rule -- and re-deriving it from the file instead would make the test compare the corpus with itself.
  **`tests/support/oracle.rs`'s `oracle_root()` still hardcodes `/home/moritz/dev/repos/ooRexx/build` and was not edited** -- the binary behind that path was replaced instead. So no file in this checkout records which interpreter answered a given run: **the oracle's version is a property of the machine, not of the tree**, and a green differential proves only what the binary present at the time said. Check `parse version` before trusting a differential you did not just run.
  Two trace divergences this bullet used to carry -- a header's `>L>`/`>V>`/`>K>`/`>=>` lines indenting one level shallower here, and no `>>>` pair on a re-tested pass -- were 5.0-versus-5.3 artifacts from `BaseDoInstruction.cpp`'s `newBlockInstruction` moving behind `setup()` and `DoBlock::checkControl` gaining two `traceResult` calls. **Both are closed by the swap**: `trace i` over `do i = 1 to 2` is now byte-identical on all three descriptors, measured 2026-08-20. A probe that still disagrees on a *trace* transcript is the place to diff the two trees: `diff /home/moritz/dev/repos/ooRexx/interpreter/<file> interpreter/<file>`.
* **Wrap every oracle run** as
  `( ulimit -v 1048576; LD_LIBRARY_PATH=/home/moritz/dev/repos/ooRexx/build/lib /home/moritz/dev/repos/ooRexx/build/bin/rexx FILE )`.
  Without the `ulimit` the interpreter requests gigabytes mid-range and is OOM-killed; that has already ended a session and taken the machine's memory with it.
* **The oracle must be built `-O3` for any performance claim, and `build/` as it stands still is not.** Since the 2026-08-20 swap it is `RelWithDebInfo` -- `CXX_FLAGS = -O2 -g -DNDEBUG -std=gnu++11 -fPIC` -- which is optimised, so the `-O0` tell below no longer appears and a profile of it now looks plausible. **That makes it more dangerous, not less**: `-O2 -g` is close enough to pass a glance and still not the build any published figure was taken on. The `-O0` state the next sentences describe is what `build/` held before that day, and the measurement after them was taken against it. The tell is in any profile of it: `ObjectHeader::getObjectSize()`, `RexxString::getLength()` and `Memory::roundUp` appear as separate entries with their own self time, which is what one-line accessors do when nothing is inlined.
  Measured 2026-08-18 on `samples/rexxcps.rex` pinned to one trial and a fixed count: `-O0` reports 1,723,452 clauses/second and 21.93 billion user instructions, `-O3` reports 10,818,273 and 5.33 billion.
  **Every performance ratio taken against `build/` before 2026-08-18 is void as a comparison** -- against `-O0` this crate appears to win by 3x, against `-O3` it loses by 2x. **Ratios taken between 2026-08-18 and the 2026-08-20 swap are void for a second, independent reason**: they compared against a 5.0 interpreter, and the binary answering now is 5.3. A figure needs both its optimisation level and its interpreter version to mean anything, and neither is recorded anywhere in this checkout.
  Build one out of source with `cmake -DCMAKE_POLICY_VERSION_MINIMUM=3.5 -DCMAKE_BUILD_TYPE=Release <source>`, then `make` and `make rexx_img` for `lib/rexx.img`. The link needs `libcrypt.so` on `LIBRARY_PATH` -- Debian ships only `libcrypt.so.1` -- and without it the build stops before the test libraries and leaves a library set that does not match `build/`'s.
  **Correctness is the same on both, and that was checked rather than assumed**: the two builds agree byte for byte on stdout, stderr and exit status across `corpus/`'s programs, `corpus/errors/parse-errors.tsv` driven through `rexxc`, `corpus/expr/precedence.tsv` driven through `rexx`, and the trace and bench programs; and the gated suite reports the same passes, the same failures and the same panic text against either. The one normalisation needed is `rexxc`'s banner, whose build date and copyright year are compile-time stamps. So a differential *correctness* run may use either build; a *timing or instruction-count* run may not.
* **An instruction-count ratio against the oracle is not a time ratio, and the two disagree by enough to change which side looks ahead.** The two interpreters do not do the same amount of work per instruction: the oracle allocates a `RexxInteger` per integer operation and reaches a variable through a pointer, while this crate keeps small integers in the tag and slots in one contiguous `Vec`, so its working set stays in L1. Measured 2026-08-19 at `746a826ac` on `bench-programs/varlookup.rex`: 145,110 L1 load misses here against 78,658,648 for the `-O3` oracle, which is 0.008 per iteration against 4.1.
  **Do not read a fixed direction into that.** It has been stated here as "instructions overstate the gap" and that is not what the counters say: measured 2026-08-20, `varlookup` retires about as many instructions as the oracle (0.97x) and wins on the clock (0.71x), while `arith` retires fewer (1.08x) than its wall ratio (1.15x) and still loses. The IPC figures once recorded here -- 1.6 to 2.7 against the oracle's 1.2 to 2.2 -- were taken against a 5.0 `-O3` oracle before the optimisation body landed and describe neither binary now.
  **`rexx-bench-suite` counts every run and prints all of this**, so the live figures are a table rather than a sentence: `perf-baseline.md`'s newest counted section has cycles, instructions and IPC per axis per side. Read them there rather than from a number written down here, which is the whole reason the suite was taught to count.
  **Instruction counts stay the instrument for A/B-ing a change of this crate's own**, because they are deterministic where cycles move a few percent between runs here -- one axis reproduced to eight significant figures across two runs minutes apart -- and that is why every optimisation in this tree is justified with them. What they are not is the scoreboard. **A ratio quoted against the oracle must either be in cycles, or say that it is instructions.**

* **`ulimit -v` caps address space, not memory used, and that difference has already produced a misleading finding.**
  It charges a process for memory it merely *reserves*: `INTERPRETER_STACK_BYTES` reserves 512 MiB for the sized interpreter thread before any program runs, so under a 1 GiB cap this crate has ~500 MiB to allocate in where the oracle has ~1000, and a large-result comparison turns over exactly there.
  Measured 2026-08-05: raising the cap by precisely that 512 MiB makes the two sides agree again.
  **A cgroup memory limit is the right instrument** -- `systemd-run --user -p MemoryMax=`, or `memory.max` in a delegated cgroup -- because it charges RSS and would cost a reservation nothing.
  It is unavailable here: there is no user systemd manager ("offline"), no user bus, and `/sys` is a tmpfs with no cgroup filesystem mounted, so `systemd-run` cannot run and no cgroup can be created. Linux's `RLIMIT_RSS` (`ulimit -m`) is documented as having no effect.
  So `ulimit -v` stays, and any memory finding taken under it must say whether it survives the reservation being free.
* **Read stdout, stderr and exit status as three separate descriptors.** Never capture `2>&1` as one string: the trace sink and stdout interleave undefinedly by design, and comparing them together produced two false regressions.
* Run `rexx-run` from `rust/`.

## Probes

* **Run every probe from a fresh empty subdirectory you `mkdir` yourself**, never the scratchpad root.
  The scratchpad is on the oracle's **external-routine search path** and holds hundreds of stale `.rex` files, so a probe calling any unresolved name finds one and executes it.
  Measured: the same three-line program reported `44.1 rc 212` from the root and `43.1 rc 213` from a clean directory.
* **Use absolute paths for every redirect.** A relative redirect inside a subshell that has `cd`'d writes where you did not intend; that produced three false mismatches against correct code and left stray files in the repository.
* **Never instantiate `.Package~new` on a file inside the repository** -- it executes that file's prolog and has written untracked files into the tree.
* **Never run `select; when 1 = 0 then; when 2 = 2 then nop; end`** -- it segfaults the oracle (upstream SF #2018).
* **Never run a clause that queues the same `CALL ON` condition twice**, as in `zr = ra() + ra()` where `ra` ends `raise user c1 return 1` and `c1` is trapped. The oracle runs the handler once and then segfaults at rc 139, measured 2026-08-15. Two *differently* named conditions in the same clause are fine and are how the drain rule was measured; it is the same name arriving twice at one boundary that kills it. `corpus/oracle-crashes.txt` carries the whole program.
* **Never set `NUMERIC DIGITS` above 1000** in a probe.
* **A controlled `DO` whose step is rounded away at the `DIGITS` in force never ends**, and the oracle will fill the disk proving it. `numeric digits 1; do i = 1 to 9; say i; end` prints `1` through `9` and then `1E+1` forever, because `9 + 1` rounds to one significant digit and the comparison against `9` rounds too; measured 2026-08-20, the oracle wrote 21,795,453 bytes before the timeout. `numeric digits 3; do i = 998 to 999`, `numeric digits 1; do i = 1 to 9 by 3` and any initial value wider than `DIGITS` are the same shape. **Check that a probe's loop terminates at the precision it sets before running it**, put a `timeout` on both sides, and note that a counter inside the loop sticks for the same reason -- the escape has to be `==` against the stuck rendering. The narrower `numeric digits <var>` inside `do var = ...` form of this is in project memory; this is the rule it is a case of.
* A symbol named `x` or `b` immediately followed by a quoted string parses as a hex or binary literal, so `say '['x']'` is error 15.3 rather than concatenation. Use other names.

## Gates

* **`cargo fmt --all --check`** from `rust/`.
  **Not** `cargo fmt --edition 2024 --check`: `cargo fmt` has no `--edition` flag, that spelling exits 2 before doing any work, and a task once ran it and reported formatting clean.
  `--edition 2024` belongs to the standalone `rustfmt` binary.
* **`cargo clippy --workspace --all-targets -- -D warnings`** must be clean.
* **`REXX_CORPUS_GATE=1 memcap 8G cargo test --workspace --no-fail-fast`**, a **debug** run beside the `--release` ones, and it is not redundant with them: `[profile.release]` sets `debug = true` for the symbols a profiler needs and does not set `debug-assertions`, so every `debug_assert` in this workspace is compiled out of everything a `--release` gate runs -- `Interp::enter_clause`'s tripwire among them, the one that makes a construct resolving an instruction without ending its header clause first announce itself rather than wait for a reviewer's probe, and the temps-frame watermark `SteppedClause` carries. Expected against the tree as committed: exit 0, no failures.
  **Negative control, measured 2026-08-15 at `3492b0b9e`:** deleting `deliver_one_pending_trap`'s `queued_during_delivery` marking loop leaves the gated **release** suite at exit 0 with nothing failing, and under this debug command reddens `ir_dual.rs`'s two-engine cases, `corpus.rs`'s oracle differential and `collect_stress.rs`, every failure a panic at `Interp::enter_clause`'s assertion. **Do not change `[profile.release]` to close this** -- it is pinned because both its consumers are measurements, and its own comment says so.
* **Read every exit status unpiped, and confirm the command actually ran.** A pipeline reports the last command's status, and a misspelled flag exits non-zero before doing any work -- which reads as failure in one context and is silently skipped in another.
* **Commit before the full gate run, not after -- and leave the tree frozen until it finishes.**
  Ruled 2026-09-04. The five gates take about 27 minutes (measured 27m45s at `c1afdb9e9`), and an
  agent that waits on them times out and does not wake: Phase 5d Task 2 finished every gate at 0,
  died before committing, and its work had to be recovered from the staged index by the controller.
  The order that removes the window: fast checks yourself (`fmt`, `clippy`, the test binaries your
  change touches), **then commit code and report together** with the report's gate cells left as
  placeholders, **then** start the suite in the background writing each status unpiped to a file as
  it goes, with the commit sha as that file's first line and a pidfile the waiter keys on -- then
  report "committed at `<sha>`, gates running, statuses at `<path>`" and stop.
  **This makes the gated tree the committed tree by construction**, which is stronger evidence than
  a tree hash recorded before and after the run.
  **The second half is not optional**: the gates run sequentially over the working tree, so an edit
  landing between G1 and G7 -- a docs fix, a comment, the controller filling in a report -- is
  measured by the later gates and silently voids the property. The tree belongs to the gate run
  until the status file says `finished`, even though the agent has already released it. Task 3
  voided one benchmark sitting exactly this way, by a two-comment edit that rebuilt the head binary
  mid-run.
* **Write a gate line only from output you are looking at.** Never leave a placeholder in the shape
  of a result, intending to fill it in when the run lands: a prospective "exit 0" reads exactly like
  a measured one, and if the run is interrupted the placeholder is what ships. Measured here at
  Phase 5a Task 23: a report claimed five green gates for two commits where the third and fifth
  commands had never been run at all, and the controller found it by running them and getting exit
  101. This is one step later than the `cargo fmt --edition` failure above -- there the command was
  malformed and never executed, here the command was fine and the reading was invented -- and the
  two produce an identical-looking green line. **Also say which command printed a figure**: `248 of
  248` was real and came from `cargo test -p rexx-exec --test corpus`, not from the gated workspace
  run the report credited, and `cargo test` stops at the first failing binary, so the gated run had
  not reached the corpus harness at all.
* **`cargo test <name>` exits 0 when it matches nothing** -- `0 passed; 0 failed; N filtered out`, status 0. So a mutation harness that runs a test by name and reads only the status **cannot tell "passed" from "does not exist"**. Measured here after a harness restored a file with `git checkout --`, silently discarding uncommitted work, and then reported STAYED GREEN for a test that had ceased to exist. Assert that the run count is non-zero, restore from a copy rather than from git, and never let a mutation harness be the only thing that decides a test is load-bearing.
* **Run anything that may allocate without bound under `memcap LIMIT COMMAND`**, as in `memcap 8G cargo test --workspace --no-fail-fast`.
  **`memcap` is not present in every session, and neither is the cgroup filesystem it needs -- so check `command -v memcap` rather than assuming either way.** Measured 2026-08-20: it was absent at 11:50 with no `/sys/fs/cgroup` at all, and present an hour later with the hierarchy mounted, on the same machine in the same session; under it the gate reports the same 1634 passed / 30 failed the substitute below does. Prefer `memcap` whenever it is there -- it caps a process tree's resident memory where `ulimit -v` caps one process's address space. When it is not, the substitute is `( ulimit -v 33554432; ... )` around the whole gate, and **the size is load-bearing**: each test spawns an interpreter thread whose stack reservation is charged to address space, so the same `HEAD` that reports the expected 1634 passed / 30 failed at `ulimit -v 33554432` reports 1540 / 124 at 8388608, with every extra failure `spawning the interpreter thread: Os { code: 11, kind: WouldBlock }`. A cap that turns green tests red is not a cap, it is a second experiment -- **read the failure text before believing a failure count**, and compare the failing *set* against a run at `HEAD` rather than the count.
It places the command in a fresh cgroup v2 with `memory.max` at the limit, swap pinned to zero so the cap bounds resident memory rather than resident plus swap, and `memory.oom.group` set so a multi-process run dies as a unit instead of limping on with one member missing.
Measured 2026-08-12: a one-line off-by-one mutation in a byte accessor turned a single test binary into an unbounded allocation, the kernel OOM-killed it at an anonymous resident set of 111777896 kB, and it took the session down with it.
The same mutation under `memcap 8G` exited 137 with `peak 8.0G` and left the host alone.
**A mutation run is where this bites hardest**, because its whole purpose is to execute code that is known to be wrong, and wrong code has no bound on what it allocates -- so the cap belongs on the run whose result you are least able to predict.
`ulimit -v` in the oracle wrapper is a different instrument and not a substitute: it caps one process's address space, while `memcap` caps a process tree's resident memory.
* **A green `clippy` is only evidence if the linter re-examined the code, and a warm target directory does not guarantee that.** Measured at the pre-4c boundary: `cargo clippy --workspace --all-targets -- -D warnings` reported exit 0 repeatedly across a session, including at two commits that fail the identical command when it is re-run. The violation (`clippy::byte_char_slices` in `rexx-parse/tests/scanner.rs`) had been in the tree since 2026-07-30 and was never introduced by anything that session. Whether the cause was cargo reusing a per-crate result for an unchanged crate or a toolchain that moved mid-session was not established, and it does not matter: both produce a command that runs, exits 0, and has not linted the code. **Run the lint from a clean target directory at every phase boundary, and treat a same-session green as provisional.** This is the running rule one level up -- the check itself needs checking, not just the claim it makes.

## Repository hygiene

* **No `unsafe` by default, and the workspace enforces it: `unsafe_code = "deny"`. If something appears to need it, stop and say so** -- that has not changed, and it is still the answer in almost every case.
  **What changed (2026-08-11, Moritz): `unsafe` is discouraged rather than banned, and may be allowed in a specific, self-contained situation.** The decision is his and is taken per site, never by the task that wants it.
  **The workspace lint is `deny`, and the record of every granted site is the set of `#[allow(unsafe_code)]` attributes**, asserted by `crates/rexx-core/tests/unsafe_sites.rs`. That test holds two lists -- the files carrying an opt-in, and the files containing an `unsafe` block -- and fails if either changes.
  This replaced `forbid` on 2026-08-20 (Moritz), after the previous rule was built and found unbuildable. It said the granted crate drops `lints.workspace = true` and carries its own `#![deny(unsafe_code)]`; **Cargo refuses that** -- "cannot override `workspace.lints` in `lints`, either remove the overrides or `lints.workspace = true` and manually specify the lints" -- so the crate would have to copy the whole hundred-line clippy table and let it drift. `forbid` also cannot be overridden by an inner `#[allow]`, which is exactly what an approved module needs.
  **The two assertions are separate because the compiler couples them only one way.** An `unsafe` block cannot compile without an opt-in above it, but an opt-in on a module reaches every *submodule* of it: measured 2026-08-20, a new `src/bytes/inner.rs` with an `unsafe` block compiles clean and leaves the opt-in list unchanged, and only the second list catches it.
  `2026-07-27-rust-rewrite.md:23`-`:32` describe the older mechanism and are the thing to correct if that plan is revised.
  **The bar a site has to clear**, so that "self-contained" does not erode into "convenient": the unsafety is confined to one module behind a safe interface; the invariant it rests on is stated at the site and is checkable by reading that module alone; a safe implementation is described and its cost measured rather than assumed; and it is covered by a test that would fail if the invariant broke. **A performance argument alone is not enough -- the measurement has to exist first.**
* **Never `git add -A`.** Stage the exact paths you changed. Never `git reset --hard`, never force-push.
* Scratch files live under the session scratchpad, **never in the repository**. Check `git status` before committing and remove anything stray.
* **Commit first, then read the hash back with `git log`**, then quote it. Hashes written from memory have gone into records wrong twice.
* **Keep comments minimal, and prefer no comment to a paragraph. Moritz, 2026-08-27, and this rule governs every comment rule below it.** A comment documents, at most: **one sentence** of high-level overview; the **parameters, returns and panics**; and **properties that are not clear from the implementation itself**. Nothing else. No prose, no narrative, no record of experiments, no argument for why the code is the way it is.
  **The reason is cost, and it is measured on this tree.** Effort goes into validating prose rather than code. The consolidated review of the Phase 5a gate-close plan found **zero** code defects across 52 files and 3110 added lines, and **five** prose defects; every fix round on this project has introduced new false statements while the behaviour it shipped was right the first time. Prose is the part that rots, the part that has to be re-read, and the part reviews spend their budget on. A comment that does not earn its place costs more than it saves.
  **What survives, and what does not.** A measurement stays only where it states a property the implementation does not show -- "the oracle declines this too, rc 163" is a fact about an external system that no reader can derive from the code. The same measurement written as an account of how the design was reached does not stay. If a property is load-bearing, **assert it in a test**; a test cannot rot silently and a comment can.
  **This narrows the rules below rather than contradicting them.** They govern what a comment may claim once it has earned its place; this one governs whether it earns it. When in doubt, delete: a deleted comment has never yet cost this project a defect, and false ones repeatedly have.
* Comments state the contract at the top and the reasoning at the decision point.
  Never delete a true comment to make a change easier -- but a comment that states something **false** must be corrected or removed, not hedged.
  Prefer `--` over an em-dash. There is no rule against semicolons in comments here.
* **A comment may not name the size of a set.** Not "six functions", not "the eighteen comparison operators", not "all three concatenation spellings" -- name the set, never its cardinality. **Moritz, 2026-08-12: it burns tokens, no human will verify the number still matches, and it carries no value.**
  This is wider than the rule below it and supersedes the reading that a count is safe when its referent is external and immutable: "the twelve comparison operators" was a true statement about the language, and it still goes, because *correct* is not the bar -- carrying value is. A count that has to be corrected has cost twice over: once when it rotted, and once in the correction round, which is this project's most reliable source of new false statements.
  **Measurements keep their numbers**, and the difference is that they are evidence: `rc 245`, `8 instructions per pass`, `peaked at 69,108 KB`, oracle bytes, error numbers like 41.1, register indices. Those are verifiable by re-running, and they are why the sentence exists.
  **Code is untouched by this.** An enumeration in code -- a `matches!` listing the operators, a test's own independent restatement of a set -- is the thing that cannot rot. It is the prose *about* the enumeration that does.
* **A comment may say what the oracle does, what the C++ does, and what was measured. It may not say how many call sites there are, what every other site does, or what a gate currently totals.**
  Those change without the sentence being reread. **If such a claim is load-bearing, assert it in a test; if it is not, delete it.**
  Measured across one task: comments pointing at *immutable* referents -- oracle bytes, C++ citations, benchmark numbers -- needed **zero** corrections over four commits, while every false comment was a *mutable repo aggregate*. Six shipped, and each arrived in a commit correcting the previous one; corrections are this defect's habitat, because correcting a comment means writing about the code's context, which is exactly what you cannot see from the line you are editing.
* **A claim must not be falsifiable by the act of committing it.** Never quote a search command inside the file it searches: a comment reading ``grep -c 'foo()' this_file.rs`` -> 1 makes the answer 2 the moment it lands. Assertions are the one mechanism here with a clean record -- they are re-run, and a mutation proves they can fail.
* **Phase status is a mutable aggregate, and it is the one that actually rots.** "Owned by 4c", "not yet implemented", "in scope since Task 3", "the ten prefixes this crate emits today" are all facts about where the implemented/not-implemented boundary sits, and that boundary moves every time a task lands. The evidence is a contrast, not a count: `corpus/keyword-exempt.txt` *derives* these facts from the loud message and polices them in both directions, and needed **no** correction across thirteen tasks, while `INSTRUCTION_WITNESSES`' one-line count comment stated the same kind of fact in prose and rotted **four times** -- 20, 19, 17/16, 14/14 -- each correction falsified by the next task. Same data, different medium, opposite outcome. (A first version of this rule cited "522 comment lines" as the size of the defect. That figure was the union of *names a phase* and *uses a word like "currently"*, and about half the second group turned out to be run-time state -- "the frame currently executing", "not yet asked" -- which was never the defect and cannot be told apart by grep. A count of a mutable in-repo aggregate, conflating two populations, inside the rule forbidding exactly that.) (This rule's own illustration used to give that table's size as a row count. The count was written twice and was wrong both times, each correction falsified by a later task, which is the rule catching itself: a count of a mutable in-repo aggregate, inside the sentence forbidding exactly that. It is deleted rather than corrected a third time, because the contrast the illustration draws -- a derived, policed table against a prose count -- holds at every size and needs no size to make it.) **Assert the boundary or do not write it down.** Where a property holds regardless of where the boundary sits, state the property: `tests/support/mod.rs`'s normalisation covers every marker `trace_prefix_table` lists, whether or not this crate emits it yet, and that sentence cannot go stale.
* **Comments say what the code does, not how it got there.** No task numbers, no "used to", no account of what moved or shrank. History belongs in the commit message and the SDD ledger -- both searchable, neither re-read on every edit. A measurement justifying the *current* design stays, because it is evidence for the contract: "measured, the oracle declines this too" earns its place. "Task 3 implemented `Call::Named` and Task 7 implemented `Call::Trap`, so three rows are gone and this expansion shrank with them" is history, and it was fourteen lines wrapped around a function with two arms.
* **An exhaustiveness claim is only as good as the enumeration behind it, and only if that enumeration lives outside this repository.**
  "Every `TRACE` letter `TraceSetting::parseTraceSetting` accepts" survives, because that C++ switch enumerates them -- an external, checkable referent, and the sentence cites it rather than counting it. (It was written as "all nine accepted `TRACE` letters" and reviewed as safe on the strength of the referent; the count goes under the rule above, which the referent does not rescue.) "All three ways a label is reached" was false -- an internal function call is another -- because **nothing** enumerates routes; it was a universal quantifier wearing the same clothes as the safe kind.
  The refinement, earned separately: *something enumerating it* is not enough. `WITNESS_PREFIXES` genuinely enumerates, and "`>>>` appears in every witness below" still rotted -- because that `const` is in this repo and changed when a witness landed. **The axis is whether the enumeration can change without the sentence being reread.** Outside the repo -- the C++, the oracle's own tables -- cite it and prose is fine. Inside the repo, assert it.
  When neither is available, state the property and its citation rather than a count: "a label echoes when the `LABEL` instruction is executed, per `RexxInstructionLabel::execute`" is checkable; "the three ways" is not, and "the four ways" would only be the same mistake with a bigger number.

## Method

Habits, each earned the expensive way.

* **A summary of a measurement is a new claim, and it needs the measurement re-run -- not the prose reread.** Restating a result in different words is authorship, not quotation, and the restatement can be false while every word around it is true. Measured here: a correction commit compressed "blocks on an unresolved routine call" into "blocks on a builtin", which contradicted a sentence two lines above it in the same paragraph and survived because it was locally plausible. Neither more care nor rereading the diff reaches this; only re-running does.
* **"Can fail" is not "adds coverage."** A mutation going red proves a test can fail. It does not prove the test catches anything the existing suite would have missed. The extra step costs one run: apply the candidate mutation to the suite *without* the new test. Two corpus programs were deleted here after that check showed existing programs caught their mutations identically -- the suite got smaller and stronger, which is the opposite of what a coverage count rewards.
* **When tempted to explain why something cannot happen, run it instead.** Six confident "X cannot be reached" claims have been wrong here, every one a sound inference from a *true* premise missing a second premise nobody knew to look for. More care produces the same answer with more confidence; only running separates them.
* **A test that cannot fail is a defect.** Eight have shipped, two of them fixes for earlier such findings. For every assertion ask: what degenerate implementation satisfies this, and would deleting its subject leave it green?
* **Pair a refusal with its adjacent success.** Three times the test that made a fix *correct* was not the failing case but the neighbouring passing one, because that is what pins the rule to the property you think it is rather than to something coincidental.
* **When a plan or brief is wrong, correct the plan -- not the message that carries the work.** A correction written into a dispatch, a review summary, or a chat reply is read once and then lost, because briefs regenerate from the plan, reviewers review against the brief, and a later fix round hands a *fresh* worker the same brief path. Measured here: a `trace r` divergence found during Task 7 was recorded only in a review summary, was absent from Task 9's brief when it arrived, and survived solely because it happened to be re-measured. The same applies to anything one task discovers that another task owns -- write it into the receiving task's text at the moment it is found. If a correction is worth making, it is worth making where the next reader will see it, and if the plan itself contradicts the tree or itself, fix the plan and say in it what was removed and why.
* **A method that exists and does nothing is not implemented, and building one lays a trap for the next phase. Moritz, 2026-09-04.** The next phase reads "the method is there" as "the method works" -- that is the default reading and no amount of care at the far end changes it. **Prefer not building the shell at all** to building one that answers nothing.
  **Measured, and this rule was written after it cost a phase's scoping.** Phase 5c built constructors rather than bodies. `.MutableBuffer~new` answers an instance, the instance keeps no contents, and all 51 documented instance methods refuse -- `dispatch.rs`'s own doc says the contents "are not kept, and nothing that would read them answers". `.File~new('/tmp')` then dies at `MutableBuffer~length`, so **no `File` method is reachable at all**, and Phase 7 was scoped on `File`'s 57 `answers` rows before anyone opened one.
  **A loud refusal makes hollowness safe. It does not make it done, and the two get confused because the evidence looks the same.** Every reader refusing is what keeps a stateless constructor from being a *wrong* answer, and that part of the 5c design was right. What it does not do is stop a later reader counting the class as built.
  **The mechanism to distrust is existence-shaped evidence**: `hasMethod` readbacks, "the constructor answers", "the class is registered", "the row agrees". Each is satisfied by a shell. Table C's rows are `hasMethod` readbacks and a hollow class scores full marks; a plan reviewer caught a whole phase planned on moving them before any code was written. `corpus/method-bodies.txt` was built to answer the harder question and **inherits the same blindness one layer down**: for a class whose zero-argument constructor raises, both sides raise identically, every line below is unreached, and the row records `answers`. `File`'s 50 instance rows are that, and say so in their own header.
  **So: build the body, or leave the name unbound.** If a phase deliberately ships a shell anyway, it owes three things and they are not optional -- the refusal at every reader, a sentence at the site saying the state is not kept, and **an entry in the phase's own handover naming the class as hollow**, because that is the text the next phase reads. A count of rows that "answer" is not a count of methods that work, and no gate in this tree currently distinguishes them.
