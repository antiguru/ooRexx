# Every extracted `base/keyword` body that does not pass today, and what
# would actually make it pass. One `GROUP::METHOD<TAB>unblocked_by` per line;
# lines starting with # are comments.
#
# Measured at ooTest r13178. This is the committed set
# `keyword_assertions.rs` polices in both directions: a body here that starts
# passing is as red as a body not here that starts failing, so an improvement
# shows up in a diff rather than being quietly absorbed.
#
# The `unblocked_by` column is NOT hand-written FOR A BODY THAT FAILS LOUDLY:
# there it is the owning phase `rexx-exec`'s own message names, re-derived on
# every run, so this file cannot drift from `instruction_owner`/`expr_owner`
# and a blocker moving between phases goes red here.
#
# Two limits on that, both real:
#
#   * A derived owner says what a body hits FIRST, not what would make it
#     pass. Three bodies are known to have a second blocker behind the first
#     -- worse, they are not equivalent to the method they came from at all:
#     CALL::test_expression and CALL::test_literal fail under the C++ oracle
#     itself (Error 43, Routine not found) because they call ::routines the
#     standalone program does not carry -- measured, routine "label" and
#     routine "". NUMERIC::test_42 is the third and is the one whose first
#     blocker has since been removed, so it now reads what was always behind
#     it, RAISED: `::method "test_42"` is the only method in its
#     neighbourhood with no `return` before its trailing
#     `dig: Return digits()`, so the extracted program falls into that
#     subroutine and its RETURN value becomes the program's exit code.
#     Measured, the C++ oracle exits 3 on the same program, so this is the
#     extraction and not a divergence.
#
#     CALL::test_on_name WAS LISTED IN THAT SENTENCE AND DOES NOT BELONG.
#     Its first blocker is a BUILTIN, not a missing ::routine -- the run's
#     own breakdown reads routine "CHARIN", from `call charin "/"`, which is
#     the third clause of the body. A correction that over-reaches is still
#     a false statement, and this one over-reached by one name.
#
#   * A derived owner is 4c for EVERY unresolved routine name, including
#     names Phase 4 excludes outright. `Loud::unresolved_call` carries a
#     fixed "4c" because a builtin and a ::routine are the same thing to the
#     message. So three of the five 4c rows below are really waiting on a
#     builtin: ASSIGNMENT::test_3 on DATATYPE (Task 11's), and
#     CALL::test_on_name and CALL::test_9 on CHARIN and LINEIN, which are
#     WHOLE exclusions and so Phase 7's. Measured from the run's own "first
#     construct hit" breakdown, not read off this file.
#   * The `defect:` rows below are NOT derived -- every assertion failure is
#     mapped to one constant. What has teeth for them is membership, not the
#     label: a body that starts failing its assertions and is not listed here
#     goes red as an unaccounted failure. A second defect class would need
#     the constant split by hand.
#
#   4c  Bodies blocked on a construct rexx-exec names as 4c's -- a builtin
#       routine it does not run yet, or instruction work 4c still owes. No
#       body here is blocked by Phase 5, so 4b owes this table nothing
#       further. Which names are still blockers is the derived half of this
#       file and moves as they land; the run's own breakdown is the current
#       answer, never this sentence, and no count of either group is written
#       down here for the same reason.
#
#   RAISED  Not an attribution at all: the harness's own word for "exited
#       non-zero and named no construct", so there is nothing to derive a
#       phase from. A row carrying it needs its cause written into this
#       header, as the second bullet above does.
#
#   Phase 7  The `ADDRESS` bodies that do more than name an environment.
#       Naming one runs; issuing a command to it, and the `WITH` redirection
#       that says where a command's three streams go, both need the command
#       dispatch. Two of these three are `WITH` forms and the third,
#       `test_environment_path_null`, is a plain command -- `address "path"
#       ""` -- so "the WITH bodies", which this line used to say, named the
#       wrong set.
#
#   defect:compound-do-control-variable  6 bodies. NOT a phase gap: a real
#       divergence, confirmed by running each rewritten program under the C++
#       oracle as well, where all six pass. Every one uses a compound
#       variable as a DO control variable (`Do cv.j=1 To 5`, `Do a.i=a.i to
#       16`, `Do i.j=0 to 6 ... End i.j`). Two measured witnesses:
#         c=0; j=1; Do cv.j=1 To 5; c=c+1; End; say '['c cv.j']'
#           oracle [5 6], rexx-exec [5 CV.1] -- the control variable is never
#           assigned when it is compound.
#         a.=0; i=1; Do a.i=1 To 3; If i>7 Then Leave; i=i+1; End; say '['i']'
#           oracle [8], rexx-exec [4] -- the oracle re-resolves the compound
#           name each iteration, so which variable controls the loop changes
#           as `i` does.
#       DO is 4a's, so this is a 4a defect this 4b table surfaced. It is
#       recorded rather than fixed here: Task 11 measures, and a DO change
#       belongs with the tasks that own DO.
