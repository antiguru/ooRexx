# Table D's row set: the directive and option surface, from dire.xml and
# from interpreter/parser/DirectiveParser.cpp, unioned.
#
# One `directive<TAB>keyword<TAB>position<TAB>side<TAB>evidence` per
# line, grouped by directive in the order DIRECTIVES lists and sorted
# within a directive by (keyword, position).
#
# `position` is `subkeyword` or `value-of(NAME)`. The markup does not
# distinguish an option from an option's value -- ::OPTIONS' <option>
# occurrences include ENGINEERING and SCIENTIFIC, which the prose says
# are values of FORM -- so the parser's switch nesting settles it.
#
# `side` is which authority produced the row. `cross-reference` means the
# section documents the name and the directive's own parser has no arm
# for it; the evidence says where one does handle it. ::CLASS's CLASS row
# is the worked case: its METACLASS paragraph describes ::METHOD's CLASS
# option.
#
# The parser side reads every SUBDIRECTIVE_* and SUBKEY_* token inside a
# directive function, not only the SUBDIRECTIVE_* arms of its own switch,
# and `evidence` records which form each is. Two reasons, both measured:
# ::OPTIONS' FORM and NUMERIC values reach the parser as SUBKEY_* arms,
# so the narrower rule marks four implemented keywords as documented-only;
# and ::RESOURCE's END is recognised by an `if` rather than a `case`, so
# the narrower rule gives it no row at all though it is both documented
# and implemented.
#
# DirectiveParser.cpp is tracked in this repository, so it needs no
# revision stamp of its own -- a change to it lands in the same history as
# this file. The stamp below is dire.xml's.
#

# module is `src/docs/directives.rs`. Re-derived and compared in both
# directions by `tests/extract_docs.rs`.
