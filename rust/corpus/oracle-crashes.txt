# Programs known to crash or exhaust the C++ oracle interpreter
# (/home/moritz/dev/repos/ooRexx/build/bin/rexx), so nobody has to
# rediscover them by running them. This file exists precisely so a sweep,
# a probe, or a corpus generator can exclude these by reference rather
# than by folklore passed between sessions -- do not run any of the
# programs below to "confirm" the entry still holds; that is the failure
# mode this file exists to end.
#
# Every entry was measured under the standard oracle wrapper:
#   ( ulimit -v 1048576; LD_LIBRARY_PATH=/home/moritz/dev/repos/ooRexx/build/lib \
#     /home/moritz/dev/repos/ooRexx/build/bin/rexx /abs/path/FILE )
# run from a fresh empty directory (the scratchpad root is on the oracle's
# own external-routine search path and must never be the run directory).
#
# The failure modes are not folded into one label. An entry is a deterministic
# memory-safety defect in the C++ (SIGSEGV, rc 139); or a resource-exhaustion
# hazard (unbounded allocation, OOM-killed), which is not a crash in that
# sense; or an INDEFINITE BLOCK -- the process alive and healthy, consuming no
# CPU, parked on a wait that nothing in the program can ever satisfy. Each
# entry below says which it is.
#
# The third mode was added on 2026-08-23 for entry 7 and needs the wrapper
# above to grow a deadline: a block produces no bytes and no status of its
# own, so it is the one mode whose entry can only be characterised by killing
# it. Every such entry states the deadline it was killed at, and rc 137 there
# is the kill and not the oracle's answer.

## 1. `select; when 1 = 0 then; when 2 = 2 then nop; end`

    select
      when 1 = 0 then
      when 2 = 2 then nop
    end

Effect: SIGSEGV, rc 139, deterministic.

Cause: upstream SourceForge **SF #2018**, filed and commented with the
crash site and a verified guard. An orphaned `WHEN` (a `WHEN` clause with
no body, immediately followed by another `WHEN`) reaches a null-pointer
dereference in the C++ parser/interpreter's `SELECT` handling. Not a
oorexx-rust-rewrite bug and not something this crate needs to reproduce --
`rust/CLAUDE.md` and every phase plan already carry "never run this" for
the same reason this file now carries the account.

## 2. `say date('M','0','D')`

    say date('M','0','D')

Effect: SIGSEGV, rc 139, deterministic (measured 3 runs of 3).

Cause: `DATE`'s day-of-year range check
(`interpreter/expression/BuiltinFunctions.cpp:1163`) is
`yearday < 0 || yearday > YEAR_DAYS + 1 || ...`, so `0` passes it -- day
zero is not the day-of-year range's lower bound, it is one below the
first valid day, and the check only rejects strictly negative values.
`RexxDateTime::setDay` (`classes/support/RexxDateTime.cpp:457-475`) then
computes `month = 0` for a zero day count, and the `'M'` output style
reads `monthNames[month - 1]` (`RexxDateTime.cpp:526`) -- `monthNames[-1]`,
one element before the array, whose stored bytes happen to form an
invalid pointer that a subsequent string read dereferences. Other output
styles derived from the same `month == 0` state (`D`, `B`, `W`, `F`, `T`)
read a different out-of-bounds slot (`monthStarts[-1]`) that happens to
hold `0` on this build and so return stable, wrong-looking-but-harmless
numbers instead of crashing -- `'M'` is the one that dies because it is
the one whose out-of-bounds read is dereferenced as a pointer rather than
used as an integer. Found 2026-08-07 building this project's differential
corpus; filed upstream 2026-08-22 as **SF #2082**.

## 3. `changestr('a'||'00'x,'aa','ZZZ')`

    say changestr('a'||'00'x, 'aa', 'ZZZ')

Effect: SIGSEGV, rc 139, deterministic.

Cause: the tail of `StringUtil::pos`'s own window-overrun defect
(DEVIATION 3, `docs/superpowers/plans/phase-4-exclusions.txt`, and
`find_forward`'s own doc comment in
`rust/crates/rexx-exec/src/builtin/string.rs` for the full mechanism).
`POS`'s search can match one byte past the end of the haystack, where the
C++ reads the `RexxString`'s own NUL terminator -- so a needle ending in
`'00'x`, searched to the end of the haystack, can match through that
terminator (`pos('a'||'00'x,'aa')` is 2 on the oracle, a match "ending"
one byte past a two-byte haystack). `POS` and `COUNTSTR` merely report
that position and survive; `CHANGESTR` copies the haystack up to and
including the matched needle, and copying "through" a match that runs
past the buffer's own bytes is what walks off the end of the allocation
and crashes. Found 2026-08-14 while fixing the Rust port's own `POS`;
filed upstream 2026-08-22 as **SF #2083**, which carries this crash and
the in-string wrong answer as one ticket because one off-by-one causes
both.

## 4. `NUMERIC DIGITS` above 1000, used in an arithmetic operation

    numeric digits 1001
    say 1 + 1

Effect: **not a SIGSEGV** -- runaway allocation, OOM-killed by the host
(or by the `ulimit -v` wrapper's own address-space cap, which is what
turns an otherwise slower failure into an immediate one under the
standard oracle invocation above). Recorded here as a hazard rather than
a defect: raising `NUMERIC DIGITS` widens the precision every arithmetic
operation carries, and at four figures and above the C++ allocates
proportionally to that precision on a scale this project has not
characterised further, so the safe rule is the blanket one already in
`rust/CLAUDE.md` and every phase plan -- never set it above 1000 in a
probe, full stop, rather than searching for the exact boundary.

## 5. One clause queuing the same `CALL ON` condition twice

    call on user c1 name h1
    zr = ra() + ra()
    say 'after' zr
    exit 0
    ra:
    raise user c1 return 1
    h1:
    say 'h1' sigl
    return

Effect: **SIGSEGV, rc 139**, after the handler has run once. The oracle
prints `h1 2` on stdout and then dies, so what kills it is the boundary
reaching the *second* copy of an already-delivered condition name, not
the queuing of it.

Found 2026-08-15 while measuring what a clause boundary does with more
than one pending condition, and it bounds that measurement: the same
clause with two *differently* named conditions answers cleanly and is
how the rule was established -- `zr = ra() + rb()` gives `h1` then `h2`
then `after`, both handlers reporting the raising clause's own line, and
a three-name version gives all three in the order they were queued. So
the oracle drains a boundary in queue order, and this program is the one
shape in that family it cannot answer for.

Consequence for this crate: a boundary that drains has to decide what to
do with a repeated name, and there is **no oracle behaviour to match**.
Whatever it does is unconstrained here, and must not be described as
agreeing with the oracle. Filed upstream 2026-08-22 as **SF #2084**.

## 6. An array with a leading empty slot as the sole subscript of `~at`

    a = (1,2)
    say a~at((,2))

Effect: **SIGSEGV, rc 139**, deterministic (measured 3 runs of 3, and the
same for `a~at((,,3))`).

Cause: `ArrayClass::validateIndex` spreads a lone array argument into the
subscript list by taking its **item count** alongside its **slot array**
(`classes/ArrayClass.cpp:1219`-`:1226`): `indexCount = indirect->items()`
and `index = indirect->data()`. `items()` counts the non-empty slots and
`data()` is the raw slot array, so an array whose leading slot is empty and
whose item count is one hands `validateSingleDimensionIndex` an
`indexCount` of 1 with `index[0] == OREF_NULL`, and `:1264` calls
`index[0]->requiredPositive(argPosition)` on it.

The neighbours bound it and are all clean: `a~at((1,))` answers `1` (one
item, leading slot filled), `a~at((1,,3))` is 93.926 (two items, so the
count is rejected before either subscript is read), and `a~at((,))` is
93.901 (no items at all). Any array whose first filled slot is not slot one
and which holds exactly one item is the crashing shape.

Consequence for this crate: **there is no oracle behaviour to match**, so
`rexx-exec` refuses the shape rather than answering it -- `Loud::
array_index_hole`, whose own doc names
`dispatch.rs`'s `an_expanded_index_of_one_empty_slot_is_loud` as the
instrument. No differential row can cover it.

Found 2026-08-22 while building this crate's own `~at`; filed upstream the
same day as **SF #2085**.

## 7. `GUARD ... WHEN` in a method, with an expression that is false

    say .K~m
    ::class K
    ::method m class
      expose v
      v = 0
      guard on when v = 1
      return 'no'

Effect: **neither a SIGSEGV nor an exhaustion -- an indefinite block**, the
third mode this file's header names. Measured twice under the standard wrapper
with `timeout -s KILL 10` added: rc 137 (the kill, not an answer), nothing on
stdout, nothing on stderr. **That much is direct evidence and is what makes
"for ever" the right reading and "slow" the wrong one.**

**The "parked rather than spinning" half is predicted, not measured.** It was
argued here from a `/usr/bin/time -v` run reporting 0.00 s user and system
over 5.00 s elapsed, and that instrument is now known to be blind to the
distinction: measured 2026-09-03, `/usr/bin/time -v timeout ... <binary>` run
against `do forever; nop; end` -- a program `/proc/<pid>/stat` shows in state
`R` at 700 utime ticks over seven seconds -- also reports `User time 0.00`,
`System time 0.00`, `Percent of CPU this job got: 0%`. GNU time's `wait4` sees
only `timeout`. A park and a full-core spin are indistinguishable through it.

`guardWait` blocking on a condition variable is what the cause below predicts,
and the same prediction held when it was checked directly for this file's
`Message~result` entry. It has not been checked for this one, because doing so
means running this program, which this file's own header forbids.

Cause: `RexxInstructionGuard::execute` evaluates the expression and, while it
is false, loops on `context->guardWait()`
(`instructions/GuardInstruction.cpp:167`-`:185`). That releases the object's
scope and waits to be woken by another activity changing one of the exposed
variables the expression names. A program with one activity has nothing that
can change it, so the wait has no end. `GUARD OFF WHEN` blocks identically:
the `WHEN` form waits whichever way the `ON`/`OFF` flag is set, and
`guardWait` releases the object's scope in both cases. The flag decides the
state the activity returns to when it is awake, not what the wait holds
(`instructions/GuardInstruction.cpp:147`-`:150`).

The neighbours bound it and are clean, all rc 0 and all agreeing with this
crate on both engines: the same method with `v = 1` answers, so it is the
expression's *value* and not the `WHEN` form that blocks; and `guard on` and
`guard off` with no `WHEN` at all are no-ops.

**The `expose v` line is load-bearing in the repro and dropping it does not
block.** Measured: the same method without it, `guard on when 1 = 0`, is a
clean `Error 99.913 GUARD instruction did not include references to exposed
variables.` at rc 157 in 0.00 s, three runs of three. What that check tests is
which names the expression mentions, and nothing about whether the expression
can ever change: `LanguageParser::captureGuardVariable` records a variable only
when `isExposed(varname)` holds (`parser/LanguageParser.cpp:2024`), and the
raise fires when that list comes back empty
(`parser/InstructionParser.cpp:2640`-`:2646`). The maintainers state their
reason for it there -- "if using GUARD WHEN, we will never wake up if there are
not at least one object variable accessed." -- which is the check's motivation
and not its reach. Measured at the neighbours, three runs each: `guard on when
w = 0`, with `w` local and the expression already true, is the same 99.913 at
rc 157 even in a method that exposes something else, and `guard on when v = v`,
which no other activity's change could ever falsify, answers rc 0. So a reader
shortening this program to the `WHEN` clause alone measures the translation
check instead of the block.

Consequence for this crate: **there is no oracle behaviour to match**, so
`rexx-exec` refuses the shape rather than answering it -- `Loud::
guard_when_false`, whose own doc names `run/tests.rs`'s
`the_guard_instructions_answers_and_the_phase_6_refusals` as the instrument. No
differential row can cover it, and there is not even an exit status to compare
against: the rc 137 above is the deadline killing the process, not an answer.
Entry 4 shares that much -- its rc is the OOM kill -- and differs in having a
cause that consumes something; this one consumes nothing at all.

Found 2026-08-23 while building this crate's `GUARD`; the CPU-time reading is
that task's review round. **No upstream ticket.** The block is what
`GUARD ... WHEN` is specified to do, and whether an interpreter should detect
that no other activity can ever satisfy a particular wait is a design question
this project has not put to the maintainers.

## 8. A metaclass whose `NEW` answers something that is not a class

    say .object~subclass("k", .MyMeta)~id

    ::CLASS MyMeta SUBCLASS Class
    ::METHOD new CLASS
      return 'x'

Effect: SIGSEGV, rc 139, deterministic (measured 3 runs of 3), stdout and
stderr both empty.

Cause: `RexxClass::subclass` builds the class object by sending `NEW` to the
metaclass and casts the answer without checking it --
`RexxClass *new_class = (RexxClass *)meta_class->sendMessage(GlobalNames::NEW,
class_id, p);` (`classes/ClassClass.cpp:1579`), and the very next statement
dereferences it, `new_class->setPackage(package)` (`:1582`). A metaclass may
carry its own `NEW`, and nothing constrains what that method returns, so a
`RexxString` reaches a `RexxClass` field write.

The neighbour that bounds it: the same metaclass whose `NEW` forwards
(`forward class (super)`) answers rc 0 and builds the class, and the same
`::METHOD new CLASS` reached *directly* -- `.MyMeta~new("k")~id` -- is a clean
`Error 97.1: Object "x" does not understand message "ID".` at rc 159. So it is
the cast inside `subclass`, not the overridden `NEW` itself, and a reader
shortening this program to the direct send measures the wrong thing.

Consequence for this crate: none to match. `rexx-exec` refuses a metaclass
whose `NEW` resolves anywhere other than `.Class` at rc 120 before it builds
anything -- `dispatch.rs`'s `factory_metaclass`, whose doc carries the reason
-- so the crashing shape is one this crate cannot reach.

Found 2026-08-26 while building `Class~subclass`. **No upstream ticket.**

A `FORWARD` without `CONTINUE` that resolves back to the method it is in

    o = .K~new
    say o~m

    ::CLASS K
    ::METHOD m
      forward

Effect: SIGSEGV, rc 139, deterministic (measured 3 runs of 3), stdout and
stderr both empty.

Not about any one option. `forward` bare is the minimal form; `forward
array(1,2)` and `forward message('M')` crash the same way, and so does the
subclass shape where a `::METHOD m` overriding a superclass `m` forwards
without naming a target. What they share is that `FORWARD` supplies the
defaults: `RexxActivation::forward` (`execution/RexxActivation.cpp:1335`-`:1347`)
fills an unspecified target with `receiver` and an unspecified message with
`settings.messageName`, so the send goes back to the method it left.

Cause: the non-continuing path makes the activation a phantom **before** it
sends. `execution/RexxActivation.cpp:1365`-`:1391`: it calls
`settings.setForwarded(true)`, then `stopExecution(RETURNED)`, and only then
`target->messageSend(...)`, finishing with `termination()`. The comment above
it says so -- "this activation becomes a phantom, and we issued the message as
if we don't exist". Because the activation is already stopped, the recursion
does not grow the interpreter's own activation depth, which is what the
resource guard counts; it grows the C++ stack instead, and that runs out
without anything checking.

The neighbour that bounds it, and it is one keyword: **the same program with
`forward continue` is a clean `rc 245`** with a traceback, because the
continuing path at `:1349`-`:1361` sends without terminating the activation, so
the depth guard sees the frames. Ordinary unbounded Rexx recursion -- a
`procedure` that calls itself -- is also a clean `rc 245`. So the interpreter
does have the guard; the phantom path is what steps around it.

Consequence for this crate: **nothing to match, and a licensed divergence.**
The oracle's answer to this shape is a signal and not a behaviour. This crate
sends with the forwarding activation still on the stack, so its own
`MAX_ACTIVATION_DEPTH` guard counts the recursion: measured on the crate alone,
both engines, the program above is **rc 245**, stdout empty, stderr ending
`Error 11.1:  Insufficient control stack space; cannot continue execution.` --
the clean answer the oracle itself gives `forward continue`. The divergence is
recorded in the same terms Task 9's list uses for the oracle's `Error 5` stack
overflows; matching an oracle crash is not a target.

**With a `REPLY` before the FORWARD, this crate does not terminate**, and that
is a second divergence rather than a narrowing of the first. Measured on the
crate alone, both engines, `timeout -s KILL 60`: a method doing `reply` and
then a FORWARD that resolves back to it is rc 137 at the timeout with both
descriptors empty, where the same shapes without the `reply` are rc 245 in
under 0.08 s. The replied body is queued and `Interp::run_deferred_replies`
drains a queue each drained body refills, so no activation depth grows and the
guard above never fires -- `VmRSS` flat at 17,760 kB, the interpreter thread's
stack 24 frames and not growing. The oracle's answer to this member cannot be
measured, because it is this shape. No bound has been chosen; Task 9's list
carries the reasoning.

Found 2026-09-01 by the controller while measuring `keyForward`'s six options
for Task 4's brief. **No upstream ticket.**

`Message~result` on a message whose send has not been made

    m = .Message~new(.Object~new, 'STRING')
    say m~result

Effect: **an indefinite block**, the third mode this file's header names.
Measured under the standard wrapper with `timeout -s KILL` added: rc 137 (the
kill, not an answer), nothing on stdout, nothing on stderr, twice at 15 s and
8 s.

**It is parked, not spinning**, measured by launching the interpreter directly
-- no `timeout` between the shell and it -- capturing `$!` and sampling
`/proc/<pid>/stat`: state `S` at three and at seven seconds, **0 utime and 0
stime ticks over the four seconds between**, one thread, `wchan`
`futex_do_wait`. Do not use `/usr/bin/time -v timeout ... <binary>` for this:
GNU time's `wait4` sees only `timeout`, so it reports `timeout`'s rusage and
prints `0.00` for a program burning a whole core.

The control that makes those zeros mean something, sampled the same way in the
same run (`CLK_TCK` 100): `do forever; nop; end` reads state `R` with utime 99
at one second and 700 at seven, where this program reads `S 0 0` at both. And
the wrapper above was run against **that** spinner to show it cannot tell the
two apart: it reports `User time 0.00`, `System time 0.00` and `Percent of CPU
this job got: 0%` over 6.00 s elapsed for the 700-tick program.

Cause: `MessageClass::result` waits for the message to complete
(`classes/MessageClass.cpp:279`). `Message~new` builds the message without
dispatching it -- `MessageClass::newRexx` ends at `completeNewObject`
(`:896`), with no send -- so nothing will ever complete it and the wait has no
end.

The neighbours bound it and are all clean, rc 0 under the same deadline:
`~completed` and `~hasError` on the same unsent object answer `0` and `0`;
`~messageName` and `~target` answer `STRING` and `an Object`; `m~send` then
`m~result` answers `an Object`; and `.Object~new~start('STRING')~result`, whose
send was made by `~start`, answers `an Object`. So it is the *unsent* state and
not `~result` itself.

Consequence for this crate: **there is no oracle behaviour to match**, so
`rexx-exec` refuses the shape rather than answering it --
`Loud::unsent_message_result`, whose own doc carries these measurements. No
differential row can cover it, and the rc 137 above is the deadline killing
the process rather than an answer.

Found 2026-09-03 while building `Message~new` for Phase 5c Task 2. **No
upstream ticket.** The wait is what `~result` is specified to do, and whether
an interpreter should detect that no activity can ever satisfy a particular
one is the design question entry 7 already puts and this project has not put
to the maintainers.

A strict *ordering* comparison sent to a string with no argument

    say "abc"~"<<"

Effect: SIGSEGV, rc 139, deterministic (measured 3 runs of 3), stdout and
stderr both empty.

The family is exactly six, and the boundary is sharp. All six of `<<`, `<<=`,
`>>`, `>>=`, `\<<` and `\>>` crash this way. The other twelve comparison
operators sent identically -- `=`, `==`, `<`, `<=`, `>`, `>=`, `<>`, `><`,
`\=`, `\==`, `\<`, `\>` -- are a clean `Error 93.903: Missing argument in
method; argument 1 is required.` at rc 163. **Strict equality is clean and
strict ordering is not**, so "strict" is not the axis.

It is the receiver's class and not the operator. `1~"<<"` is the same clean
93.903 at rc 163, and `.Object~new~"<<"` is `Error 97.1` at rc 159 because
`Object` has no such method.

Cause: `RexxString::primitiveStrictComp` opens by dereferencing its argument
with no check at all -- `RexxObject *other = otherObj->requestString();`
(`classes/StringClass.cpp:920`-`:923`) -- and the six operator methods are the
ones that route to it: `strictGreaterThan` (`:1297`), `strictLessThan`
(`:1303`), and the two at `:1311` and `:1317`. A method sent without its
argument arrives with `OREF_NULL`, and that is a virtual call on a null
pointer.

The twelve clean ones go through `RexxString::comp` (`:753`), whose first
statement is `requiredArgument(other, ARG_ONE)` (`:762`). The `CompareOperator`
macro they all share (`:1248`) guards only `.nil`, so it is not what saves
them.

**The checked twin already exists and is the one the operators do not call.**
`RexxString::strictComp` (`:874`) carries a body identical to
`primitiveStrictComp`'s and opens `RexxString *other = stringArgument(otherObj,
ARG_ONE);` (`:879`). The comment above `primitiveStrictComp` says it is for
calls "by either the Interger or NumberString class", which is a statement
about intended callers rather than a check, and the operator methods use it
anyway. So the upstream fix is a one-liner either way: guard the argument
there, or route those six methods to the twin.

Consequence for this crate: these six are among `String`'s documented instance
rows, and `corpus/method-bodies.txt` classifies a row by sending its name with
no arguments. Today they are `loud`, and that verdict is reached in the
crate-only pass without running the oracle at all. **The first commit that
implements any of them makes the refresh reach the oracle for that row**, where
`method_bodies.rs` will record a `Structural` failure -- "the oracle did not
finish" -- rather than a verdict. That is the instrument behaving correctly and
it is still red, so whoever binds these six decides first how the table is to
carry a row whose oracle answer cannot be obtained.

Found 2026-09-05 building the Phase 5f receiver sweep. **No upstream ticket.**

`Stem~index` and `Stem~hasItem` sent with no argument

    s = .Stem~new
    s['k1'] = 'v1'
    say s~index

Effect: SIGSEGV, rc 139, deterministic (measured 3 runs of 3), stdout and

a clean 93.x at rc 163. So the two crashing methods need that same check and
nothing more.

Same shape as the six `String` shift operators in the entry above -- a native
body whose required argument is unguarded, registered at an arity that is a
maximum -- which makes this the second instance of one upstream defect class
rather than a new one.

Consequence for this crate, and it is the same trap: `Stem~index` and
`Stem~hasItem` are documented instance rows, and `corpus/method-bodies.txt`
classifies a row by sending its name with NO ARGUMENTS. Both read `loud`

for that row**, where `method_bodies.rs` records a `Structural` failure rather

Found 2026-09-06 by Phase 5g Task 0(b)'s argument instrument, which flagged it

`List~removeItem`, `~hasItem` or `~index` on a list holding an empty entry

    l = .List~of('a', 'c')
    l~insert(, 0)
    say l~removeItem('c')

Effect: SIGSEGV, rc 139, deterministic (measured 4 runs of 4), stdout empty
after the preceding line and stderr empty. Four shapes, and they are one
defect: the empty entry can come from `insert(, handle)` or from
`put(, handle)`, and any of `removeItem`, `hasItem` or `index` reaches it.

Cause: a `List` entry is allowed to hold nothing -- `ListClass::insertRexx`
has no `requiredArgument` for its value (`classes/ListClass.cpp:454`) and
`putRexx` requires only the index (`:349`), both measured -- and the three
methods that search by ITEM dereference each entry's value without checking
for it. Same class as the `Stem~index` entry above: a null the search does not
guard.

**Do not construct one of these to confirm it.** The shape to avoid is an
empty `List` entry followed by any item-searching send. `corpus/lang/`'s
`list_operations.rex` is the nearest thing in the tree and is safe: it calls
`put` with a value, never the value-less form.

Consequence for this crate: it answers all four without crashing -- `c`, `1`,
`2` and `0` respectively at rc 0 -- so these are rows where **a differential
cannot be run at all**, not rows where the two sides agree. Nothing in
`corpus/method-bodies.txt` reaches them, because the classification sends no
arguments and an empty entry needs one send to create.

Found 2026-09-07 by the Phase 5g review. **No upstream ticket.**

## 9. `::OPTIONS TRACE ?<letter>` -- a package trace setting with the `?` prefix

    say 'anything'
    ::options trace ?r

Effect: **neither a SIGSEGV nor an exhaustion -- an indefinite block**, the
third mode this file's header names, and the reason this entry is here rather
than left as a note: a block gives no signal at all, so it costs a session the
way an OOM does and offers less to diagnose it with.

Measured 2026-09-08 under the standard wrapper with no deadline: the run
produced nothing on stdout, nothing on stderr, and did not return; it had to
be killed by name. No `timeout` figure is quoted because none was set on that
run, and this file forbids running the program again to obtain one.

**The "waiting for a line on the console" half is predicted, not measured.**
`?` is `TraceSetting`'s debug prefix, and interactive debug pauses after a
traced clause to read a command from the console; the wrapper gives the child
no terminal and nothing else ever writes to it, so nothing can satisfy that
read. It was not confirmed at the C++ site, and confirming it means running
this program.

The neighbour bounds it and is clean: `::options trace r` -- the same letter
with no `?` -- answers rc 0 and this crate agrees with the oracle on all three
descriptors, as it does for each of the nine plain letters. So it is the `?`
and not the letter.

**What to do instead if a probe needs this surface.** Read the setting back
rather than letting it take effect: `Package~trace` answers the one letter and
`Package~options('TRACE')` answers the word, neither of which runs a traced
clause. `corpus/lang/package_settings.rex` reads both. If the *debug* form
itself has to be exercised, it needs a deadline on both sides and a decision
about what a console-less interactive pause should even mean, which no phase
has taken.

Found 2026-09-08 by Phase 5i Tasks 7+8, while measuring what `Package~trace`
answers for each `::OPTIONS TRACE` letter. **No upstream ticket** -- it is not
established that this is a defect rather than interactive debug behaving as
documented with no console attached.
