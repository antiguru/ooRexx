# Task 8.8 truth root ownership

The two-element truth candidate survives because a global return-value root protects its array through the first element's allocating conversion. This is not a proof that `truth_of_string_value` can omit its push. A three-element version exposes a concrete later interval in which that global has been replaced and an unvisited element still needs the array's root. This report recommends that bounded witness, retaining both production pushes and leaving the queued item open pending the implementer's independent mutation result.

This investigation read the primary worktree at initial HEAD `7454d8310`, with unrelated implementer edits present. It ran no builds, programs, mutations or probes and changed only this report. Source citations below are repository-relative and refer to the inspected source, including the existing candidate in `rust/crates/rexx-exec/src/condition/tests.rs:109-126`. The implementer reported the two-element baseline and dropped-truth-push survivor, but those executions were not repeated by this investigator.

## Root model and return ownership

Rust handles and copied `Vec<ObjRef>` values are not automatically GC roots. `RootSet::iter` enumerates globals and activity roots, and `ActivityRoots::iter` enumerates registered temporaries, live registers, slots, aliases and parked values (`rust/crates/rexx-core/src/roots.rs:393-398`, `:747-759`). A temporary frame is only a stack watermark, and popping it truncates all later temporary entries (`roots.rs:456-469`). Array reachability is transitive because the collector enumerates its occupied slots (`rust/crates/rexx-core/src/body.rs:1485`).

Every ordinary Rexx `Flow::Return(Some(value))` writes a global root before returning `Ended::Returned` (`rust/crates/rexx-exec/src/run.rs:607-614`). The target is `EXIT_VALUE_ROOT`, whose spelling is `the program's exit value`, and `root_exit_value` calls `RootSet::add_global` (`rust/crates/rexx-exec/src/lib.rs:363-366`, `:3201-3205`). That operation replaces the prior value under the same name rather than retaining a stack of results (`rust/crates/rexx-core/src/roots.rs:161-166`). Consequently a method result remains globally rooted only until another value-bearing Rexx return or exit replaces it, unless another owner also holds it.

There is no general `Activation.result` or `Activation.call_result` field in the exhaustive current activation root enumeration (`rust/crates/rexx-exec/src/activation.rs:969-1014`). The language `RESULT` variable is populated by `settle_call_result` for a `CALL`, which pushes the value and stores it in the caller's reserved slot (`rust/crates/rexx-exec/src/run/call.rs:1710-1751`). The candidate invokes `==` through an expression send, whose path is `send_operator` to `send_message`, `complete_send`, then `finish_send`, without `settle_call_result` (`rust/crates/rexx-exec/src/eval.rs:1353-1369`, `dispatch.rs:3918-3927`, `:3133-3145`, `:3267-3286`). The activity's `pending_result` and `root_end` are real separately enumerated roots, but their conditional command, condition and activity-completion roles do not establish a blanket owner for this synchronous send answer (`activity.rs:715`, `:729-732`).

## Why two elements survive

The candidate constructs `a = .array~of(.comp~new)` and asks `a~hasItem(.comp~new)`. Its `==` method returns a fresh array containing two fresh `.part` objects, and each `OBJECTNAME` allocates `copies('x', 100)` before returning the inline text `A` (`rust/crates/rexx-exec/src/condition/tests.rs:109-126`). `same_item` keeps the comparison result only in a Rust local before calling `truth`, so neither `condition_value` nor its outer push participates (`dispatch/collection.rs:255-262`). The relevant ownership intervals are as follows.

| Interval | Registered owners and effect |
| --- | --- |
| Constructing the returned array inside `==` | `.Array~of` roots its store as a temporary and places the part handles in its body (`dispatch/array.rs:595-620`). Evaluated argument temporaries and expression registers can also protect the parts while the return clause is active. |
| Leaving the `==` return clause and activation | Clause exit truncates clause temporaries (`run.rs:3189-3205`). `Flow::Return` stores the array in `EXIT_VALUE_ROOT` (`run.rs:610-614`), then method teardown pops the activation and its slots (`run/call.rs:1409-1416`, `dispatch.rs:3686-3701`). The native constructor's temporary is therefore not a permanent owner. |
| Entering truth conversion | `truth_of_string_value` normally adds the array's own temporary (`eval.rs:1614-1622`). With only that push deleted, the exit global still protects the array and both parts. |
| First `OBJECTNAME` allocation | Required-string array conversion copies slot handles into a Rust vector, then iterates them (`dispatch/reqstr.rs:464-466`, `value.rs:691-694`, `:380-393`). The exit global still owns the array throughout the first part's `copies` allocation. The active part is also a method receiver. |
| First `OBJECTNAME` returns `A` | Its own `Flow::Return` replaces the global array root with `A`. The first receiver's method roots disappear when that activation ends. The array vector remains a Rust vector of handles, not a registered root container. |
| Second `OBJECTNAME` allocation | The second part is now the active receiver, rooted by `Activation::method_identity`, so the collector may discard the array without discarding the currently rendered part (`activation.rs:1076-1083`, `activity.rs:798-803`). No unvisited part remains in a two-element array. |
| Joined text returned to truth | The join has copied each rendering into owned bytes. Only afterward does required-string dispatch build and root its returned string (`dispatch/reqstr.rs:187-190`), after which truth reads the bytes and raises 34.901 (`eval.rs:1621-1631`). At this point retaining the original array is unnecessary for those completed bytes. |

The first and second `OBJECTNAME` methods need not retain each other or their array for this schedule to succeed. A method activation roots its own receiver and scope, and construction of that identity is explicit in `begin_method` (`rust/crates/rexx-exec/src/dispatch.rs:3605-3625`). The source array has no reverse edge from a plain part object, and the candidate's part method declares no attribute or exposure that stores one. Thus the two-element output can remain correct even if the array itself has become dead before the join ends, which is why output success alone did not judge the missing push.

## Other possible owners and limits

Required-string return rooting does not protect its input for the whole conversion. Heap text and number answers receive a temporary on the armed fast path, and dispatch roots converted object or byte answers after `required_string_answer` completes (`rust/crates/rexx-exec/src/dispatch/reqstr.rs:114-129`, `:181-190`). A plain array instead enters `StringConversion::Array` and executes the entire item join before any returned-string push (`:343-354`, `:440-459`, `:464-466`). This timing leaves the original array and its not-yet-rendered parts dependent on their existing owners while user `OBJECTNAME` methods run.

Extra interpreter-held roots do not amount to automatic Rust-stack scanning. `Activity::object_roots` explicitly excludes the reusable `value_buffer`, recycled activations and ordinary call tails because their live values are meant to be owned elsewhere (`rust/crates/rexx-exec/src/activity.rs:585-623`). Active native method levels root their receiver and arguments, and active Rexx methods root their own receiver and arguments, which protects the outer `hasItem` inputs and current part but does not create a reference to the fresh `==` result (`activity.rs:737-740`, `activation.rs:1071-1083`). The collection helper's temporary `anchor` is installed only for one collection and popped immediately afterward, so it cannot retain a previous sweep's global array after that global is replaced (`lib.rs:3553-3561`).

This audit establishes an explicit replacement event and a concrete unvisited-object interval, rather than inferring anything from a green test. It does not claim every indirect prefix, binary or String-choice caller has a proven independent owner. Nor does it claim a three-element failure has already been measured, or that no unexpected temporary can survive on a different compiled execution path. The exact unresolved observation is whether the third part is unreachable at the second part's allocation after the first return has replaced `EXIT_VALUE_ROOT` and the `==` clause's temporaries and registers have been released.

## Minimal next witness and controller decision

Extend only the returned array to `.array~of(.part~new, .part~new, .part~new)` and retain the same allocating `OBJECTNAME`. After the first return replaces the global, the second call's allocation occurs while its own receiver is rooted but the third part is still merely a handle in the join's Rust vector. With the truth push present, the array keeps that third part reachable; with only that push removed, the second collection is the proposed sole-owner boundary. Compare ordinary and stressed output `34.901 A\nA\nA\n`, then independently judge the exact dropped-push mutant and restore it, with the existing two-element survivor retained as a bounded control.

The controller should retain both production pushes and reject a redundant-root conclusion from the current survivor. The three-element proposal uses the existing execution path and stress collector, without a synthetic production allocation or a new root side map. If it still survives, the next diagnostic is a test-only reachability observation at the second allocation that identifies any remaining root to the array or third part, including live registers, rather than increasing allocations indiscriminately. No queued item is closed by this report, and the independent `condition_value` catch remains a separate judgement.
