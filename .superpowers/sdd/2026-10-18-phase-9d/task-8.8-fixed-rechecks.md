## Active executable identity defect

The queued original specifically installs a copied method with private and unguarded flags, starts it through a subclass, then redefines the installed name before first asking `.context~executable`. The reconstructed probe preserves that trigger and uses a protected BODY template, matching the original report's flag distinction. Replacing FOO with another Method, removing FOO with an omitted argument and replacing FOO with source text all produce `exe 1 0 1` here and `exe 0 1 1` on the oracle. Each pair has empty stderr and status 0, so the mismatch is a successful-program semantic difference rather than a refusal or harness error.

`flags-identity-prefetch-installed` shows that the copied template and installed FOO both have flags `0 1 1` before invocation on both sides. After active redefinition, the crate's first context query returns flags `1 0 1` and compares unequal to the previously held installed Method, while the oracle returns `0 1 1` and compares equal. Prefetching the installed Method therefore does not repair the crate's context answer. `flags-identity-ask-before` instead asks `.context~executable` inside the running body before redefinition, after which both sides retain flags `0 1 1`.

The local reference defines RexxContext executable as the current executable object for the current context (`oodocs/rexxref/en-US/utilityclasses.xml:7653-7671`). Class define replaces a receiver's method definition or makes its name unavailable when the method argument is omitted (`fundclasses.xml:320-350`), while the Method flag queries report that Method object's guarded/private/protected status (`:2259-2337`). The source and oracle evidence support preserving the running installed Method's identity and flags across later class redefinition. The minimal implementation direction is to retain that active executable identity through retirement or reconstruct it from the active invocation's installed Method, rather than selecting the template after the name's definition changes; this report neither implements a fix nor proposes a Deviation.

## FIFO boundaries

The original FIFO read source was reused in reduced form with FIFO creation and the bounded writer moved into the foreground Python driver. The writer has redirected stdin/stdout/stderr, waits briefly and writes exactly `abc`, so a command-owned pipe cannot masquerade as the FIFO read's EOF. Both reader programs return `[abc] READY` with status 0 and empty stderr. This directly rechecks the old queued empty-read/illegal-seek symptom.

The first FIFO write experiment launched a reader subprocess without proving it had opened the FIFO, and that oracle helper timed out without producing a payload record. Follow-up experiments establish an `O_RDONLY|O_NONBLOCK` reader descriptor before starting either interpreter, retain it until the child exits and then collect the exact buffered bytes. Writing `hello` followed by `STREAM CLOSE` agrees on both descriptors and `hello\n` payload. Writing followed by closing `LINEOUT` instead returns 0 with `hello\n` here and 1 with `ello\n` on the oracle, even with the reader established.

The queued item describes FIFO read/write failures caused by seeks and separately preserves interrupted-read error behavior. The successful explicit-close control proves ordinary FIFO data transfer without an illegal-seek error, but it cannot certify every closing LINEOUT behavior or dynamic EINTR delivery. Existing Deviation 46 concerns LINEOUT blank-record behavior and does not by itself establish a licence for this FIFO payload difference. The closing-LINEOUT observation therefore needs a separate scope decision rather than being hidden by the ordinary-transfer pass, while terminal coverage remains unproven because no existing PTY driver was found in the searched scripts and record directories.
