# Task 8.8 M6 timer ownership proof

## Judgement and scope

M6 has a reachable activity-attribution counterexample, suitable for the same category of judgement as M7, but this analysis executes no mutant or test. A due timer tick for outgoing A can survive A's real park and become incoming B's first recorded pinned deferral, although no tick occurred during B's dispatch. This contradicts the switch's explicit slice-attribution rule, without establishing a language outcome outside permitted scheduling cadence (`rust/crates/rexx-exec/src/scheduler.rs:1103`, `rust/crates/rexx-exec/src/timer.rs:27`). Keep the production clear and distinguish this source counterexample and proposed deterministic witness from an executed catch.

The historical universal seeded-unreachability argument also needs correction because it omitted the REPLY producer in `dispatch.rs:3625-3626`. The narrower statement about requests generated and consumed inside one `serve_requests` visit remains valid. A started replier can generate a request while completing and reach `switch_to` without another request visit, even with the timer disarmed. Accordingly this report does not endorse either universal seeded unreachability or complete timer-mode observational equivalence.

## Request word ownership

The physical request word belongs to an interpreter inbox, not to an `Activity` (`timer.rs:69-95`, `timer.rs:291-325`). `set`, `pending` and `clear` respectively use atomic release OR, acquire load and acquire-release AND, so independent producers can interleave without touching activity records (`timer.rs:73-84`). The timer registry identifies an interpreter and tracks its slice start, with no activity identifier or request generation number (`timer.rs:182-189`). A due tick coalesces into the one SLICE bit and advances the timer deadline even if the bit was already set (`timer.rs:226-235`). These facts make the cleanup an attribution boundary, rather than a transfer of a per-activity field.

There are three production SLICE setters: the due timer tick, the selected switch-mode decision and REPLY continuation spawning (`timer.rs:232`, `scheduler.rs:2331`, `dispatch.rs:3626`). The production clears are request consumption and `switch_to`, and neither resets the timer deadline (`scheduler.rs:1104`, `scheduler.rs:2343`). `arm` leaves an already armed deadline intact, while `disarm` removes the deadline without clearing request bits (`timer.rs:349-377`). Therefore switching does not promise a fresh 24 ms quantum for every activity, and a tick genuinely arriving after the clear can immediately affect B. An assertion that B must always run for 24 ms would reject baseline behavior and is not a valid M6 judge.

`switch_to` swaps activity and root records, changes the running handle, files or retires A, clears SLICE, resets the interpreter's deferred flag, and optionally disarms the timer (`scheduler.rs:1083-1114`). Its attribution guarantee must be stated at the clear's atomic position: absent a later producer, a request already present before this boundary is not consumed by B. A tick after the state swap but before the clear is also discarded by baseline, so the code does not implement exact activity ownership at every machine instruction. A tick after the clear but before disarm can remain pending in baseline because disarm does not clear it. The counterexample below deliberately puts its tick before the activity swap and has no later producer, avoiding both qualifications.

## Switch and request paths

Every `switch_to` call occurs inside `run_others_from`, whose first dispatch follows `next_runnable` (`scheduler.rs:1824-1832`). Later switches cover a parked or ended activity moving to the next runnable, restoration of the enclosing owner after a driver error, restoration after the owner's root ends, restoration after selection fails, and restoration when the loop has no other runnable (`scheduler.rs:1833-1865`). Selecting the current activity runs it again without a switch, and initially selecting the enclosing owner also returns without a switch (`scheduler.rs:1829-1830`, `scheduler.rs:1853-1857`). `next_runnable` drains completions, wakes sleepers, selects a ready handle, and may idle for posts or a sleeper, without consuming SLICE (`scheduler.rs:1888-1932`). Consequently a tick can survive selection, idle, completion or error processing and arrive at any actual switch boundary.

Normal yielding consumes a request before returning `Failure::Slice`, and the sliced driver queues the activity before the next dispatch (`scheduler.rs:2338-2351`, `scheduler.rs:2110-2115`). An independent tick after that consumption can nevertheless leave a new request pending before dispatch. A pinned wait first records its real park and then runs the nested scheduler, without a SLICE clear on that path (`scheduler.rs:1247-1255`). Completion similarly returns through `run_started`, `run_until_park` and the next dispatch, without requiring an intervening request visit (`scheduler.rs:2032-2056`, `scheduler.rs:602-612`). These are supported transitions, so reaching `switch_to` with a request is not an impossible hand-constructed scheduler state.

Request service can also enter guard waiting before sampling SLICE, and a pending REPLY split can return `Failure::Slice` before that sample (`scheduler.rs:2297-2308`). After inbox draining, sleeper processing and producer/arming work, a fresh request is cleared before the empty-ready, unpinned-yield, pinned-yield and first-deferral branches (`scheduler.rs:2313-2375`). The first pinned deferral records the current activity's pin stack, while an eligible second request can enter a nested pinned yield (`pinning.rs:132-150`, `scheduler.rs:2358-2373`). Thus retained SLICE changes activity-attributed counters even though the separate M7 deferred-flag reset remains intact. This is the downstream invariant used below.

Callback recall is a separate boundary that must not be silently included in the proof. `serve_recall` changes the running activity with `swap_running`, lends the baton, then restores the earlier activity with another `swap_running` (`scheduler.rs:1622-1657`). That helper deliberately omits the switch's other work, including both slice cleanup operations (`scheduler.rs:1670-1684`). A universal claim that every change of running identity clears or transfers all requests is therefore false of baseline as well. The counterexample uses an ordinary pinned wait and `switch_to`, with no callback, trace delivery or REPLY.

## Reachable timer counterexample

Use the existing three-activity comparator topology from `tests/concurrency_tests.rs:1067-1075`: main A enters a comparator that waits for started sort B, while C is also ready. A's pin key contains `TreeSend` plus `Native("SORTWITH")` and `SortComparator`, whereas B's directly started sort has the shorter sorting key (`tests/concurrency_tests.rs:1091-1097`). Give A's comparator a bounded ordinary numeric loop before its message-result wait, long enough to reach the normal cold countdown while B and C are ready. That visit arms the timer through the real timer-mode branch, with no switch mode installed (`clause.rs:289-317`, `scheduler.rs:2333-2336`). No synthetic activity record, pin depth or ready-queue entry is required.

The following finite event order is permitted by the production timer and scheduler. A pauses after its last request service, enough time elapses for the armed deadline to become due, and one tick sets SLICE before A's pinned wait dispatches B. A's message-result park is real, `next_runnable` selects B, C remains ready, and `switch_to(B, false)` runs before any further timer tick. B starts directly in native `SORTWITH`, enters its real Rexx comparator, and reaches a cold visit while still pinned, with no REPLY, callback or trace-delivery producer. A two-element sort with a comparator containing a bounded loop longer than the countdown supplies such a visit without relying on a test that mutates the countdown.

| Point | Baseline | M6, only the clear deleted |
| --- | --- | --- |
| Due tick while A still owns the dispatch | SLICE set, A parked or about to park, B selected, C ready | Same |
| Return from the A-to-B switch, no newer producer | SLICE clear, `slice_deferred == false` | SLICE set, `slice_deferred == false` |
| B's first pinned request visit with C ready | No request and no new deferral | Fresh request consumed and B records one deferral |
| Remaining B comparator visits without another tick | B sorting-key deferral delta stays zero | B sorting-key deferral delta stays one |

The exact observable is the delta of `deferred_slices` at B's sorting pin key, zero at baseline and one under M6 (`pinning.rs:382-388`). The pinned-yield delta remains zero in both variants because there is no second fresh request, and the next real switch resets the deferred flag. This directly checks ownership of the request that produced B's counter entry, rather than merely asserting that the deleted statement changed an internal bit. The ratified P29 rule explicitly distinguishes the first pinned deferral from a second request's pinned yield (`.superpowers/sdd/2026-10-01-phase-6-s2-s5/progress.md:49-51`). This establishes an activity-attribution counterexample, not an unlicensed stdout ordering, fairness failure or minimum-quantum violation.

## Smallest faithful deterministic experiment

The existing seams provide the real Rexx topology, pin-stack counters, timer arming inspection, ordinary scheduler transitions and the timer's due-time computation. They do not currently provide controlled interpreter timer ticks: the existing deterministic switch modes disarm the timer, while the Loom timer test exercises timer registration without the full interpreter (`scheduler/tests/native.rs:264-273`, `tests/loom.rs:119-135`). Setting SLICE on a fabricated activity state, or using `EveryOpportunity` as if it represented an independent timer, would not establish this reachability. A narrow test-only controlled-timer seam is therefore needed to make the proposed full-runtime witness deterministic. It should replace only this registration's asynchronous tick delivery and retain real arming, disarming, due checks and request publication.

One implementation is a `cfg(test)` per-registration controlled mode, a synchronous due-tick method, and a one-shot observer immediately before the A-to-B `switch_to` state swap. Share the existing per-entry due-check/update logic of `State::tick` with the synchronous method, rather than duplicating it or calling a global tick that advances unrelated test interpreters (`timer.rs:226-247`). The normal timer thread must skip only the controlled registration, while the test requests a tick at its recorded slice start plus `SLICE_LENGTH`; this models a legal elapsed interval without a wall-clock race. At the observer, assert actual timer-mode operation, the armed entry, A's real parked wait, valid idle B selected by the scheduler, C still ready, and no prior deferred request, then deliver the one due tick. Keep the registration controlled through B's first pinned visit so that no second producer can contaminate the ownership observation.

Run the adapted comparator program with no `SwitchMode`, ordinary countdown visits, tracing off, no REPLY and the `pinning` feature enabled. A and B each use a bounded loop, for example 4096 iterations, to guarantee a cold visit while their actual comparator frames exist, and B sorts two elements so that its comparator executes once. Assert that the transition observer and B's cold visit each fired, that exactly one controlled due tick was published, that B saw C ready, and that B's sorting-key deferral delta is zero with pinned-yield delta zero. Deleting only `scheduler.rs:1104` must change the deferral delta to one and fail that assertion, and the inverse edit must restore the baseline result. These are predicted results to measure, not results already observed here.

One companion placement should deliver the same controlled due tick after the switch clear, while B runs, and require one B deferral in both variants. That control proves the timer seam reaches request service and that the primary assertion distinguishes stale ownership rather than disabling all timer requests. Both cases can live in the scheduler test module, where private transition state is visible, reusing the existing comparator source and pin-key construction. Run only these named cases at baseline, the exact M6 mutation and restored source, with committed revisions, bounded foreground execution and an exact restoration check. A complete language-level equivalence proof remains unnecessary for an accepted attribution catch and is not claimed by this proposal.

## Correction to the seeded premise

`spawn_continuation` sets SLICE whenever another activity was already ready, independently of `self.switch`, and explicitly requests the sender's next clause boundary (`dispatch.rs:3572-3577`, `dispatch.rs:3620-3630`). A method ending immediately after `REPLY` still creates an empty continuation through `release_method_activation` and `empty_continuation` (`dispatch.rs:3547-3569`, `ir/drive.rs:3242-3271`). For a started root method, `finish_send` calls `finish_call`, which invokes that release, then normal outcome recording can return `Stopped::Ended` without another Rexx clause (`dispatch.rs:3268-3287`, `run/call.rs:1411-1417`, `scheduler.rs:2032-2053`). A plain successful Message with no notifier needs no Rexx execution during recording (`dispatch/object_protocol.rs:1175-1198`). The next `switch_to` can therefore clear a pending REPLY request in seeded mode too.

A concrete candidate prefix is main starting an unguarded method R whose complete body is `reply 1`, starting a second unguarded worker B, then waiting for R's result. Under FIFO simulation with no forced preemption reached, main's wait runs R while B remains ready, R spawns its empty continuation and sets SLICE, and completion readies main before dispatch to B. `sim:1,fifo,order=fifo` selects no ordinary policy preemption, although the configured fairness floor remains another request source within `serve_requests` (`sim.rs:1013-1048`). No test was executed to certify this candidate's exact clause trace, but the cited producer and completion path are sufficient to invalidate the old proof's claimed exhaustive list of setters. A narrow next check can observe that pre-switch pending bit on this real program if the controller wants separate seeded evidence.

The corrected induction is conditional: initially clear SLICE remains clear at switches when the independent timer is disarmed, every request is generated inside a completed `serve_requests` visit, and no intervening REPLY producer or pre-existing request exists. Within that restricted set, request generation is followed by consumption before any subsequent yield or deferral (`scheduler.rs:2319-2375`). It does not cover all ordinary seeded programs, because supported REPLY completion violates the producer premise. The historical accepted seeded disposition should therefore be narrowed or reopened, not silently copied into a broader closure. The timer-attribution experiment above avoids REPLY entirely and judges M6 independently of that correction.

## Preferred next experiment: Seeded REPLY attribution

The REPLY producer permits a smaller deterministic M6 judge using existing public simulation and pinning seams only. One reachable attribution catch suffices to judge the deletion, so implementing controlled timer delivery is unnecessary for that judgement. The timer construction above remains a source counterexample and an unexecuted optional experiment, not the recommended implementation scope. The following witness uses a terminal REPLY to publish the outgoing request and a directly started native sort to ensure that the incoming activity's first Rexx clause is already pinned. Its predicted counter values still require a baseline, exact-mutation and restoration run.

```rexx
r = .worker~new~start('replyValue')
b = .array~of(2, 1)~start('sortWith', .cmp~new)
c = .worker~new~start('other')
say r~result
say b~result~at(1) b~result~at(2)
say c~result
::class worker
::method replyValue unguarded
  reply 1
::method other unguarded
  return 7
::class cmp
::method compare unguarded
  return arg(1) - arg(2)
```

Use `Invocation::none().with_deadline(RUN_DEADLINE).with_switch_mode(SwitchMode::Sim(SimConfig::parse("sim:1,fifo,order=fifo,floor=1000000")?))` and enable the `pinning` feature. No artificial loop is needed because simulation requests a cold visit at every clause, and no timer delivery is enabled (`scheduler.rs:2281-2288`, `scheduler.rs:2319-2332`). FIFO policy produces no selected preemption, while the explicit high floor is checked by asserting the returned `SimReport.contended < 1000000`, which also bounds every individual activity's contended run below that floor (`sim.rs:1005-1019`, `sim.rs:1044-1048`). Explicit `order=fifo` preserves spawn order and the completion event order instead of using the default event shuffle. The deadline remains an external bound, not a source of requests or accepted timing variability.

Main's result wait first dispatches R while B and C remain ready. R's terminal REPLY creates an empty continuation E, sets SLICE because B was already ready, then completes its Message and readies main without running another Rexx clause (`dispatch.rs:3547-3569`, `dispatch.rs:3620-3630`, `scheduler.rs:2032-2053`). With no notifier, `notify_parties` returns without any send because no `MESSAGE_PARTIES` entry exists (`dispatch/object_protocol.rs:1638-1667`). The ready queue is consequently B, C, E, main when R-to-B dispatch begins, and the normal switch removes B while leaving C ready. Only the production clear differentiates the outgoing request at this transition.

B's first step is the native `SORTWITH` send itself, rather than a Rexx worker method that subsequently calls sort (`scheduler.rs:1944-1962`, `dispatch/object_protocol.rs:1390-1401`). `native_array_sort_with` calls `sort_by`, which enters `SortComparator` before sending the Rexx `COMPARE` method (`dispatch/array/sort.rs:343-350`, `dispatch/array/sort.rs:297-301`, `dispatch/array/sort.rs:60-66`). A two-element array executes exactly one comparison through the insertion-sort branch (`dispatch/array/sort.rs:123-144`). Therefore the first consuming Rexx visit is the comparator's single RETURN clause, with pin key `[Native("SORTWITH"), SortComparator]`, matching the already measured directly started comparator witness (`tests/concurrency_tests.rs:1067-1097`). Baseline sees no fresh request there, while M6 consumes the pending REPLY request and records one deferral.

Assert exit code zero, empty stderr and stdout `1\n1 2\n7\n`, plus the simulation report and floor bound. At the sorting key, treat a missing map entry as zero and require deferred slices zero and pinned yields zero. Also require total deferred slices zero and `pinning.unbalanced == 0` at baseline, so an unexpected pin key cannot hide the event. The predicted exact M6 result is sorting-key deferred slices one, pinned yields zero and unchanged stdout, because no second request is generated and the intact M7 reset clears the deferred flag at the next switch. These predictions derive from request flow and the one-comparison path, and are not asserted as observed results.
