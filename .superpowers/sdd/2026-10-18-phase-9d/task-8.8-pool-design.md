# Task 8.8 pool failure design

This report is a read-only source investigation of the e2 dispatch, P6 investigation, queued failed-spawn item, and their current production paths. It runs no build, interpreter, oracle, resource probe, or Git mutation. Its recommendations are proposals, and no acceptance item is marked complete. Test and fixture sources are being edited by another worker, so the cited test helpers describe the inspected versions rather than verified final fixtures.

## Contract and boundary

The pool must distinguish deliberate inline execution from failed thread creation. `scheduler/pool.rs:141` returns `None` for bound zero, test-only fixed saturation, and `Builder::spawn` failure through `.ok()?`, while production bound 64 limits retained threads rather than concurrency (`:24`, `:150`). The local reference raises `Error_System_service_service` with `ERROR CREATING THREAD` in `interpreter/platform/unix/SysActivity.cpp:79`, the catalogue assigns 48001 in `interpreter/messages/RexxErrorCodes.h:454`, and `oodocs/rexxref/en-US/errnums.xml:2767` specifies subcode 001 with a service substitution. Use a cold helper returning `Raised::syntax(48, 1, vec![b"ERROR CREATING THREAD".to_vec()]).into()`, matching the existing constructor and another 48.1 use in `error.rs:138` and `dispatch/stream.rs:38`.

The smallest pool change is `reserve(&self) -> std::io::Result<Option<Worker>>`. Preserve bound-zero and fixed-saturation decisions as `Ok(None)`, idle-worker reuse as `Ok(Some(worker))`, and propagate the actual spawn error before changing the thread vector or spawn counters. Only actual `Err` becomes 48.1, without substituting an errno-specific message or a scheduler refusal. All Rust paths below are relative to `rust/crates/rexx-exec/src` unless a full repository path is given.

The command process-group claim in the P6 report needs correction. `command.rs:770` applies `process_group(0)` only when `switch_mode` is present, and `sim.rs:1251` supplies that value only for simulation. Normal commands therefore cannot be killed as a private group by treating their PID as a group ID, and `Child` destruction does not kill or reap them. Reader and writer threads start only in `collect` (`command.rs:854`), which makes avoiding collection on reservation error essential.

## Native recommendation

Keep reservation at the driver-exit boundary, but move it ahead of `native_park.take()`, `record.leave`, the native-exit counter, and `in_flight += 1`. Add a failed-unstarted variant to the existing private `Stage`, carrying `Failure`, and on reservation error record it and `unpark(self.activities.running)` without lending the baton or posting a synthetic completion. In `resume_parked`, select the recorded spawn failure when no external wait failure supersedes it, then use the existing `resume_native_park(park, Some(failure))` route (`scheduler.rs:2142`, `dispatch.rs:3214`). This delivers the error through `DriveStart::Woken` and existing `then` processing for both the main root and started activities, rather than escaping the scheduler with a top-level `?` (`scheduler.rs:1992`, `:2211`).

Make `abandon_native_call` distinguish unstarted records from calls that actually left. For the unstarted case, use existing `pop_native_frame` and release the reserved guard using the same receiver/scope logic as today, while retaining existing `take_native_frame` plus `keep_abandoned` behavior for calls that left (`dispatch/library.rs:518`, `:854`). Merely dropping a native-frame box is insufficient, because `end_native_frame` explicitly releases kept values and lent buffers (`:892`). Do not enter or leave a new pin for failed-unstarted cancellation, since successful preparation already left its pin and only successful resumption enters one (`:439`, `:488`).

Suggested private interface details:

* `Stage::SpawnFailed(Failure)` and a predicate distinguishing Prepared/SpawnFailed from Left/Completed.
* A narrow extraction method may replace SpawnFailed with Prepared while moving its failure out, since `resume_parked` immediately performs cancellation and never returns to driver exit with that record.
* If an external failure already exists, preserve its current precedence and still recognize SpawnFailed as unstarted during cleanup.
* Preserve the original native park on failure, including receiver and continuation roots. Do not call the normal native completion function for a body that never ran.

This adds one cold outcome to an existing per-call state machine instead of changing all scheduler return types. In particular, `Posted::Completed` decrements `in_flight` unconditionally, so manufacturing one for a call that never incremented it is incorrect (`scheduler.rs:1515`). Moving reservation into native preparation would require storing an unused worker across later unwinding and defining its cancellation, because Worker currently has no return-on-drop behavior. The existing parked continuation is therefore the narrower native boundary.

## Command alternatives and recommendation

Prefer reserving immediately before the OS spawn, after command parsing and pipe setup have succeeded. Only the non-resuming path should reserve, and `Child::Running` can carry the resulting worker in the command-specific guard described below to the already-existing `exit_for_block` dispatch (`command.rs:732`, `:810`, `:982`). Pass the populated guard to `exit_for_block` and make it return its token directly, while no reserved worker continues through `collect_on_baton` exactly as the configured inline policy does today. This removes the spawned-child cleanup obligation from actual pool reservation failure without changing successful commands' process groups or introducing a generic reservation framework.

An unused reserved worker must be dispatched when the later `builder.spawn()` fails or its owner unwinds. Use a command-specific guard containing `Option<Worker>`, carried by `Child::Running` and consumed only by its final `run(job)` operation, whose Drop dispatches `worker.run(Box::new(|| {}))` when a worker remains. This reuses the existing work loop to return the worker idle or end excess threads, and it covers the existing spawn-to-RC127 branch without a generic reservation framework (`scheduler/pool.rs:216`, `:256`). Repeated invalid executables may transiently create extra workers before no-op jobs return, so a focused reuse test must wait for return and verify bounded settled thread count rather than asserting synchronous reuse.

The entire interval from reservation to dispatch currently contains no interpreter suspension or callback. `IoContext::begin` and output-sink callbacks happen before `start`, input buffering and all pipe setup precede the proposed reservation, and subsequent redirection predicates are plain field comparisons (`command.rs:971`, `:781`, `:995`, `redirect.rs:181`, `:199`). Between reservation and dispatch, the remaining operations are OS spawn, builder/merged-writer drops, Child and Block construction, and scheduler job construction, so retain the guard through that final construction instead of extracting a bare Worker before it. On successful dispatch the guard must be disarmed before returning, on any early return or unwind it sends only the no-op, and neither branch depends on callback code to release the worker.

Pool destruction does not provide a fallback for a forgotten reservation. `Pool::drop` sends End and joins only workers listed as idle, while handles for remaining threads are detached (`scheduler/pool.rs:183`). A reserved worker dropped without mail can therefore leave its thread waiting indefinitely with the shared state and mailbox retained, rather than necessarily blocking Pool destruction. Add a guard-drop test before dispatch and a spawn-error test, and observe return or thread exit without treating a cleared Pool handle vector as proof that the thread ended.

This ordering preserves invalid PATH parsing, pipe setup failures, registered handlers, internal commands, redirection initialization, and the resuming inline path. It changes precedence when both thread creation and child execution would fail, because 48.1 now occurs before the old RC127 result can be observed. A successful reservation can also precede an OS child-spawn failure, which is why the no-op release path is mandatory. Those are explicit costs, but they are narrower than changing process-group behavior for every successful ordinary command.

If the controller requires retaining the current post-spawn reservation boundary, implement an explicit failure-only `Block::abort` and private process-group ownership for commands entering that boundary. On actual reservation failure, close the owned input/output/merged handles without starting readers, kill only the known private group, kill/reap the direct child using its owned `Child`, and adopt the regular-file stdin offset before raising 48.1. Reuse the `kill_process_group` mechanism from `collect_on_baton`, but not its asynchronous collector, timeout refusal, or assumption that normal children already have a group (`command.rs:1015`). Never place this cancellation in a general successful-command destructor, because `read_all` intentionally allows background descendants to survive their parent command (`command.rs:544`).

The post-spawn alternative has material behavior and ownership costs. Creating private groups changes ordinary child process-group/job-control and signal behavior, while killing only the direct shell can leave grandchildren running or retaining inherited pipe descriptors. A group kill cannot catch a descendant that deliberately leaves that group, so it is not a general process-tree ownership guarantee, and direct-child `wait` does not reap arbitrary grandchildren. Consequently reserve-before-spawn is the recommendation unless the controller explicitly selects the larger ownership change or requires the old simultaneous-failure precedence.

Redirection cleanup is distinct from OS-child cleanup and must not be invented from destructors. `IoContext::begin` may already have changed targets, `exec_command` pops its temporary root frame on either result, and `IoContext::finish` deliberately skips named-stream cleanup when propagating a held failure (`redirect.rs:224`, `:290`, `command.rs:1259`). The new spawn failure should use the existing error boundary without pretending a successful command completed or blindly invoking `finish` with empty output. An oracle requirement to close these named streams specifically on thread failure remains unestablished by this investigation and should not be bundled into the pool repair.

## Stdin recommendation

Propagate `Result<bool, Failure>` from `fill_stdin_keeping` and `fill_stdin`, `Result<Option<Vec<u8>>, Failure>` from `input_line`, and `Result<Vec<u8>, Failure>` from `input_bytes`. On reserve error reset only the just-set `stdin.reading` flag and return 48.1, leaving buffered bytes, EOF, exhaustion, and descriptor ownership unchanged. Do not call `receive(Vec::new())`, which marks EOF, or `interrupted()`, which changes the exhausted state (`input.rs:335`, `:347`, `:359`). Reads already in flight must retain their marker and proceed through the existing wait because `start_stdin_read` returns false for them.

Always requeue `kept` before propagating the result from `fill_stdin`, so an early `?` cannot discard other activities' posts (`input.rs:643`). Mark `reading_stdin` only for `Ok(true)`, preserve `Ok(false)` as the HALT path, and add `?` at the nil-route fallback in `linein_line`, stream CHARIN, and shared `next_line` (`input.rs:598`, `dispatch/stream.rs:1276`, `:1493`). Those existing stream functions already return Failure and therefore reach their ordinary caller's SYNTAX trap without manufacturing NOTREADY or changing stream status to EOF. A successful or deliberate-inline read continues to be the only operation that obtains `std::io::stdin().lock()` (`input.rs:80`).

## Deterministic proof plan

The existing `1 << 46` pool stack is a real spawn seam, not proof that every host rejects the allocation. First assert that reservation returns an actual error and does not increment thread counters, and if a worker unexpectedly starts, dispatch an empty job and report the seam as ineffective instead of leaking it or escalating resource pressure. For deterministic Linux execution, isolate a single test subprocess and apply a bounded address-space limit comfortably above its existing interpreter footprint and below 64 TiB before requesting that stack. This limits the one request rather than exhausting host threads or address space, and a memory cgroup alone does not guarantee rejection of a large virtual stack mapping.

The recommended pre-spawn design cannot honestly claim an actual child was killed by reservation-error cleanup, because no child exists at that boundary. Its replacement proof is actual non-creation plus release of a worker reserved for an OS spawn that fails, while the table specifies actual child cleanup proof if the controller selects the post-spawn alternative. Record that distinction explicitly rather than labeling a missing marker as proof of killing a child. Existing background-child tests under `tests/suite/process_ownership` and the `command.rs:544` behavior provide preservation targets, but an oracle-only deadline test is not by itself runtime evidence.

Stdin tests need an isolated process because `std::io::stdin` is process-global and its lock/buffer must not be replaced in a parallel Rust test process. The test-only stack setter is compiled only into unit-test code, so running the ordinary CLI does not inherit that seam (`lib.rs:296`), and `run_shaped` currently constructs `Invocation::none()` rather than stdin input. Reuse the unit-test binary as the bounded child or add a narrow input option to the existing helper, without a production environment variable or broad injection framework. A permanent huge-stack setting cannot prove a later pooled spawn succeeds in the same interpreter, so separately exercise recovery on an inspectable interpreter whose pool can be replaced after failure, or state that repeated-trap progress is the integration proof rather than claiming a one-shot failure.

## Performance and cancellation limits

The release reservation hot path keeps the same mutex acquisition and idle-pop operations, with one explicit Result match and no new map, dependency, unsafe code, or normal-path error allocation. Native failure delivery adds a private stage variant and one extraction check on parked resumption, so enum layout and parked-call benchmark effects should be measured rather than assumed free. Stdin adds Result propagation on the live input boundary without changing buffered/file reads, and the preferred command ordering avoids new process-group work on successful commands. Keep error construction cold and retain the controller's own-BASE performance obligation instead of proposing unrelated scheduler refactoring.

The cancellation proof must distinguish a prepared call from a native body that can still access its descriptors and handles. Only the former may immediately run `end_native_frame`, while the latter must retain the existing abandoned frame until its completion and preserve pending conditions, callback roots, and guard release rules. Command reader helper threads use other spawn APIs inside `collect`, and this repair does not establish their behavior under independent allocation failure. Those remaining boundaries, platform reliability of the huge-stack seam, and the controller's command-ordering choice remain explicit limits of this source-only report.
