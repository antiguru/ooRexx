## Common switch and cancellation boundaries

`switch_to` swaps the whole `Activity` and its `ActivityRoots`, while the SLICE bit and `slice_deferred` remain on the interpreter (`scheduler.rs:1069-1091`). Its callers are the scheduler loop's initial dispatch, activity transitions and return to the enclosing owner, including failure returns (`scheduler.rs:1811-1845`). `swap_running` deliberately performs only the state exchange for callback recall, without the switch cleanup, and is a separate boundary from these mutants (`scheduler.rs:1624-1669`). Thus M6 and M7 concern the interval from an actual scheduler switch until the incoming activity's next request processing, rather than a copied field inside a continuation.

`cancel_wait` runs after `wait_until_woken` fails, after an injected or naturally failed `pinned_wait`, and at entry to main's termination drain (`scheduler.rs:1212-1253`, `scheduler.rs:1740-1743`). A natural failure can be an unsatisfiable or inverted wait, an error from another activity, or the stack-bound 11.1 error from `run_round` (`scheduler.rs:1243-1252`, `scheduler.rs:1786-1792`). The seeded `fail=wait:K` counts pinned waits specifically, parks first, then cancels immediately and returns trappable 11.1 (`rust/crates/rexx-exec/src/sim.rs:1181-1187`, `scheduler.rs:1233-1239`). Consequently cancellation does not imply termination, and the existing SYNTAX handlers provide a real continuation interval in which stale state matters.

## M6: Incoming pending request

In seeded mode, deleting the clear in `switch_to` has a bounded reachability argument rather than a seed to expose it. The only production setters of SLICE are the timer tick and `serve_requests`' switch-mode decision, and setting a switch mode disarms the timer (`rust/crates/rexx-exec/src/timer.rs:226-234`, `scheduler.rs:2262-2268`, `scheduler.rs:2299-2323`). Within `serve_requests`, a generated fresh request is cleared before any subsequent branch can yield, defer it or return; an early guard-wait return occurs before generating this visit's request (`scheduler.rs:2277-2280`, `scheduler.rs:2318-2356`). Starting from an interpreter whose request is clear and using ordinary seeded execution, induction over these setters leaves no pending SLICE for a later `switch_to` to clear, so seeded switch counts, trace hashes and output cannot distinguish M6.

Timer mode permits an independent tick between visits, so the corresponding global equivalence claim needs a narrower formulation. A leftover request can make an incoming unpinned activity yield at its next yielding visit, or set its first deferral while pinned; it can also serve as a second request if another deferral exists, although the separately intact M7 cleanup clears that incoming deferral at the switch (`scheduler.rs:1091`, `scheduler.rs:2325-2353`). The historical argument is that such incoming request timing is also producible by an ordinary timer tick, but it does not prove identity of timer deadlines or complete traces (`../2026-10-07-phase-6-1/task-11-report.md:106-112`, `timer.rs:349-375`). The current `SimReport` exposes steps, contended steps, switches and a decision hash, not request ownership, while the timer-disabled seeded test confirms why these instruments cannot establish a timer-mode catch (`sim.rs:163-177`, `rust/crates/rexx-exec/src/scheduler/tests/native.rs:264-274`).

The minimal additional witness would be a scheduler unit fixture that models a timer tick by setting SLICE immediately before a real `switch_to`, keeps another activity ready, and observes the incoming request before its next fresh producer runs. That fixture can assert that the switch cleared the outgoing request, then call request processing at a non-yielding pinned visit to distinguish a stale deferral from no request. This would be an ownership/instrumentation catch, not a language-level outcome outside an allowed cadence, and must be labeled accordingly. Without that instrument, the defensible controller choice is only seeded unreachability plus an unresolved timer-mode observational-equivalence argument, not a corpus-derived safe verdict.

## M7: Incoming deferred state

M7 is reachable when outgoing A defers a request at a pinned comparator clause and then parks before consuming it, allowing B to run while C is also ready. The stored boolean survives the activity/root swap under the mutation, so B's next fresh pinned request takes the second-request `pinned_yield` branch instead of its normal first-request deferral (`scheduler.rs:1074-1091`, `scheduler.rs:2338-2353`). A pinned yield runs other activities on the pinned caller's stack, so the consequence includes different per-pin yield accounting and scheduling opportunities for C (`scheduler.rs:2456-2469`). Resetting at a later B visit does not undo the first wrongly attributed yield or restore the deferral count.

The existing `measured::a_slice_deferred_before_a_pinned_park_stays_with_its_activity` already implements this exact A/B/C shape, with a one-clause B comparator that gives an odd count of pinned visits (`rust/crates/rexx-exec/tests/concurrency_tests.rs:1058-1075`). Under `EveryOpportunity` it asserts main's comparator deferral count 1, B's comparator deferral count 2 and B's pinned yield count 1, alongside exact output (`concurrency_tests.rs:1076-1097`). Phase 6.1 records the mutation changing B's deferrals to 1 and yields to 2, and explains why an even-visit comparator previously hid the error in the totals (`../2026-10-07-phase-6-1/task-11-report.md:61-73`, `:91`). Reusing that test is the minimal faithful instrument witness, with a seeded `sim:1,uniform:1` run of the same program as an additional candidate whose counts and reach must be measured rather than copied from the EveryOpportunity run.

## M9: Cancelled WHEN park

M9's stale boolean originates in `park(GuardWhen)`, not in a generic failed wait (`scheduler.rs:614-623`). `STALE_WHEN` reaches an exposed false flag through `INTERPRET`, traps the pinned wait's injected 11.1, returns from that routine, and then waits on a different started method's result (`rust/crates/rexx-exec/src/scheduler/tests/mutants.rs:101-112`). Before cancellation, `note_cancelled_wait` counts `when_parked` directly, and the test requires exactly one WHEN cancellation (`scheduler.rs:1284-1288`, `scheduler/tests/mutants.rs:130-141`). The guard execution's watch cleanup is separate, so a subsequent variable store is not an adequate assumed wake source after abandonment (`rust/crates/rexx-exec/src/guards.rs:727-748`).

The faithful consumer is `halt@K`: `wake_for_halt` takes a stale `when_parked` and unparks main even though main now waits for a message result (`scheduler.rs:2596-2617`). The existing test already runs `sim:2,pre:2,k=40,fail=wait:1,halt@20` and `sim:3,uniform:0.3,fail=wait:1,halt@20` before the uniform-1 cases, and expects `caught 11.1`, `result slow halted`, then `main halted` (`scheduler/tests/mutants.rs:114-147`). Historical mutation evidence reports `result The NIL object` through those halt paths, while uniform-1 can fail the ready-with-park-reason invariant without a halt (`../2026-10-07-phase-6-1/task-11-report.md:92`, `scheduler.rs:1164-1165`). Reuse both halt-dependent seeds and the no-halt twin to distinguish the behavioral route from the independent invariant catch, retaining the category count rather than treating any 11.1 as WHEN provenance.

## M10: Cancelled guard queue entry

For M10 the relevant state is a guard table entry plus the activity's actual place in a lock's FIFO queue. `serve_guard_wait` enqueues a contended reservation before invoking the pinned wait, and `Guards::enqueue` both pushes the activity into the lock queue and records `Waiting::Guard(key)` (`guards.rs:493-516`, `guards.rs:120-125`). The cancellation counter calls `Guards::queues`, which reads that waiting map rather than scanning the queue, so the enqueue path and immediate `fail=wait:1` cancellation together establish the queue provenance (`guards.rs:238-257`, `scheduler.rs:1233-1239`). Deleting only table withdrawal preserves both stale structures even though the separate activity `guard_waits` cleanup remains intact (`scheduler.rs:1263-1266`).

`STALE_GUARD_WAITER` starts a holder that sleeps with its lock, enters a pinned interpreted `touch`, traps its failed acquisition, waits for the holder, and starts a later `touch` from a third activity (`scheduler/tests/mutants.rs:150-160`). Releasing the holder's final lock count transfers ownership to the first queued waiter, rather than testing whether that wait is still live, so the mutant can grant it to the already-cancelled main and obstruct the later send (`guards.rs:128-148`). The existing test requires one cancelled guard wait and exact output `caught 11.1`, `held`, `later touched` under fifo, uniform-1 and preemption seeds (`scheduler/tests/mutants.rs:162-177`). Reuse those seeds independently of M9, and if tighter provenance is wanted, inspect the actual queued activity/key at cancellation without changing the runtime queue behavior or substituting a generic wait counter.

## M11: Cancelled sleeper

M11's state originates in `park(Sleep)`, which inserts a deadline/order/activity tuple and sets the activity's sleep order (`scheduler.rs:629-634`). The existing `STALE_SLEEPER` test imports `tests/sim_gate/m11_stale_sleeper.rex`, whose interpreted one-second sleep is the first pinned wait and whose handler continues to a different started method's result (`scheduler/tests/mutants.rs:79-97`). `note_cancelled_wait` searches the sleeper heap for the running activity, and the test requires exactly one sleep cancellation, establishing the category without depending on elapsed output alone (`scheduler.rs:1289-1292`, `scheduler/tests/mutants.rs:92-97`). Ordinary successful sleep completion clears `asleep`, but the final heap removal in `cancel_wait` is the independent protection against the old deadline (`rust/crates/rexx-exec/src/builtin/rexxutil.rs:272-285`, `scheduler.rs:1276-1278`).

With that removal deleted, the one-second deadline remains after main has trapped the failure and parked on the slow method's three-second result. `wake_due_sleepers` pops due tuples and readies their activity without checking that the current park matches the old sleep, while `make_ready` only deduplicates ready entries (`scheduler.rs:1677-1687`, `scheduler.rs:414-421`). The existing library witness checks both `result slow done after 1` and the sleep count under `sim:1,order=fifo,fail=wait:1`, `sim:1,uniform:1,fail=wait:1` and `sim:2,uniform:1,fail=wait:1`, while the imported gate fixture explicitly judges scheduler invariants rather than stdout (`scheduler/tests/mutants.rs:82-97`, `tests/sim_gate/m11_stale_sleeper.rex:1-4`). Keep that existing negative control and its category-specific assertion, without treating the gate's invariant catch as proof of the separate output assertion.

## M12: Failed-message rooting interval

M12 has a genuine possible sole-root interval, and the outcome map does not close it. A spawned send installs `root_then = Started(message)` and `Activity::object_roots` traces it while the send runs (`rust/crates/rexx-exec/src/dispatch/object_protocol.rs:1390-1401`, `activity.rs:756-757`). When the send ends, `run_started` takes `root_then`, invokes `apply_then`, and the Raised branch of `record_started` appends the message to `failed_sends` before storing its outcome and removing its message waiter identity (`scheduler.rs:2014-2041`, `rust/crates/rexx-exec/src/dispatch.rs:3350-3359`, `dispatch/object_protocol.rs:1180-1198`). In that failure branch, the handoff from the removed root to `failed_sends` performs no Rexx heap allocation, but the later settlement does.

`message_outcomes`, `started_messages` and `unnotified_messages` are explicitly omitted from interpreter root enumeration and are pruned using heap liveness after collection (`rust/crates/rexx-exec/src/lib.rs:3410-3412`, `lib.rs:3663-3669`). Scheduler object roots enumerate idle activities, abandoned frames and timer-held values, rather than making the message identity table a root (`scheduler.rs:451-470`). `first` has already been taken and its transient send roots popped before completion, and the send roots concern its receiver/scope/arguments rather than the Message outcome owner (`scheduler.rs:1930-1946`, `dispatch/object_protocol.rs:1162-1168`). A dropped fire-and-forget Message with no notifier, argument back-reference or surviving caller temporary therefore has no replacement owner in these containers after `root_then.take()`.

The complete current insertion sites are `record_started`, the SYNTAX branch of `record_held`, and the two started-notifier failure paths (`dispatch/object_protocol.rs:1187`, `dispatch/object_protocol.rs:1300`, `scheduler.rs:2033`, `scheduler.rs:2070`). Settlement is called for started completion or notifier replacement, notify-slot failure, main's untrapped non-nested failure, and a failure held for a native frame (`scheduler.rs:2056`, `scheduler.rs:2073`, `dispatch/object_protocol.rs:1586`, `lib.rs:3023`, `rust/crates/rexx-exec/src/dispatch/library.rs:1940-1950`). A taken trap also attaches its built or reraised condition directly, consuming the same pending failed-send vector (`rust/crates/rexx-exec/src/run/condition.rs:717-729`). These routes can have different extra owners, and a full redundant-root argument would have to prove coverage for every one rather than extrapolate from one retained-message caller.

The decisive allocation interval begins at `end_failed_started` calling `settle_failed_sends` and ends at condition attachment (`scheduler.rs:2051-2056`, `rust/crates/rexx-exec/src/condition.rs:199-234`). Settlement's pushed root frame does not push the failed messages, and condition construction starts by building two List objects before the rest of the condition entries (`condition.rs:203-218`, `condition.rs:444-460`, `condition.rs:639-656`). Those constructors ultimately allocate through `alloc_with`, whose collection decision precedes allocation, and collection obtains activity roots through the current root enumeration (`lib.rs:3219-3237`, `lib.rs:3508-3509`, `lib.rs:3546-3561`). Thus removing the failed-message enumeration can sweep the dropped message during the very construction intended to attach its condition, even though the raised failure remains available as a Rust value.

Attachment takes `failed_sends` and calls `set_native_entry(message, MESSAGE_CONDITION, object)` for each handle, after which this vector no longer owns it (`condition.rs:231-234`). A plain Native Message's attachment performs no heap allocation, so clearing the vector at this point does not create the earlier construction gap for that object kind (`rust/crates/rexx-exec/src/environment.rs:1447-1458`). `notify_failed_send` roots the message afterward, but that happens after initial settlement, and cannot resurrect a message swept during it (`scheduler.rs:2056-2061`, `condition.rs:243-257`). Held sends, notifiers and Message subclasses have additional roots or allocation paths, so this argument is deliberately for the plain dropped send rather than a universal claim about every `failed_sends` member (`dispatch/object_protocol.rs:1274-1305`, `dispatch/object_protocol.rs:1638-1665`, `environment.rs:1462-1469`).

The existing `a_dropped_failed_send_is_written_while_alive` already uses that plain program shape, seeds 1 through 3, and `gc=1` or `gc=0.1` (`scheduler/tests/mutants.rs:181-207`). It compares total native writes with a successful twin and requires no writes to dead handles, using `heap.peek` at the write site, while Phase 6.1 recorded an M12 dead write under this witness (`environment.rs:1448-1452`, `../2026-10-07-phase-6-1/task-11-report.md:95`). These are meaningful liveness checks, but this test neither reads the attached condition at that site nor records that a collection and slot reuse occurred in the exact settlement interval. Heap generations reject an old handle even when its physical slot is reused, so silent lost attachment remains possible without corrupting the replacement object (`rust/crates/rexx-core/src/heap.rs:408-423`, `heap.rs:583-601`, `heap.rs:622-630`). This read-only analysis has not established the absence of every residual temporary or transitive object-graph reference in that current program run, so exact sole-root reach remains a specific measurement obligation rather than a claimed observed fact.

The minimal faithful extension is a test-only observer around the existing dropped-send settlement, retaining only handle identities and measurements rather than adding roots. Record the message identity at settlement entry, collection count there and at attachment, then assert at the attachment site that the same handle is live and its `MESSAGE_CONDITION` equals the constructed condition with SYNTAX code 42.3. For the mutant, record physical-slot reuse with a different generation during condition allocation, preserving the old handle's failure to resolve and ensuring any replacement object remains unmodified; run `sim:1,gc=1` first and bound any further seed search explicitly. If that seed does not reuse the slot, report the missing reuse evidence rather than count a dead write or successful process exit as the full requested witness.
