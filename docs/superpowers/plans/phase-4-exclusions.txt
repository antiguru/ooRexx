Phase 4 exclusions and deviations
=================================

Two sections, and the distinction between them is the whole point of the file.

  An EXCLUSION is work assigned to a later phase. It will exist one day, and a
  row names the phase that owes it.

  A DEVIATION is a permanent difference chosen on purpose. Nobody is coming
  back for it.

A deviation is therefore strictly worse than an exclusion, and the gate asserts
the SET of both sections rather than a count. Adding a row to either is a plan
amendment, not a file edit -- otherwise the file is an artifact of the phase
being gated, and anything that turns out hard can be excluded by editing it.

Phase 7 and Phase 10 delete their own exclusion rows as they deliver them. The
deviations section shrinks only if a decision is reversed, which is a plan
amendment too.

The gate reads "66 of the 81 builtins in builtinTable[] (BuiltinFunctions.cpp
:3042) are in scope, three of them partially, and the excluded set is exactly
this file".


EXCLUSIONS -- builtins, whole
-----------------------------

Each fails loudly meanwhile: the not-implemented exit code, NOT_IMPLEMENTED_EXIT
in rexx-exec, plus a message naming the construct and the phase that owes it.
Never a plausible Rexx condition, because a program expecting that condition
would otherwise pass against a gap.

The constant is named rather than its value written out here. What matters to
the argument is the band: the code must sit outside 157..253, where 256 - major
lives, or a not-implemented failure is indistinguishable from a raised
condition, which is the worse failure. The specific integer is Task 12's to
confirm, and this file is a gate artifact that nothing recompiles -- writing the
number here is how it goes stale silently while still reading as true.

Each row says WHY it is blocked, not only who owes it (D4). "The platform
layer" names a phase; it does not tell Phase 7 what it is walking into, and
for three of these rows what it is walking into is a decision rather than a
task. Every measurement below was taken on this host from a fresh empty
directory, with the oracle under the standard ulimit.

  Phase 7, the stream model and the platform layer:

    CHARIN      Reads characters from a stream.
    CHAROUT     Writes characters to a stream.
    CHARS       Reports the characters available on a stream.
    LINEIN      Reads a line from a stream.
    LINEOUT     Writes a line to a stream.
    LINES       Reports the lines available on a stream.
    STREAM      Opens, closes, queries and repositions a stream.

                All seven are blocked on the same absence and there is no
                argument about any of them: Phase 4 has no stream model, and
                none of these means anything without one. Measured,
                stream('nosuch.txt','C','QUERY EXISTS') returns empty.

    QUALIFY     Resolves a name against the current directory. NOT ACTUALLY
                BLOCKED, and this row exists to say so: measured,
                qualify('foo.txt') returns an absolute path for a file that
                does not exist, so it is pure path manipulation and
                std::path with std::env::current_dir covers it. It is
                excluded because it is unscheduled, not because it cannot be
                written. D4 weighed moving it into 4c (which would read 67 of
                81) and chose not to; what would force the move is an L1
                base/bif group 4c must pass turning out to need it.

    USERID      Returns the invoking user's name; measured, "moritz" here.
                Blocked, but weakly: Rust's std has no username API, so a
                faithful answer needs getpwuid through libc -- which is
                unsafe, and this workspace sets unsafe_code = "forbid" -- or
                an external crate. Its value is also host-dependent, so a
                differential run of it is single-machine, the same caveat the
                QUEUED row below carries.

    SETLOCAL    Saves the process environment; ENDLOCAL restores the most
    ENDLOCAL    recently saved one. Measured, `s = setlocal(); say s
                endlocal()` prints "1 1" -- and an unpaired `say endlocal()`
                prints 0, so the pair, not the call, is what returns 1.
                Blocked, and harder than "the platform layer" implies:
                restoring an environment means std::env::set_var, which is
                unsafe in edition 2024. Verified by compiling it under this
                toolchain (rustc 1.97.1): error[E0133], "call to unsafe
                function `set_var` is unsafe and requires unsafe block".
                Against unsafe_code = "forbid", Phase 7 needs either a shadow
                environment or a lint exception, and that is a decision, not
                a task. Written down here so Phase 7 does not meet it cold.

  Phase 10, the RXAPI daemon:

    RXQUEUE     Creates, deletes and selects external data queues.
    RXFUNCADD   Registers an external function by name.
    RXFUNCDROP  Deregisters one.
    RXFUNCQUERY Reports whether one is registered.

                All four are blocked on the rxapi daemon protocol, which
                nothing in Phase 4 speaks. Measured, rxqueue('G') returns
                SESSION -- an answer that comes from a live rxapi, which is
                also why the QUEUED row's single-program caveat below is real
                rather than theoretical.

Fifteen names. 81 - 15 = 66 in scope.


EXCLUSIONS -- partial
---------------------

Three builtins are in scope in one form and excluded in another. Excluding the
whole name would overstate the gap; ignoring the split would understate it.

  VALUE      The variable-access form is 4c's. The external-selector form,
             which reads a pool such as ENVIRONMENT, is Phase 7's: it needs
             process environment access, which is the platform layer.

  ADDRESS()  Reporting an environment set by an ADDRESS instruction is 4c's,
             and so, SINCE 4c TASK 10, is the platform-supplied default this
             row used to assign to Phase 7 -- measured, "say address()" with
             no ADDRESS instruction prints "sh".

             WHY THE ROW MOVED. The reason given for deferring it was that
             the default "comes from the layer D18 defers", and that
             conflates naming the default environment with issuing a command
             to it. The name is SYSINITIALADDRESS, a #define in
             platform/<os>/PlatformDefinitions.h -- "sh" at the unix file's
             line 66 and "CMD" at the windows file's line 65 -- reached
             through GlobalNames.h:124 and returned by an identical
             getDefaultAddressName() on both platforms. It is fixed when the
             interpreter is built, and nothing about reading it needs the
             command layer.
             Deferring it also made the corpus witness this row's own
             enumeration says ADDRESS() is owed impossible to write, because
             a callee's inherited alternate is the default in the simplest
             shape.

             So it is spelled as a #[cfg]-selected constant in
             builtin/state.rs, and it is in the corpus -- for the reason
             PARSE SOURCE's "LINUX COMMAND" is and PARSE VERSION's build date
             is not: it is a compile-time constant of the interpreter rather
             than a value that moves under a rebuild. What stays Phase 7's is
             unchanged: issuing a command to that environment.

  QUEUED     In scope against 4b's in-process queue. Cross-process sharing with
             the oracle's rxapi-backed session queue will never match, so a
             differential run of QUEUED is single-program only. This row is a
             caveat on a delivered builtin rather than undelivered work.


EXCLUSIONS -- trace prefixes, with an owner
-------------------------------------------

The oracle has nineteen trace prefixes (RexxActivation.cpp:3567-3587). Thirteen
have a committed witness at the end of 4b and six do not; all nineteen are
enumerated with their owner in rexx-exec/tests/trace_oracle.rs's own
PREFIX_COVERAGE, which is asserted rather than described (that file's coverage
test is what fails if this paragraph and the table drift apart). Three of the
six -- >.> (4c), >M> and >N> (Phase 5) -- follow directly from the construct
that emits them being that phase's. The other three need a row of their own,
because their answer was got wrong before it was measured.

  +++         Phase 7, not 4c.

              A +++-prefixed line has five producers in the C++:
              RexxActivation.cpp:4468, a command's non-zero RC, measured
              live as

                       1 *-* 'exit 3'
                         >>>   "exit 3"
                         +++   "RC(3)"

              from `trace e` followed by `address sh` and 'exit 3' -- and
              the trace setting is load-bearing, since the same program
              under `trace n` emits nothing at all; :4024
              (traceSourceString, whose caller is guarded by inDebug() at
              :4305), the first banner line; :4237, the debug prompt, the
              second, whose message text begins "+++"; and Activity.cpp
              :1496 and :1507, whose message text likewise begins "+++".
              Those last two are ONE function, displayDebug, and they are
              counted separately because each fetches the message and makes
              its own displayUsingTraceOutput call -- :1496 for the primary
              message and :1507 for the secondary, guarded on the exception
              object carrying one. Counting displayDebug once gives four
              and is the answer to a different question: how many functions
              emit the prefix, rather than how many sites do.

              Four are interactive debug and one is command dispatch, both
              Phase 7's under D18 and under the TRACE ? row below.

              THE REASON IS THAT SPLIT RATHER THAN THE ABSENCE OF ANY PATH,
              and this is what the earlier "4c" answer missed.
              AddressInstruction.cpp:163 IS a 4c instruction, and it is one
              of RexxActivation::command's two callers (the other is
              CommandInstruction.cpp:89). So 4c does reach the function
              that emits the RC line -- it is ADDRESS's own 4c/Phase 7
              division, the instruction being 4c's and issuing the command
              being Phase 7's, that keeps the prefix out of 4c's reach. An
              owner argued from "no path exists" would have been wrong; the
              argument has to be about which half of ADDRESS lands when.

  >I> / <I<   DELIVERED by 4c Task 13, alongside ::routine dispatch itself.
              The row is kept rather than deleted because its argument is
              about how an owner was got wrong and then right, which a
              deletion would lose; the paragraph at the end of the row says
              what shipped and what did not.

              BY DECISION, NOT BY UNREACHABILITY, and the distinction is the
              whole reason this row exists. 4b Task 3 first recorded ">I> is
              not reachable at all"; its own review caught that. The witness
              that made the wrong answer look right was `::routine max`
              beside `call max 1,2`, where the builtin wins -- the one shape
              in which "behind 4c's builtin step" and "unreachable entirely"
              predict identical bytes. With a non-builtin name they part
              company: measured, `call zorkolo` with a `::routine zorkolo`
              present runs on the oracle at rc 0. So a ::routine IS reachable
              in 4b for any non-builtin name; 4b declines to implement it
              because getting builtin-colliding names right needs 4c's table,
              and a wrong answer there would silently run the wrong routine
              rather than fail loudly.

              THE SENTENCE ABOVE IS THIS ROW'S OWNERSHIP CLAIM -- "4b
              declines to implement it because getting builtin-colliding
              names right needs 4c's table" -- and it is the one to cite for
              who owns ::routine. Cited by line number rather than by
              content, that claim has already been fetched from the wrong
              place once: the 4c plan's D-R quoted "which 4c will have to
              meet", which heads the THREE MEASURED WAYS list further down.
              That list is about what a ::routine ACTIVATION looks like, an
              obligation on whoever implements it, and it would read the
              same whichever phase owned the work. Neither it nor the
              two-condition trace gate between here and it assigns anything.
              (The row header's own "4c, deferred alongside ::routine
              dispatch itself" states the conclusion; this paragraph is the
              reason for it, which is what a citation usually wants.)

              THE GATE IS TWO CONDITIONS, both of which 4b fails:
              `tracingLabels() && isMethodOrRoutine()` (RexxActivation.cpp
              :3655, read directly, in RexxActivation::traceEntry). Re-
              measured at Task 9 rather than carried forward:

                * `trace l` in the CALLER, targeting a ::routine -> nothing
                  at all. The caller's setting does not cross into it.
                * `::options trace labels` in the package, or a `trace l`
                  as the routine's own first instruction -> both lines fire.
                  RE-MEASURED AT TASK 13 AND THE SECOND HALF WAS NARROWER
                  THAN IT SHOULD HAVE BEEN: this said "non-dynamic", which
                  is `earlyTraceEntry`'s own condition (:3629-:3640) and not
                  the whole gate. `trace value 'l'` as a routine's first
                  instruction fires both lines too, through `setTrace`'s own
                  call to `traceEntry` (:1024). What "first instruction"
                  excludes is measured and is narrower still: a routine
                  whose first clause is a LABEL and whose second is `trace
                  l` fires nothing, because a label clears
                  `traceEntryAllowed` (:659) like any other instruction.
                * Exactly A, I, L and R, verified by running the same
                  routine under all nine accepted letters; n, c, e, f and o
                  produce zero stderr.
                * The content is NOT a clause echo. It is, verbatim:
                      >I> Routine "ZORKOLO" in package "<absolute path>".
                      <I< Routine "ZORKOLO" in package "<absolute path>".
                  so reproducing it needs the package object as well, and an
                  absolute path makes it host-dependent for any committed
                  expectation -- a witness for these belongs in the live
                  corpus, not in tests/trace_oracle/.

              THREE MEASURED WAYS A ::ROUTINE ACTIVATION IS NOT AN INTERNAL
              LABEL'S, recorded here before 4c met them:

                * It has its own variable pool. Measured: a caller with
                  `nn = 5` calling a ::routine that says `nn` prints the
                  derived name NN, not 5.
                * Builtins shadow it. Measured: `call max 1, 9` with a
                  `::routine max` present sets RESULT to 9 and the routine
                  never runs.
                * TRACE DOES NOT CROSS INTO IT AT ALL. Measured: a caller's
                  `trace r` echoes its own clauses and none of the routine's.
                  An internal label's clauses ARE echoed under the same
                  setting, which is what 4b implements.

              THREE MORE THAT TASK 13 MEASURED AND THIS LIST DID NOT HAVE.
              None of them falls out of the three above, and two are silent
              failures rather than visible ones:

                * NUMERIC, ADDRESS, the condition traps and CONDITION() are
                  all inherited by a CALLed label and by none of them by a
                  ::routine. Measured one field at a time, caller against
                  routine: `numeric digits 7`/`form engineering` reads back
                  as `9 SCIENTIFIC`; `address system` reads back as `sh`; a
                  caller's `signal on syntax name mytrap` does not arm the
                  routine's own `mytrap:` label; and CONDITION('C') inside a
                  routine called from a live handler is the null string.
                * A ::routine call sets no SIGL, on either side. The
                  caller's stays at whatever line it held, and `sigl` read
                  inside the routine is the derived name.
                * EXIT INSIDE A ::ROUTINE ENDS THE ROUTINE, NOT THE PROGRAM,
                  where EXIT inside a CALLed label ends the program.
                  Measured, all rc 0: `exit 5` in a routine leaves the
                  caller's RESULT at 5 and the main body running on; a bare
                  `exit` leaves RESULT unset; and the same holds when the
                  EXIT is reached from a label inside the routine, from an
                  expression call inside it, or from an INTERPRET inside it.
                  `implicitExit` (:1455-:1469) sets RETURNED outright for an
                  isProgramLevelCall activation and only otherwise walks up
                  through exitFrom.

              THE LESSON THAT GENERALISES, and it is why the first answer was
              wrong: absence under one instrument is not evidence of
              ownership. The first revision probed `trace i` on an internal
              label -- an instrument that could never have produced these two
              prefixes whatever the answer was.

              `::method` travels with `::routine` here (`isMethodOrRoutine`
              is one predicate) but is Phase 5's by the object model, not
              4c's. The row is named for both because the C++ gate is.

              WHAT SHIPPED AND WHAT DID NOT. Both lines are emitted, byte
              for byte, through the route the routine's own TRACE takes.
              corpus/lang/routine_dispatch.rex is the witness, and it is in
              the live corpus rather than in tests/trace_oracle/ for the
              reason this row already gave: the absolute package path makes
              any committed expectation host-dependent. trace_oracle.rs's
              PREFIX_COVERAGE carries the two rows as WitnessedLive and its
              own test runs the program, checks the prefix reaches stderr,
              and checks the program is in a subset file so corpus.rs
              compares it against the oracle.

              THE ::OPTIONS TRACE LABELS ROUTE IS NOT IMPLEMENTED, and it is
              not a gap in these two prefixes: ::OPTIONS is a declared Phase
              5 refusal (the directive section below), so a program taking
              that route is refused before `main` rather than run without
              the lines. The earlyTraceEntry code-analysis route is not
              implemented either, and no probe separates it from the
              setTrace route here -- it exists in the C++ to announce the
              entry before a guarded METHOD takes its object lock, and with
              no methods and no locks nothing can run between the two
              points.


EXCLUSIONS -- external routine resolution, Phase 7
--------------------------------------------------

  A NAMED CALL THAT MATCHES NO INTERNAL LABEL, NO BUILTIN AND NO ::ROUTINE
  RAISES 43.1 HERE. The oracle searches one more place first: an external
  Rexx file named for the target. Measured 2026-08-07, two directories, the
  same three-line program:

    a directory holding zorkolo.rex, whose body is
        say 'EXTERNAL FILE RAN' ; return 'EXT'

        call zorkolo ; say 'r=' result
          -> rc 0, stdout "EXTERNAL FILE RAN" then "r= EXT"

    an empty directory

        call zorkolo ; say 'r=' result
          -> rc 213, stdout EMPTY, and on stderr
               1 *-* call zorkolo
             Error 43 running <path> line 1:  Routine not found.
             Error 43.1:  Could not find routine "ZORKOLO".

  The second is what this crate answers in both directories. So the
  difference is confined to a program that has a matching file beside it,
  and 4c is byte-identical to the oracle for every program that does not.

  A ::ROUTINE BEATS THE FILE, which is why the step this task did land sits
  in front of the one it did not: measured, with zorkolo.rex present AND a
  `::routine zorkolo` in the calling program, the routine wins and the file
  never runs. So implementing the file search later cannot change any answer
  4c gives today; it can only add answers where 4c raises.

  OWNER: Phase 7, the platform layer. Resolving a name to a file needs the
  search path (the oracle tries the program's own directory, the current
  directory and PATH-like locations), file loading, and a second Package
  object -- the same subsystem the seven stream builtins above are blocked
  on.

  A CORPUS RULE FOLLOWS FROM IT, and rust/corpus/phase-4c.txt carries it: no
  corpus program may depend on external routine resolution. This is the
  easiest probe error in the phase rather than a theoretical one -- the
  session scratchpad sits on the oracle's own search path and holds hundreds
  of stale .rex files, and the same three-line program has been measured
  reporting 44.1 rc 212 from the scratchpad root and 43.1 rc 213 from a
  clean directory. Every measurement in this section was taken from a
  directory created for it.


EXCLUSIONS -- every directive except ::ROUTINE, Phase 5
-------------------------------------------------------

  THE RULE IS RESOLUTION, NOT PRESENCE, AND THE TWO FAIL IN OPPOSITE
  DIRECTIONS. Refusing any program that *contains* a directive rejects
  programs the oracle runs; ignoring one whose installation the oracle
  performs runs programs the oracle refuses. Measured 2026-08-07, one probe
  per directive form, each from a clean directory.

  RUNS ON THE ORACLE, rc 0, printing "main ran" -- and runs here too,
  because installing one of these neither executes code, changes a setting
  a Phase 4 construct can read, nor resolves a name against a table this
  crate does not have:

    ::class foo
    ::class foo + ::method bar
    ::class foo + ::attribute baz
    ::constant kk 5
    ::resource foo ... ::END
    ::annotate package author 'me'
    a loose ::method with no ::class

  REFUSED BY THE ORACLE BEFORE main, stdout EMPTY in every case -- and
  refused here, loudly, naming Phase 5 (or Phase 7 for the two that need a
  library loaded):

    ::class foo subclass zzznotaclass                  98.909 rc 158
    ::class foo metaclass zzznotaclass                 98.908 rc 158
    ::class bar inherit zzznotaclass                   98.909 rc 158
    ::annotate routine nosuchrtn                       99.945 rc 157
    ::requires 'no_such_file_zz.rex'                   43.901 rc 213
    ::routine z external "LIBRARY nosuchlib nosuchfn"  98.903 rc 158
    ::method m external "LIBRARY nosuchlib nosuchfn"   98.903 rc 158

  THE TWO DELIBERATE OVER-REFUSALS, both of which reject a program the
  oracle runs. Neither is silent: both name a phase and exit with
  NOT_IMPLEMENTED_EXIT, which is this file's standing trade -- a declared
  gap over a wrong answer.

    ::CLASS NAMING ANOTHER CLASS is refused whether or not that class
    exists, because 4c has no class table to tell the two apart. Measured,
    `::class foo subclass object` is rc 0 "main ran" on the oracle and loud
    here. The alternative is running the zzznotaclass program above at rc 0
    where the oracle produces nothing at rc 158.

    ::REQUIRES IS REFUSED EVEN WHEN THE FILE IS PRESENT. This one
    contradicts a measurement the task brief recorded as a requirement, and
    the reason is a probe the brief did not take: ::REQUIRES does not merely
    make names available, it LOADS AND RUNS the required file's prolog.
    Measured -- helper.rex whose first clause is `say 'PROLOG RAN'`, and
    `::requires 'loud_helper.rex'` in a program whose own body is `say 'main
    ran'`: the oracle prints

        PROLOG RAN
        main ran

    at rc 0. So presence IS use for this directive, in a way that changes
    stdout and not only which routine a call finds. The brief's own
    boundary case is the weaker half of the same fact: `::requires
    'helper.rex'` where the helper holds `::routine helperfn public` makes
    `helperfn()` return HELPED, so ignoring the directive also changes
    resolution. Getting either right means loading and running the file,
    which is Phase 5's ::REQUIRES.

  ::OPTIONS IS REFUSED FOR THE SAME REASON AND WITHOUT THE TRADE: its whole
  effect is to change package settings, unconditionally. Measured,
  `::options digits 12` in a program whose body is `say digits() form()
  fuzz()` prints `12 SCIENTIFIC 0`. There is no unused ::OPTIONS.

  WHAT REMAINS UNCLOSED. A duplicate ::ROUTINE is NOT in this section: it is
  detected and reported here as the oracle's own 99.903 at rc 157, echoing
  the directive clause, and rust/crates/rexx-exec/src/run.rs asserts the
  whole transcript. Everything else above that the oracle refuses is refused
  here with a loud message rather than with the oracle's own condition, so
  the number, the sub and the exit code differ; only "refuses before main
  with empty stdout" is shared.


DEVIATIONS -- permanent, chosen
-------------------------------

  0. LEADING INDENTATION ON STDERR IS NORMALISED BEFORE COMPARISON.

     IMPLEMENTED by 4b Task 2b: `tests/support/mod.rs` (shared by
     `rust/crates/rexx-exec/tests/corpus.rs` and `tests/trace_oracle.rs`) is
     the normalising function, applied at both harnesses' own stderr
     comparison and nowhere else -- never on a `trace_oracle.rs` `.expected`
     file's own regeneration, which stays raw oracle bytes. Every figure
     this project reported before this task landed was obtained under EXACT
     comparison; figures reported after it are under this normalisation, and
     Task 2b's own report says which, if any, moved (none did: the corpus
     was already 33 of 33 matching, so nothing could newly pass here).

     SCOPE, and it is deliberately narrow. The differential harness collapses
     the run of spaces between a line's prefix field and its content, on BOTH
     sides, for stderr only. Everything else stays byte-exact: exit status,
     stdout, the catalogue text, the clause text, the line numbers, the value
     lines' CONTENT, and the presence, absence and ORDER of every line. This
     is not licence to normalise anything else, and must not be cited as
     precedent for a second normalisation.

     WHY. The oracle's indent is not a computed property, it is a mutable
     counter with two inconsistent exit paths, and one of them is a defect:

       settings.traceIndent is a counter (execution/ActivationSettings.hpp:188).
       A loop ending NORMALLY calls terminate ->
         terminateBlockInstruction(doblock->getIndent())
         (instructions/BaseDoInstruction.cpp:161), an ABSOLUTE RESTORE of the
         value DoBlock saved at construction (instructions/DoBlock.cpp:71).
       A loop whose CONTROL TEST FAILS calls endLoop (:377), which does
         popBlockInstruction and a BARE unindent() -- no restore.
         unindent() clamps at 0 (execution/RexxActivation.hpp:318).

     So a completed loop that ends on a failing test leaves the counter one
     notch low for everything after it, until some enclosing construct
     restores from its own saved DoBlock.

     THE ARGUMENT IS INFORMATION CONTENT, NOT COSMETICS. Indentation is
     DERIVED from the clause sequence and block structure the harness already
     compares byte-for-byte. A matching indent proves nothing that a matching
     clause sequence does not already prove -- except that we have reproduced
     a C++ counter defect.

     *** THAT ARGUMENT IS TOO BROAD, AND 4b TASK 4 PROVED IT. ***

     It holds for an indent divergence caused by the ORACLE's counter defect,
     which is what this row was written about. It does NOT hold for an indent
     divergence caused by OUR OWN state management, and the harness cannot
     tell the two apart.

     Measured: Task 4's C1 was a failure to restore Interp::current_value_
     indent across a nested activation, so a second call in one clause
     computed its base from the first callee's last clause. With no TRACE in
     the program at all, an ordinary error report read

       oracle        4 *-*   say 1/0
       ours          4 *-*     say 1/0

     -- a real bug, user-visible, and the clause sequence is IDENTICAL, so
     nothing else in the comparison carries the information. Under this
     deviation the corpus reported 34 of 34 with that bug live.

     SO THE PINNED UNNORMALISED WITNESSES ARE NOT A FORMALITY. They are the
     only instrument that catches our own indent bugs, and the list below is
     load-bearing rather than decorative. A task that adds activation or
     block-level state must add a raw-bytes unit test beside them; the corpus
     will not do it. Task 4's own regression test says so in its comment,
     which is the pattern to copy. Value lines are the opposite case and stay exact:
     >>> , >V>, >O>, >L>, >F> and >A> carry intermediate results and
     evaluation order that NOTHING else in the output exposes, which is what
     makes trace the densest differential instrument this project has.

     WHAT IT COST TO NOT DO THIS. Four agents stated the indent rule five
     different ways and were wrong every time; three fix rounds on one task;
     and the remaining route to byte-exactness was to port the counter,
     defect included.

     WHAT SURVIVES SO A GROSS ERROR STILL FAILS: a small set of pinned
     indent witnesses at nesting depth <= 3 containing NO completed loop,
     compared WITHOUT normalisation. If we run a WHEN body at the wrong level
     those still go red. They already existed as `rexx-exec/src/run.rs` unit
     tests asserting an exact indent -- pinned by name rather than
     duplicated, since a unit test's own `assert_eq!` is outside either
     harness's comparison function and normalisation cannot reach it:
     `one_two_and_three_enclosing_dos_indent_by_two_four_and_six`,
     `the_corrected_28x_indent_rule_matches_all_fourteen_probed_shapes`, and
     `an_absorbed_whencases_escaping_false_branch_reports_end_at_its_own_
     residual_indent`. NOT
     `the_indent_after_a_loop_has_already_exited_is_not_left_over_from_it`:
     it runs at top level, where the oracle's counter is already clamped at
     0 and the correct and incorrect models agree, so it looks like a
     witness for this row's own gap and is not one.

     NONE OF THE THREE PINNED WITNESSES DEMONSTRATES THE COUNTER DEFECT
     ITSELF (review round 1, I2 -- an error introduced by this row's own
     wording, not by the task that pinned the names). The defect needs a
     completed loop pass followed by a failing control test; all three
     pinned witnesses raise on a FIRST iteration, before any pass completes
     and before the loop the failure sits inside ever ends. They are
     correct witnesses for lexical nesting depth, which is what "must still
     fail" above asks for -- nothing pinned anywhere exercises the counter
     gap itself, and that is the honest state, not a further gap to close.

     WHAT THIS DOES NOT CLOSE. The re-tested pass's missing >>> lines were a

  1. DO OVER on a stem does not reproduce the oracle's traversal order.

     The oracle walks a balanced tree; we use a hash map. Measured, inserting
     tails 1, 2, 3, 10, ZZ, B, the oracle yields "1 B 3 2 ZZ 10" -- not
     insertion order, not ascending, not descending, not byte order. It is
     CompoundVariableTable's tree shape, and reproducing it means reproducing
     the tree, which is the entire cost the hash map exists to avoid.

     Justified by measurement rather than by appeal to ANSI leaving the order
     implementation-defined: DO OVER on a stem appears zero times in ooTest,
     zero times in CoreClasses.orx and StreamClasses.orx, and a handful of
     times in samples/windows/ under oodialog/ and ole/, of which at least two
     print in iteration order. All are Windows-only samples that no gate runs.

     Consequence, and it is a rule rather than an observation: NO CORPUS
     PROGRAM MAY CONTAIN DO OVER ON A STEM. Such a program could never pass,
     because the oracle's order is deterministic and ours is a different
     deterministic order. DO OVER on a string or a number is fine -- each
     iterates once, yielding itself.

  2. The EVALUATION-depth limit raises 11.1 where the oracle raises nothing.

     Read this row carefully, because the same error number is parity on two
     axes and a deviation on a third, and only the third belongs here.

     PARITY, not a deviation, on the parse-side axes: nested parentheses and
     nested calls both raise 11.1 in the oracle -- bisected at roughly 39,900
     parens and in [34,500, 34,760] calls -- and MAX_EXPR_DEPTH raises the same
     11.1 at 50,000 on one shared budget. Same construct, same condition, same
     number. Nothing to record but the fact that it matches.

     DEVIATION on the flat-term axis: the oracle evaluates a 100,000-term
     expression and prints its answer, then dies at 150,000 with SIGSEGV, rc
     139, no condition and no message at all. There is no number to reproduce.
     4a raises 11.1 above its evaluation-depth limit instead, because 11.1,
     "Insufficient control stack space", is the closest condition the language
     has to what actually happened.

     So: on parens and calls we match the oracle; on flat terms we report where
     the oracle crashes. Both use 11.1 and only the second is a difference.

     Second-order consequence worth stating: a limit ABOVE the oracle's own
     cliff would be worse than one below it, since it widens the window where
     we succeed and the oracle segfaults. That is why the recommended limit is
     100,000 -- the largest depth the oracle is measured to survive -- and why
     the check must fire above 100,000 rather than at it. A 100,000-term
     expression reaches depth 100,000, and that is precisely the depth the
     oracle handles.

  3. POS's window overrun can match the haystack's NUL terminator; this
     crate declines to invent that byte.

     IMPLEMENTED by the pre-Phase-5 defect round: `find_forward`
     (`rust/crates/rexx-exec/src/builtin/string.rs`) reproduces
     `StringUtil::pos`'s own window overrun (`classes/support/
     StringUtil.cpp:206-253`) -- a rescan that recomputes its search length
     from a rejected candidate's own position rather than from where it
     resumes, so the search may run exactly one byte past where the whole
     needle would fit. Licensed by Moritz, 2026-08-14, narrowly.

     THE BOUND, stated as the arithmetic gives it rather than as a hedge.
     `range` is capped at `haystack.len() - start` before any of this runs,
     so the overrun reaches at most one byte past the end of the haystack.
     One byte can only supply a needle's LAST byte, so only a needle whose
     last byte would need inventing can be affected. So: the divergence can
     only manifest for a needle whose last byte is `'00'x`, searched with a
     window that reaches the end of the haystack.

     Measured: `pos('a'||'00'x,'aa')` is 2 on the oracle, which reads the
     `RexxString`'s own NUL terminator as that invented byte and matches
     through it. This crate does not synthesise a byte past the haystack and
     answers 0 there.

     WHY EXACT AGREEMENT IS NOT AVAILABLE. Matching the oracle's 2 here does
     not make the two sides agree, it moves the divergence one call further
     out: `count_occurrences` and `changestr` both walk forward from
     whatever `find_forward` answers, and a match that runs past the
     haystack's own bytes is exactly what the oracle's `changestr` copies
     through -- `changestr('a'||'00'x,'aa','ZZZ')` dies on the oracle with
     **SIGSEGV, rc 139**. There is no oracle behaviour to reproduce on the
     other side of that crash. Answering 0 at `pos` is the only place in
     this chain where "what the oracle does" and "a byte this crate can
     produce without inventing one" are still the same question.


EXPRKIND OWNERSHIP -- the expression forms 4a/4b do not evaluate
---------------------------------------------------------------------

Criterion 5 requires every out-of-scope `ExprKind` variant to name an owning
phase, and that owner has to be one of the phases the split table names --
"4b", "4c", "Phase 5" or "Phase 7", spelled exactly as the table spells them,
because `coverage.rs` and `loud.rs` assert the set and compare the strings.

Six variants stood here at the 4a gate. The design spec assigns only one of
them outright: `Message` is Phase 5's (the "assigned elsewhere" paragraph
names it, and `InstructionKind::Message`'s own doc says its `term` is always
an `ExprKind::Message`, so the instruction and the expression travel
together). The other five were never individually assigned anywhere in the
spec -- the nearest sentence ("argument attachment inside Call, QualifiedCall,
Message, List and VariableReference is exercised by 4b and 4c") names two
phases jointly for five variants, which is not an owner a `match` arm can
return.

This gap was found and closed at Task 16 gate time, not before. Five of the
original six rows were a judgement call rather than a spec citation, made by
the team lead ("main") on request when Task 16 flagged the ambiguity as the
one place a wrong call quietly breaks criterion 5's policing.

  Call              CLOSED (4b Task 4; was 4b). Genuinely split at Task 16
                    gate time, and the split was recorded rather than
                    smoothed into one silent string: a Rexx function call
                    resolves internal-routine first, then builtin, then
                    external, so 4b delivers the internal-routine half and 4c
                    delivers the builtin half. The owner named was the phase
                    after which the variant stopped failing loudly for SOME
                    call target, which was 4b -- an internal-routine call
                    evaluates as soon as 4b lands, and Task 4 is the task that
                    landed it. **Unlike `InstructionKind::Call`, which stays
                    split because two of `rexx_parse::Call`'s four arms
                    (`Trap`, `Qualified`) are still 4b's/Phase 5's own,
                    `ExprKind::Call`'s `CallTarget` has exactly two forms and
                    both are 4b's -- there is no later-phase arm left hiding
                    inside it, so the whole variant closes rather than staying
                    split.** A reader who reaches the end of 4b and finds
                    `f(1)` still loud for a builtin name is seeing 4c's own
                    unclosed half, which this row no longer records because
                    `ExprKind::Call` itself is no longer an ExprKind ownership
                    question -- see `eval_call`'s own doc (`rust/crates/
                    rexx-exec/src/eval.rs`) for the resolution order a name
                    still falls through to the loud `4c` fallback for, and
                    `CallTarget::Literal`'s own measured answer (Error 43.1 on
                    the oracle, the loud `4c` fallback here, exactly like
                    `CALL "SUB"`).

  VariableReference 4b. `>x`/`<x` exists to be passed at a call site (Error
                    20.930 otherwise), and `USE` -- the instruction that reads
                    an argument on the receiving end -- is 4b's.

  QualifiedCall     Phase 5. `ns:name(...)` needs a resolved package/namespace
                    object; namespaces come from `::REQUIRES`, and "every
                    directive... [is] Phase 5's" per the split table's
                    assigned-elsewhere paragraph.
                    That quoted phrase now carries a carve-out -- the design
                    spec reads "every directive except ::ROUTINE, which is
                    4c's" -- and this row is unaffected by it, because what
                    a QualifiedCall needs is a namespace, namespaces come
                    from ::REQUIRES, and ::REQUIRES is on the Phase 5 side of
                    the carve-out.

  ClassResolver     Phase 5. Explicitly: "environment symbols beyond .nil,
                    .true and .false are Phase 5's", and this variant is how a
                    namespace-qualified class name resolves.

  List              Phase 5. The general form builds an array, which is Phase
                    5's object model -- the same reasoning Task 14b's gap
                    report used when it argued against bringing `List` into
                    4a for the `SAY` case alone.

  Message           Phase 5, per the spec directly (see above).

This section is asserted the same way EXCLUSIONS and DEVIATIONS are: the set
of five still-open names and their owners is fixed, and `coverage.rs`/
`loud.rs` fail if their own owner table drifts from it. `Call`'s own row is
kept rather than deleted outright, the same "CLOSED DEFECTS" convention
below applies to a row whose own history is worth a reader tripping over
rather than losing to a quiet deletion -- removing it needs the same
amendment closing a KNOWN GAP does. Changing any row here is a plan
amendment, the same rule the rest of this file follows, because this is
exactly the kind of decision that has previously gone missing by living only

  Prefix operator chains ("- - - -1") recurse in message_subterm, which the
  shared expression-depth budget does not guard. They abort natively between
  1,150 and 1,200 levels on a default 2 MiB thread. The oracle's cliff for this
  construct has not been measured, so the size of the divergence is unknown.

  Debug, PartialEq and Clone on Expr are still recursive, with cliffs measured
  at 2,000/2,050 for Debug and 2,100/2,200 for the other two. No non-test path
  reaches them on a deep tree today: the only production formatter is a
  panic!("... {other:?}") that fires when the parser is already panicking, so
  the worst case is a panic message becoming a silent abort.

  A depth counter protects a sized caller only. On a default 2 MiB thread the
  native abort arrives at 331 parens or 341 calls, long before any counter at
  50,000 could fire. Every in-tree consumer runs on the sized interpreter
  thread; a library embedder on a normal stack does not, and the long-term
  answer is a documented minimum stack or a sized entry point in rexx-parse
  itself rather than a smarter counter.

  4b TASK 3 MEASURED THE SAME THING FOR ACTIVATIONS, and the numbers say
  something the paragraph above does not: a fixed counter cannot be a
  guarantee even ON the sized thread, because the budget is shared with
  run_bounded, which costs a Rust frame per LEXICAL nesting level. Bisected
  with rexx-run on the 512 MiB interpreter thread, unbounded CALL recursion:

    enclosing DO blocks per activation | deepest surviving (debug) | (release)
    ----------------------------------+---------------------------+----------
                                    0 |                    22,534 |   133,150
                                    1 |                    14,062 |    94,518
                                    5 |                     5,616 |         -
                                   25 |                     1,403 |         -

  * The unit is a level, NOT a block. An error three nested DOs deep echoes
    ONCE; the same error inside an INTERPRET fragment echoes twice, and inside
    a fragment inside a fragment three times.

  * Every echo of a fragment carries the ENCLOSING INTERPRET clause's line
    number, never a line of the fragment. Measured with a two-line file whose
    line 2 is interpret "say 2 & 1":

         2 *-* say 2 & 1
         2 *-* interpret "say 2 & 1"
    Error 34 running /abs/frag.rex line 2:  Logical value not 0 or 1.
    Error 34.901:  Logical value must be exactly "0" or "1"; found "2".

    The MAJOR line names the innermost entry's line, which for a fragment is
    the same number and for a CALL is not (see below).

  * Each echo's indent is ABSOLUTE and is NOT 2 x the depth of the stack. A
    fragment's clauses sit at the enclosing INTERPRET clause's own printed
    indent -- delta 0 -- plus whatever nests them INSIDE the fragment, EXCEPT

    interpret "do jj = 1 to 1; say 2 & 1; end" at top level echoes the inner

  * A CALLED ROUTINE's base is the calling clause's printed indent PLUS TWO,

    it cannot be derived from a depth counter. Measured, all four combinations:

  KNOWN GAP: TRANSLATE -- A NULL STRING'S IDENTITY DECIDES WHETHER TABLEIN WAS
  SUPPLIED. TRANSLATE's third argument has two meanings and the oracle tells
  them apart by the argument's ADDRESS, not its contents:
  RexxString::translate tests `tablei != GlobalNames::NULLSTRING`, and
  optionalStringArgument substitutes that same singleton for an omitted one.
  A null string that came from a builtin returning the singleton therefore
  takes the "omitted" path -- byte value as its own index into tableout --
  while a null string written as a literal takes the "supplied" path, where
  no byte is found and nothing is translated. Measured, one line each:

    zz = ''             ; say '['translate('abcdef','123',zz)']'  ->  [abcdef]
    zz = left('abc',0)  ; say '['translate('abcdef','123',zz)']'  ->  [      ]

  The producers among the string builtins, each measured on that same second
  line and each answering [      ]: LEFT, RIGHT, CENTER and CENTRE with a
  width of 0; SUBSTR with a length of 0; DELSTR deleting the whole string;
  STRIP with everything stripped; COPIES with a count of 0 or a null subject;
  SPACE with no words. REVERSE('') and a CHANGESTR that changes nothing do
  NOT produce it -- both return their receiver rather than the singleton --
  and neither does a literal ''. Concatenating the singleton with a literal
  '' still yields it.

  rexx-exec answers [abcdef] in every one of these, which is the literal's
  answer. Closing this needs a string's IDENTITY to be observable, which
  nothing else in the language makes so and which the value model (D15) has
  no room for: two values with the same bytes are the same value there. No
  owner is assigned, and a fix should be weighed against reproducing an
  upstream artefact nothing else depends on.

  FIRST CAUSE, the abort: resolve_and_run_call renders every evaluated
  argument to an owned Vec purely to hand it to trace_argument, which then
  discards it unless the trace mode asks for intermediates -- so a value of
  any size is copied whether or not anything will print it. The assignment
  path does the same at its own `>>>` render. Both are unconditional, and
  neither is guarded by try_reserve, so the copy aborts the process rather
  than raising. The builtins' own result allocation is single and fallible;
  the abort backtrace names resolve_and_run_call, not the builtin. MEASURED:
  with the argument render placed behind `if self.trace_mode().intermediates`,
  `say length(copies('a',N))` at 300000000 and 400000000 both return rc 0
  with the oracle's answer.

  CLOSED BY 4c TASK 13. The guard is paired with the render rather than
  written beside it: Interp::intermediate_text and Interp::result_text
  (trace.rs) each return None when no line of their own gate would print,
  and the seven sites whose rendered bytes feed nothing but trace calls go
  through them. The sites, each with the existing test that goes red when
  its line stops printing, because a wrong guard drops a trace line
  silently and that is the failure this fix could have introduced:

    the argument render (>A>)          call_arguments.rex
    the Assignment >>>/>=> pair        trace_output.rex, and 15 others
    EXIT's own >>>                     exit_value.rex
    RETURN's own >>>                   a_returned_value_traces_in_the_...
    USE ARG's >>>/>=> pair             call_arguments.rex
    RAISE ... RESULT's >K>             corpus_differential
    the caller's own >>> after a CALL  a_returned_value_traces_in_the_...

  Where a site feeds both a `results`-gated and an `intermediates`-gated
  line, the gate used is `results`, the weaker of the two: it is true
  wherever `intermediates` is, so it can never drop a line, and the cost of
  choosing it is one redundant copy under TRACE R. Measured that the
  opposite choice is caught -- swapping the six result_text calls for
  intermediate_text turns 14 tests red.

  assign_expr_target's `rendered` parameter became Option<&[u8]> in the same
  change, so the guard is visible at the callee rather than only at the
  caller: an empty slice because tracing is off and an empty slice because
  the value is the null string are the same value, and only one may print.

  eval.rs's own seven intermediate renders needed nothing: trace_intermediate
  already returns at the top when !tracing_intermediates(), which is the same
  guard one level up.

  THAT MEASUREMENT WAS FIRST RECORDED HERE AS "THE WHOLE OF THIS CAUSE",
  WHICH IS FALSE, AND THE CORRECTION IS THE USEFUL PART OF THIS ROW. With

    say length(reverse(copies('a',400000000)))

  a path that may discard it -- and not the pattern's only member. Whoever
  fixes this is looking for that shape, not for one line.

    builtin::required_string        into_owned() so the builtin can hold a
                                    &[u8] while calling back into Interp
    Interp::concat  (eval.rs)       builds the joined bytes in a Vec and

    Interp::eval_compare            into_owned() of BOTH operands

    Interp::assign_targets          a SECOND, separately-found copy on the
      (parse_template.rs:670)       same path: `self.text(&cursor.string()
                                    [piece])` for every bound template

                                    `self.text_owned` would move the buffer

  "THREE COPIES" IS THE FLOOR AND NOT THE SHAPE: THERE ARE THREE BANDS.
  Measured 2026-08-06 by sweeping N down under the standard
  `ulimit -v 1048576`, last size that succeeds -> first size that fails:

    reverse / substr / if-compare        200000000 -> 250000000
    strip / parse value                  150000000 -> 170000000
    say / concat                         100000000 -> 120000000
    say length(copies('a',N)), no
      wrapping call at all               465000000 -> 470000000

  The last row is the calibration rather than a defect: with no extra copy
  this crate's usable single allocation under that limit is between 465 MB
  and 470 MB -- about 70 MB under the naive "1 GiB minus D19's 512 MiB"
  arithmetic, from the thread's own stack, the code and data segments and
  allocator bookkeeping. Dividing that ceiling by a site's live-copy count
  predicts each band: 465/2 is inside (200M, 250M] and 465/3 is inside
  (150M, 170M].

  AND `||` AND SAY PAY A GROWTH-POLICY PENALTY ON TOP OF THE COPY COUNT,
  which is why they are a band of their own rather than sitting with strip
  and parse value. `Interp::concat` builds its buffer from the left operand
  at EXACT capacity and then `extend_from_slice`s the one-byte right
  operand, so Vec's amortised growth policy asks for roughly DOUBLE the left
  operand's size to append one byte. The Say arm has the identical shape:
  `out.extend_from_slice(&line)` at an exact fit, then `out.push(b'\n')`.
  Measured directly, from the failing allocation's own size in the abort
  message: `say length(copies('a',200000000) || 'x')` requests exactly
  400000000, `say copies('a',120000000)` requests 240000000 and
  `say copies('a',150000000)` requests 300000000 -- 2N in every case. The
  cost here is the growth policy, not a further copy, and no count of copies
  predicts it.

  NO GUARD FIXES ANY OF THEM, and that is why they are their own cause
  rather than sites the first cause missed. Each copy exists to satisfy the
  borrow checker: `Interp::to_text` (value.rs:128) hands back a
  `Cow::Borrowed` that borrows the INTERPRETER, not the value, and every
  consumer needs `&mut self` again immediately, so the bytes are copied out
  to end the borrow.

  THE OBSTACLE IS TYPE-LEVEL, AND IT IS WHY THE OBVIOUS REPAIR IS NOT
  AVAILABLE: `Cow::into_owned()` HAS NO FALLIBLE FORM. It goes through
  `Vec::to_vec()`, which calls the infallible global allocator and aborts by
  design, so `try_reserve` -- the idiom `builtin::buffer`
  (builtin/mod.rs:858-863) already uses for a builtin's own RESULT
  allocation -- cannot be pasted in at any of these sites. Guarding them
  means not calling `.into_owned()`/`.to_vec()` at all. Closing it needs
  `Interp` methods that read and allocate in one call -- a
  `text_from(value, range)` for the slice-taking builtins, a `concat_text`
  reserving left+right up front (which retires the doubling as well), a
  comparison that works from two borrows, and `self.text_owned` in place of
  `self.text` at parse_template.rs:670 -- which is a value.rs signature
  change plus one edit per builtin, not a guard. None of those helpers
  exists anywhere in crates/rexx-exec/src today; checked 2026-08-06.

  AND THE THIRD CAUSE CANNOT DELIVER rc 0 AT THIS ROW'S OWN PROBE SIZE
  WITHOUT THE SECOND. Even a perfect fix -- every one of the seven sites
  down to its theoretical minimum of one live copy -- does not get these
  programs to the oracle's answer at N=400000000 under the standard limit.
  Two live copies of 400 MB is about 763 MiB against the ~465 MB usable

  owners and are NOT separately closable at this probe size. Whichever plan

  correct fix, reruns the recorded probes, sees rc 134, and concludes the
  fix was wrong.

  This cause is UNASSIGNED. It is not a Phase 5 or Phase 7 feature, it is

  Whoever takes it should note the shape difference in one line: the first

  WHAT A USER SEES. Under the project's standard `ulimit -v 1048576` two of

    bench-programs/arith.rex     rc 134, stdout empty,
    bench-programs/strings.rex   stderr `memory allocation of 402653184
                                 bytes failed`

  No Rexx condition is raised, so SIGNAL ON SYNTAX cannot catch it; no

  ONE OF THOSE TWO IS THE CAP RATHER THAN THE MEMORY, which rust/CLAUDE.md
  requires every `ulimit -v` finding to state. `ulimit -v` charges reserved
  address space, and this crate reserves INTERPRETER_STACK_BYTES = 512 MiB
  (lib.rs:309) before any program runs. Raising the cap by exactly that, to
  `ulimit -v 1572864`: arith goes rc 134 -> rc 0 with correct output, and
  strings still dies (`memory allocation of 805306368 bytes failed`). So
  with the reservation free ONE axis dies, not two. The ruling stands on the
  linearity rather than the count: growth is linear and unbounded on every
  shape measured, so any finite limit is reached by a long enough run, and
  the failure is a function of how long a program runs rather than of how it
  is written. A four-line loop correct today fails after enough iterations.

  CAUSE A -- NOTHING TRIGGERS A COLLECTION, so every heap object a program
  allocates is retained for the process's whole life. Retention is 128
  bytes per short string, 144 per wide decimal, of which 96 is the
  `rexx_core::heap::Slot` the arena vector grows by (massif, at
  `Heap::alloc_with_uncollected`). `Heap.slots` is only ever pushed and
  indexed -- no truncate, no shrink_to_fit -- so the arena is a permanent
  high-water mark. That bounds rather than defeats a trigger policy: the
  free list IS reused, and measured on one 8,000,000-iteration program,
  peak RSS tracks the collection interval linearly -- 1,002,700 KB with no
  collection, 15,796 KB forcing one every 100,000 iterations, 4,036 KB
  every 10,000.

  CAUSE B -- A LOOP HEADER'S TEMPS ARE ROOTED UNTIL THE LOOP ENDS, which is
  a root leak and NOT fixable by a collector. TWO push sites, and naming
  only the first is the error this row was first filed with:

    Interp::loop_advance   (run.rs) the control variable of DO i = ...
    Interp::eval_condition (run.rs:6017) every WHILE or UNTIL test

  Both run inside the SAME single step_in_temps_frame -- the one belonging
  to the whole DO instruction -- so both accumulate 8 bytes a pass for the
  loop's entire run, and a loop with both pays both. The tree already
  documented the second: step_in_temps_frame's own doc at run.rs:4073-4082
  says "a `do while` running 10^7 passes holds ~10^7 dead-but-rooted temps
  in one frame", classifying it as a cost rather than a defect, which was
  right while nothing collected.

  MEASURED, 8,000,000 iterations. `do n; nop; end` is flat at 2,532 KB, with
  no control variable and no condition. `do i = 1 to n; nop; end` reaches
  64,268 KB. `do n while zz; nop; end` with zz=1 -- no control variable, and
  nothing on either side of the test that allocates -- reaches 64,468 KB,
  which isolates the second site with the first absent. UNTIL matches
  (63,704 KB). When the rooted values are not tagged small integers the
  roots pin heap objects too: `do i = 1.5 to n by 1` with a nop body costs
  1,064,416 KB.

  A FIX MUST COVER BOTH SITES. All four runnable benchmark axes are
  `do i = 1 to n`, so a fix to loop_advance alone turns every axis green and
  leaves DO WHILE and DO UNTIL growing without bound -- the shape a
  long-running service loop is actually written in. `do n while zz; nop;
  end` is the acceptance test, not varlookup.rex.

  AND A WARNING ABOUT THE INSTRUMENT: massif attributes the realloc, not the
  leaking push. Both sites push into one RootSet.temps vector, so massif
  names whichever push crosses the capacity boundary. Measured on `do while
  k < n; k = k + 1; end` it names eval_arithmetic (eval.rs:620), the BODY's
  push, while the entries piling up are eval_condition's. Isolate a suspect
  push by removing the others (a nop body), not by reading the deepest
  frame.

  NOT A BROKEN COLLECTOR. Both prototypes were built, measured and reverted;
  with both in place the whole test suite passes, 1,317 tests, 0 failures.
  Peak RSS falls 42x on arith, 16x on compound, 298x on strings and 60x on
  varlookup, and strings gets 16% FASTER. Prototype B covered loop_advance
  only, so those figures bound the counted form and say nothing about what
  closing the WHILE/UNTIL site is worth.

  WHY THE DIFFERENTIAL SUITE CANNOT SEE THIS, AND THIS LIMB IS THE ONE THAT

  past the re-test: the re-test has already run by the time h2 executes, so the
  third condition h2 queues is queued after it, and the next thing the oracle
  does is the following pass's first body clause. It is THIS CRATE that queues
  the third condition before the re-test and delivers it after, which the trace
  above shows as `6 *-* do while zn < 2` followed by `16 *-* h3:`.

  WHY THE SHIFT IS INVISIBLE ON h2 AND VISIBLE ON h3. Both interpreters report
  the ITERATE's own line as the requeued handler's SIGL and agree on the number:
  h2 reads SIGL 9 on the oracle and on both engines under the traced program, and
  SIGL 8 under the untraced one above. Neither delivers the third condition at
  the point where h2 ran. Where they then put it is what stdout sees: the oracle
  reaches the following pass's first body clause (SIGL 6, or 7 traced) and, on
  the last pass where there is none, the clause after the loop (SIGL 10, or 11
  traced, after "after 5" has printed); this crate reaches the re-test's echo and
  reports the ITERATE's line, SIGL 8, or 9 traced, both times.

  any of these instruments. `trace i` places a delivery between two clause
  echoes and SIGL names a line, and neither says which clause's boundary ran it:

  KNOWN GAP: ABS OF A POSITIVE LITERAL UNDER NUMERIC FORM ENGINEERING ANSWERS
  THE LITERAL'S OWN SPELLING. This one is an UPSTREAM ooRexx DEFECT, recorded
  rather than reproduced, and the decision whether to file it is Moritz's.

  READ THE PARAGRAPH AT THE END OF THIS ROW BEFORE TRUSTING THE TRANSCRIPTS:
  the oracle's own working tree was patched for exactly this defect and
  rebuilt on 2026-08-05 at 16:02, part-way through the task that measured it,
  so the transcripts below reproduce only against the unpatched build.

    numeric form engineering ; say abs(1e10)        ->  1E10
    numeric form engineering ; say abs(01)          ->  01
    numeric form engineering ; say abs(9.996E+20)   ->  9.996E+20
                               say abs(1e10)        ->  1E+10
    numeric form engineering ; say abs(-1e10)       ->  10E+9
    numeric form engineering ; say abs('1e10')      ->  10E+9
    numeric digits 3 ;         say abs(1e10)        ->  1E+10

  THE CAUSE is a sign inversion in NumberString::copyIfNecessary
  (classes/NumberStringClass.cpp:3652), which decides whether to clone with

      digitsCount > digits || createdDigits != digits || isScientific() != form

  where `form` is number_form() and Numerics::FORM_SCIENTIFIC is `false`
  while FORM_ENGINEERING is `true` (runtime/Numerics.cpp:108). For a
  scientific-created number that reads `true != false` under SCIENTIFIC --
  always clone -- and `true != true` under ENGINEERING -- never clone. It
  wants `isScientific() != (form == Numerics::FORM_SCIENTIFIC)`. When it
  declines to clone it returns the object itself, whose cached stringObject
  is the literal's own text, and that is what prints.

  Only ABS reaches it among the numeric builtins: MAX, MIN, TRUNC and FORMAT
  all go through prepareNumber(digits, ROUND), which always clones, and SIGN
  discards the copy. Reproducing it would need the same thing the MAX/MIN row
  above needs -- a literal's parse-time-attached number told apart from a
  runtime string's -- plus the inversion itself. No owner is assigned, and a
  fix should be weighed against reproducing an upstream defect deliberately.

    (b) a selector that caselessly compares equal to `'ENVIRONMENT'` reads/

  KNOWN GAP: DATE/TIME READ THE WALL CLOCK IN UTC, NEVER THE HOST'S LOCAL
  ZONE. `builtin::datetime::real_clock_base_time` builds every no-argument
  reading from `SystemTime::now()` with a time-zone offset fixed at zero;
  this crate carries no time-zone database at all. The oracle's own
  `SystemInterpreter::getCurrentTime` reads the host's local zone. Wide by
  the numbers, not a rounding difference -- measured on this host (UTC+2
  at measurement time), all four with rc 0 both sides:

    say time('N')     oracle 15:37:39         rexx-exec 13:37:39
    say time('O')      oracle 7200000000        rexx-exec 0
    say date('T')      oracle 1786117069         rexx-exec 1786109869
    say time('T')      oracle 1786117069         rexx-exec 1786109869

  Every no-argument reading of any of `DATE`'s thirteen or `TIME`'s eleven
  letters carries this offset somewhere in its answer, whether or not the
  specific letter above was the one measured -- `N`'s own wall-clock hour
  is the most visible, `O` is the offset itself read back, and `T` is the
  absolute count both of those are built from.

  A COMPOUND OR STEM VARIABLE AS A DO CONTROL VARIABLE WAS NEVER BOUND
  (fixed, 4c Task 14 -- this was the EXCLUSIONS row above, "a compound
  variable as a DO control variable, owned by 4c", moved here). `do cv.j =
  1 to 5` is legal Rexx and the oracle assigns the compound `CV.J` on every
  pass. `rexx_parse::Controlled::control` is already a bare `SymbolId`
  carrying the whole interned spelling `cv.j` reduces to, the same starting
  point `say cv.j` uses one line later, so this was never a parse gap --
  the EXCLUSIONS row's recorded cost, "closing it needs a rexx-parse change
  (`Controlled::control` carrying the same `VariableRef` shape an
  assignment target does)", was wrong on both halves: an assignment
  target's own shape is `Expr`, not `VariableRef`, and `VariableRef` itself
  has no tail at all.

  WHAT WE USED TO DO: `bind_control` ran every control variable through
  `slot_of`, a flat name-to-slot lookup with no tail resolution, so a
  compound's tail was never looked at and nothing a later `say cv.j` could
  read back was ever written. Measured against the oracle, both from a
  clean directory:

    c=0; j=1; Do cv.j=1 To 5; c=c+1; End; say '['c cv.j']'

      oracle    [8]
      rexx-exec [4]  -- before the fix, the compound's tail was re-resolved
      on read but never on write, so the two disagreed about which pass
      was which

  THE FIX: `bind_control`, and the controlled loop's own re-tested read in
  `loop_advance`, both dispatch on `shape_of` the same way
  `assign_expr_target` already does for an ordinary assignment target -- a
  stem writes through `stem_assign`, a compound resolves its tail fresh
  each time against the tail variable's *current* value (`tail_key`) and
  writes through `stem_set`, and a simple variable's own write is otherwise
  the same slot write as before, keeping its `intermediates`-gated tracing
  and the no-allocation-when-not-tracing cost that gate's own measurement
  pins. The dispatch itself -- `shape_of` classifying the control's
  spelling, a linear scan for a `.` byte -- now runs unconditionally on
  every pass regardless of shape, a cost the cited measurement does not
  cover and this fix did not re-benchmark (correctness over performance;
  the simple-variable arm's own *behaviour* is unchanged, its cost is not
  necessarily so). Both witnesses above now match the oracle exactly, and
  so does the `>C>` trace line before every `>V>`/`>=>` of a compound
  control, measured against the oracle byte for byte under `TRACE I`.
