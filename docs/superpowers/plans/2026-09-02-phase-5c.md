## The premise, in one paragraph

Table C's method probes are `hasMethod` readbacks; a method is never sent. So a row agrees when the
probe **constructs an instance** and the class **answers the documented name set** — not when the
method works. Implementing method bodies is real work that this phase's instrument cannot see, and
it is out of scope here. Every one of the 868 is construction-blocked on this crate today.

## Task 1 — the construction route, and surface B

**First, because every other task depends on the route existing.**

`gate_table_c.rs` stated the obligation in its own words at BASE, in the doc comment on
`method_probe_text` that Task 1 has since replaced: *"Every instance-arm program here opens
with a bare `~new`, and there is no route to a committed construction program because none exists to
route to. The task that commits the first one has to add that route here in the same change; what it
must not do is flip a class to `covered` and leave the derived probe on a bare `~new` that raises."*

Build that route, and use it for surface B's eight classes, whose `~new` needs arguments. `.TimeSpan`
is the worked case: `.TimeSpan~new(1)` already answers `0.000001` on this crate, byte-identical to
the oracle, so its 47 rows need only the program.

`covered`'s second limb is the hand-written `CONSTRUCTION` const at
`crates/rexx-extract/src/docs/classes.rs`, and at BASE `status_of` reached `Covered` only through it —
**so the status transition is a string edit and is not by itself evidence of anything.** Whatever
this task builds must make the transition mean the probe constructs. Say in the report how you made
that true, and what would still let someone flip a class without it.

**Done when:** the route exists and is exercised by at least surface B's eight; each of those eight
probes is rc 0 and matches the oracle on three descriptors, both engines; and the control — flip a
class to `covered` without a program — has been run and is shown to fail.

**Landed 2026-09-02, and the done-when was not met in full.** The route is
`class-set.txt`'s `construction` column, derived from `Coverage::Covered(String)`, and it moved
`TimeSpan` (47 rows) and the three comparators (2 each) — table C's 5c count 868 → 815. Two of the
seven are **not** rc 0 and are left `not-covered`, measured from a fresh directory on both engines:

* **`Alarm`** — every path through `CoreClasses.orx:1472`'s `init` does `DateTime`/`TimeSpan`
  arithmetic, and this crate answers *the operator `+` applied to an instance of a user class is not
  implemented (Phase 5)* at rc 120 for a `String`, `TimeSpan` and `DateTime` `atime` alike.
* **`Ticker`** — rc 120 at `method "SIGN" of class "String"`, and past that its `init` reaches
  `!createTimer` (`EXTERNAL 'LIBRARY REXX ticker_createTimer'`), `guard off` and `reply`.

Both also need the construction cell to hold **more than one clause**: a live `Alarm` or `Ticker`
keeps the oracle running until it fires — measured, `.Alarm~new(86400, …)` printed its line and then
hung past a 60 s bound — so the program has to `~cancel` what it built. The committed cell is a
single Rexx *expression* today. Whoever takes these needs the operator work first; the cell growing
to a clause sequence is the smaller half.

`file` is 5d's and stays surface B's seventh.

## Task 3 — surface C, the classes with no `~new`

`RexxInfo` `RexxContext` `StackFrame` `VariableReference` — **57 rows.** All four raise on `~new` and
all four have a working Rexx-level route, measured on the oracle:

```
.context~class~id                 ->  RexxContext
.context~stackFrames[1]~class~id  ->  StackFrame
.RexxInfo~class~id                ->  RexxInfo
x = 5 ; say (>x)~class~id         ->  VariableReference
```

**These are not D73's `unreachable`.** `classes.rs`'s `UNCONSTRUCTIBLE` already carries all four as
`Status::NotCovered`, on the rule that a sentence naming a Rexx-level route makes a different claim
from one that does not. Read that doc comment before classifying anything.

**Landed 2026-09-03, two of the four.** `RexxInfo` (`.RexxInfo`) and `RexxContext` (`.context`) are
`covered` through Task 1's route, each probe rc 0 and byte-identical to the oracle on three
descriptors on both engines — table C's 5c count **280 → 237**, 28 + 15 rows. `coverage_of`'s guard
was narrowed to fire on a bare `~new` that *constructs* rather than on one with no swept outcome:
`RexxInfo` is the one class-set name absent from `CONSTRUCTION`, because its `.environment` entry is
an instance and the sweep sends `~new` only to class objects.

**`StackFrame` and `VariableReference` did not move**, measured from a fresh directory on both
engines:

* **`StackFrame`** — the book names two routes and this crate refuses both: `.context~stackFrames` is
  rc 120 `method "STACKFRAMES" of class "RexxContext" is not implemented (Phase 5)`, and
  `condition('O')` is rc 120 `CONDITION option "O" answers a Directory, which is not implemented`.
  Both work on the oracle, measured: `.context~stackFrames` answers an `Array` whose `[1]` is a
  `StackFrame`, and under `signal on syntax` `condition('O')~stackFrames` answers a **`List`** of one
  whose `~firstItem` is a `StackFrame` (`[1]` on a `List` is an index handle, not a position, and
  answers `.nil`). The condition route needs a trap — a `SIGNAL ON`, a raising clause and a label —
  where the construction cell holds one expression, so the committable shape is
  `.context~stackFrames[1]` and what it waits on is `RexxContext~stackFrames`: a method body, and a
  `RexxContext` method row's own subject.
* **`VariableReference` -- closed 2026-09-03, and the four rows now `agree`** (table C's 5c count
  237 -> 233). `>x` answers a `VariableReference` bound to the variable's storage; the paragraph
  below is the state it was found in, and the task report has the oracle edges that decided the
  object's shape, the escaping-reference case that `RootSet::promote` exists for, and the two
  renderings that are the referent's `stringValue()` rather than its string conversion.
* **`VariableReference`, as found** — this crate evaluated `>x` to the referenced variable's *value*, so
  `o = >vr` then `o~class~id` answers `String` where the oracle answers `VariableReference`, **rc 0
  on both sides with empty stderr**: a silent divergence, not a refusal. The decay is deliberate and
  dates to `8b87195bc` (2026-08-03), where
  `run::tests::a_variable_reference_decays_to_the_referenced_value` asserts `say >p` prints `p`'s
  value — which the oracle also does, so the divergence appears only once a message is sent to the
  reference rather than in the `say` that test asks. (That test still asserts the same thing and is
  now `a_variable_reference_renders_as_the_referenced_value`: the rendering was never the wrong
  half.) Its four `hasMethod` readbacks come out
  `0 1 0 0` against the oracle's `1 1 1 1`. The construction cell that would work needs no clause
  sequence — `>vr` over an uninitialised variable is a single expression and answers a
  `VariableReference` on the oracle, measured — so what is missing is the object, not the cell.

**The brief's "three of the four are already byte-identical to the oracle" is false**, measured at
BASE `dcd4d4e9c` on the committed probes: only `rexxinfo__instance` was. `rexxcontext`, `stackframe`
and `variablereference` are each rc 120 loud against the oracle's rc 163 `93.967 NEW method is not
supported`. The two that remain are therefore in `Pointer`'s position as well as their own — a `NEW`
row raising 93.967 would make each probe byte-identical and move no row, which is Task 2's finding
for `Pointer` and belongs with it.
