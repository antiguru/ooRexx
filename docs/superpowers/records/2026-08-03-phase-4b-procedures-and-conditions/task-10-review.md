## Findings

### Critical

1. **Two of the three "combination" mutations are already caught by pre-existing single-construct corpus programs, without the combination.** I ran each mutation myself (backed up `run.rs`, edited, rebuilt, ran, restored via `md5sum`-verified copy, confirmed `git diff --stat` empty). For `raise_in_routine_in_loop.rex`'s credited mutation (`exec_raise`'s `Some(trap) if trap.call` arm, `Ok(Flow::Return(result))` -> `Ok(Flow::Return(None))`, `run.rs:3041`): the pre-existing `condition_traps.rex` block 4 (a single `call raiser`, no loop, already in the 4b corpus since Task 7) diverges identically under the same mutation (`RAISER-RETURNED` -> `RESULT` in both `accumulated:`/`final:` lines). For `expose_stem_across_calls.rex`'s credited mutation (`exec_procedure`'s `alias_slot` loop, `run.rs:2000-2002`, skipped): the pre-existing `call_procedure_expose.rex` (single call to `stemsub`, no loop, no trap, already in the 4b corpus since Task 5) diverges in **five** of its five output segments under the same mutation, more thoroughly than the new program's own divergence. Only `call_on_trap_rearms.rex`'s credited mutation (`deliver_pending_trap`'s trap reinsertion, `run.rs:2709-2714`, skipped) is genuine new coverage: I confirmed `condition_traps.rex` is byte-identical before and after that mutation, because it only fires its `CALL ON` trap once. **Established by running**, not reasoning -- this is exactly the "does the program pin the combination, or would a single-construct program have caught the same mutation" question the dispatch asked, and for two of three the answer is the second one. The report never checked this; it verified only "the mutation causes *a* divergence," not "a divergence a simpler existing program does not already show."

2. **The I19 sweep's central enumeration is false.** The report states "`pop_frame` has exactly one call site in the whole crate (`run.rs:3749`)." Grepping the crate finds seven: `run.rs:3749` plus six in `eval.rs` (lines 591, 651, 701, 764, 804, 891 -- `eval_prefix`, `concat`, and four more binary-operator helpers). `rexx-core`'s own `RootSet::pop_frame` doc comment independently corroborates the six-in-`rexx-exec` count ("`rexx-exec` has six functions that open a frame and then use `?`"), so this was discoverable without leaving the tree. On inspection, the six `eval.rs` sites use a different, documented-safe discipline than I19's shape: each computes its return value and returns it to its immediate caller with **no allocation in between** (`concat`'s own comment: "`joined` is unrooted from here to the caller's own `push_temp`, and nothing between the two allocates"), and `to_text` -- the one thing `eval()`'s own post-processing calls on a freshly-returned, not-yet-rerooted value under `TRACE I` -- reads the heap without allocating (confirmed by reading `value.rs:117-163`). I found no live rooting bug among the six. But the report's "nothing else found" is not established by examining them -- it never mentions their existence -- it rests on a false count. **Established by running** (grep, plus reading `roots.rs`'s own doc comment, plus reading and reasoning through `concat`/`to_text` to check whether the miscounted sites are actually safe).

### Important

3. **Two shipped corpus-file header comments state a specific, checkable technical claim about `CALL ON` handler semantics, and the claim is backwards.** `raise_in_routine_in_loop.rex:21` and `call_on_trap_rearms.rex:19` both assert (near-identically) that "SIGL inside the handler reads [the called routine]'s own RAISE line, not the calling clause's." I ran all three programs against the live oracle from a fresh directory and diffed byte-for-byte: `raise_in_routine_in_loop.rex` prints `[H@46]`, and file line 46 is `call looper zi` (the calling clause) while line 55 is `raise user ping return 'TRAPPED'` (the routine's own line); `call_on_trap_rearms.rex` prints `[H44]`/`[H50]`, and lines 44 and 50 are the two `call raiser` clauses while line 56 is the routine's own `raise`. In every measured case SIGL reads the *calling* clause's line, the opposite of what both comments state. The same false text is duplicated in the matching `rust/crates/rexx-parse/tests/sourceline_oracle/{raise_in_routine_in_loop,call_on_trap_rearms}.txt` fixtures. This does not affect the programs' validity as byte-matching witnesses (both engines agree, whichever way SIGL actually resolves), but per `rust/CLAUDE.md`, "a comment that states something false must be corrected or removed, not hedged" -- and this is a comment making the exact kind of load-bearing behavioural claim the corpus headers exist to state accurately. **Established by running** (oracle probes plus counting file lines).

4. **The report's own "Oracle-matched output" quotations are wrong, in the same direction as finding 3.** `task-10-report.md` quotes `accum: 10:1 [H@5]TRAPPED:2 30:3` and `after loop: 1 4 9 14 H@5` and `S[H4]1:VK[H10]2:V`; the actual byte-identical oracle output (independently reproduced) is `[H@46]`, `H@45`, and `[H44]`/`[H50]` respectively -- every one of the report's SIGL numbers has lost a leading digit. This does not touch the actual gate, which computes its own diff against the real bytes and passed independently in my re-run (44 of 44). It does mean the report's "matched byte for byte, unnormalised (a raw `diff`, not merely...)" claim, whatever check produced the passing gate, was not the same check that produced these quoted numbers -- the quoted numbers were written from an assumption (a short file, single-digit SIGL) that the final, much longer header comment invalidated, and were never re-verified against it. **Established by running.**
