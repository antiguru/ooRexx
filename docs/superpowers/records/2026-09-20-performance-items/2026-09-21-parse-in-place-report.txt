## What landed

`Cursor` no longer owns a `Vec<u8>`. It keeps the positions the triggers move
and nothing else; the parse string sits beside it in `exec_parse` as a
`SourceText`:

* `Owned(Vec<u8>)` -- a buffer from `Interp::parse_buffers`. `PARSE SOURCE`,
  `PARSE VERSION`, `PARSE PULL`, `PARSE LINEIN`, a source that is not a string
  object, and every folding `PARSE UPPER`/`LOWER` still take one.
* `Inline(InlineText)` -- a source whose bytes are in the handle, which is a
  `Copy` value the enum holds, so nothing in the arena reaches them.
* `Text { value, length }` -- a rooted `Body::Text`, read where it already is.

`SourceText::bytes(&self, interp: &Interp) -> &[u8]` is the only reader, and
the slice it hands back borrows `&Interp`, so a `&mut self` call ends the
borrow and the next use derives it again. That is the whole of the soundness
argument against the arena moving the bytes, and it is the compiler's rather
than mine -- see "the control that does not compile" below.

### The positive key

`Interp::source_text` borrows for `Decoded::Text` and for a heap `Body::Text`,
and copies for everything else. A `Body::Text`'s bytes are written once, by the
`alloc` that builds the object, so they cannot change length under the walk;
a `MutableBuffer`'s contents can, and `Body::Instance` is not admitted. The
`length` is therefore cached in the arm and asserted at every derivation
(`debug_assert_eq!` in `SourceText::bytes`) and again against the slice
`next_word` is handed.

### One derivation per target, which is the whole margin

`take_piece` carves the piece and builds its text value under a single borrow.
`Heap::body_text` answers a live `Body::Text`'s bytes in one indexing and one
match where `Heap::get` plus a body match is two of each. `next_template` takes
the cursor's length from the cache rather than from the arena.

## The hazard, and the test for it

`a_template_walk_survives_a_collection_between_its_targets` runs a program
under `run_program_collect_every_alloc` whose every piece is longer than
`INLINE_TEXT`, so every assignment allocates and every allocation collects.
Its last template is

    call fill
    parse var sm.1 s1 sm.1 s3 s4

with `sm.1` filled inside `fill`, so no live register holds the object and the
second target takes the stem entry away from it: from there on, the walk's own
temporary is the only root. Every expected line was taken from the oracle
first, under the project wrapper from a fresh directory: rc 0, stdout
byte-identical, stderr empty.

### The control that reddens it, and what it took

**A collection does fall between two of this template's targets, and that was
instrumented rather than assumed.** A temporary `eprintln!` in
`SourceText::bytes` printed the handle, its liveness and
`Heap::collections_performed` at every derivation: over the last template the
same slot is derived eight times while the collection count runs 306 -> 309,
and with the roots removed the eighth derivation reports `live=false`.

**The control is "the parse source is unrooted", and it takes three deletions,
not one.** The source on the `PARSE VAR` path is rooted three times over:
`Interp::source_text`'s own `push_temp`, `parse_strings`' `PARSE VAR` arm, and
`required_string_value`'s armed-latch arm. All eight subsets were run:

    GREEN  removed: none
    GREEN  removed: source_text
    GREEN  removed: parse_strings VAR
    GREEN  removed: source_text, parse_strings VAR
    GREEN  removed: required_string_value
    GREEN  removed: source_text, required_string_value
    GREEN  removed: parse_strings VAR, required_string_value
    RED    removed: source_text, parse_strings VAR, required_string_value

So the test asserts that the source is rooted, not that a particular line roots
it, and that is what its doc comment says. `Interp::source_text`'s `push_temp`
is redundant with the other two **today**; it is kept so the arm's invariant is
readable in `parse_template.rs` alone, and it costs one `Vec::push` per
borrowed source.

### Addendum: the latch is never clear, so the third root is never absent

The control above ran with `Interp::reqstr_armed` set, which is what makes
`required_string_value`'s push happen at all. I flagged the latch-clear case as
untested. **It is untestable: no program reaching `exec_parse` can have the
latch clear.** Probes on all four arming sites, over
`source_and_version_carry_their_own_strings` -- four clauses, no `~new`, no
directive, no trap -- print `ARM makestring-install` five times and
`ARM instance-new` once, all of them before the first `PROBE
reqstr_armed=true` in `source_text`. **The bootstrap arms it while installing
the core classes**, so the arming has nothing to do with the program.

That makes the redundancy structural rather than incidental: `source_text`'s
only two callers are `parse_strings`' `Subject::Value` arm and `argument_text`,
and both call `required_string_value` on the value immediately before it. With
the latch armed, that function pushes a temp for every `Body::Text`, which is
exactly the set of values `source_text` takes the borrowing arm for.

Asserted rather than argued, temporarily, at the site:

    debug_assert!(
        self.roots.iter().any(|root| root == value),
        "the parse source reached source_text unrooted"
    );

placed **before** `source_text`'s own `push_temp`. It holds across
`cargo test -p rexx-exec --lib` (847 passed), `collect_stress` (32 passed, the
whole L0 subset under collect-on-every-allocation) and the 604-program STRICT
differential. Inverted to a predicate that cannot hold, it fails the new test
at once, so it is a live probe and not a vacuous one. The assertion was removed
again and the tree is the committed tree; it is recorded here as the experiment,
not left in the code, because it is O(roots) per borrowed source.

**So: `source_text`'s `push_temp` is dead weight, and a reader who deletes it is
right about the tree.** What would make it matter is a change to
`required_string_value`'s armed fast path -- whose own comment says the push is
deliberate, "the caller's rooting of it is not this function's to assume" -- or
a bootstrap that stops installing `makeString`. Neither is in prospect. The
honest reason to keep it is the one already given, that it makes the arm
readable alone; that is a taste argument and not a safety one, and this
addendum is what a future reader needs to weigh it.

## Concerns

* **`SourceText::bytes` panics in release** (`unreachable!`) when the arm is
  `Text` and the handle no longer names a live `Body::Text`. That is reachable
  only from an unrooted source, and the alternative -- `try_text`'s
  `not_in_arena` placeholder, or the next occupant's bytes -- is the silent
  wrong answer this task exists to avoid. The generation check in
  `Heap::body_text` is what turns "the slot was reused" into `None` rather than
  into someone else's bytes; `heap.rs`'s `body_text_tests` reddens if it is
  dropped, and that was watched.
* **`trace.rs:616` carries 43,120,035 under `exec_parse` in the committed dump
  where the base carries none.** That is `traced_mode`'s `debug_pause` test.
  Two of the gates on that line are this task's (`parse_strings`' `>K>` gate and
  `next_template`'s `>>>` gate, both of which replace an unconditional render).
  **Whether that figure is new work or moved attribution was not established**,
  and I did not chase it: the whole-run total is the figure, and the same dump
  shows `unix.rs` at 37,240,020 under `exec_parse` where the base has none while
  the run's whole-program `malloc` and `free` move by 60,101 and 12,043 Ir on
  totals of 296,419,816 and 433,469,611, which is attribution moving and not
  work appearing.
* **Not taken, and sized only by that attribution**: giving `trace.rs` an
  ungated `trace_result_line`/`trace_keyword_line` would remove one
  `traced_mode()` per `PARSE` and one per template. It is worth at most the
  43,120,035 above and probably much less, and it widens `trace.rs`'s surface
  with two entry points whose gate a caller can forget.
* **Sources that are not string objects gain nothing.** A `Body::Num`, a stem,
  an array or an instance still renders into a pool buffer. No regression, but
  `parse value 3+4 with ...` is unchanged.
* The `c2` figure (+0.0645%) is **one round against one round**. It was not
  re-run after the optimised version existed, because the optimised version is
  what shipped and it has three and two.
* **The scout's four settled facts were not re-tested and nothing here
  contradicts them.** No probe in this work touched the variable pattern, the
  allocation count, the `PARSE UPPER` copy or the oracle comparison.
* **A process trap that cost about twenty minutes**, recorded because it will
  recur: a background waiter spelled `until [ "$(pgrep -cf 'measure.sh 3')" =
  "0" ]; do sleep 15; done` **matches its own shell**, whose command line
  contains the pattern, and never terminates. Two runner jobs deadlocked that
  way and had to be killed; `pgrep -af` showed the self-match. Wait on the
  output file, not on a `pgrep -f` of the command.
