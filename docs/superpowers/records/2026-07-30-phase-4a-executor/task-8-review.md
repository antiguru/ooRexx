## Findings

### Important 1: `strict_comparison_never_calls_to_number` is a witness that cannot fail

`eval.rs` (test, near the other comparison tests). Its comment claims: "if
the strict family accidentally routed through to_number it would compare
1 == 1 and answer 1, wrongly." That is factually wrong: `compare_decoded`
returns at `rexx-num/src/compare.rs:154` on `op.is_strict()` **before ever
reading either `Number` argument**, so routing strict operators through
`to_number` changes nothing observable. Mutation M3 proves it: with
`is_strict_compare` hardwired to `false`, every test stays green, this one
included. What the test actually exercises is the `StrictEqual` mapping row,
which `the_thirteen_line_comparison_transcript` already covers with the same
`'01' == '1'` line. The property its name asserts is a performance contract
(skip a useless parse), unobservable from results by construction. Fix: fix
or remove the comment and rename, or delete the test. The *code* it describes
is fine; `is_strict_compare`'s gating is real and its own doc comment gives
the honest (performance) rationale.

### Important 2: seven of eighteen `compare_op` mapping rows are unpinned by any test

Mutations M7+M8: mapping `\>` to `Less`, `\<` to `Greater`, `\>>` to
`StrictLess`, `\<<` to `StrictGreater`, `<<=` to `StrictLess`, `>=` to
`Greater`, and `<=` to `Less` leaves all 59 tests green. The
`backslash_negated_and_synonym_forms` test's comment says it exists "to pin
the Operator -> CompareOp mapping", but none of its operand pairs are equal
under the relevant comparison, and equality is the only case distinguishing
`LessEqual` from `Less`. Non-strict `>=`/`<=` appear in no unit test at all.
The implementer's 14 oracle measurements have the same blind spot (no
equal-operand case for any negated form), so this is a measurement gap that
propagated into a test gap. The shipped mapping is **correct**, verified this
session on all seven boundary cases against the oracle. Fix: add the seven
one-line assertions (`'9' \> '9'` -> 1, `'9' \< '9'` -> 1, `'9' \>> '9'` -> 1,
`'9' \<< '9'` -> 1, `'9' <<= '9'` -> 1, `'9' <= '9'` -> 1, `'9' >= '9'` -> 1).

### Minor 3: the D15 cache handoff to `compare_decoded` is not (and cannot be) pinned behaviorally

Mutation M5 (always pass `None`) survives because `compare_decoded` re-parses
the bytes itself and gets the same answers. The whole point of the
`compare_decoded` entry (plan Step 3a) is thus invisible to the test suite,
inherently: it is a performance property. The in-repo test
`a_comparison_reuses_an_already_parsed_num_cache` is honest about this ("Not
a behaviour difference visible from the answer alone"), unlike Finding 1's
test. No action needed; recorded so nobody believes the suite guards it.

### Minor 4: eval_logical_list's doc comment cites a probe weaker than its claim

"`'x'` is never evaluated once `0` has already decided the list" is true but
was established by a probe (`if 0, 'x'`) that only shows the check is
skipped. `if 0, (1/0)` is the probe that shows evaluation is skipped; run
this session, it confirms the comment. Worth amending the comment's cited
evidence next time the file is touched; no code change.

### Minor 5: one of four measured 34.901 triggers asserted

Tests assert `' 1 ' & 1` raises 34.901 but not `'01'`/`'1.0'`/`''`. The test
comment says one representative was chosen deliberately, and all four go
through the same `logical_value`. Acceptable; noted for completeness.

The two skepticism questions posed about this test:

- *Is the (42,3) control reachable for a wrong reason?* No. The program

  clean Raised-mismatch panic instead of an activation panic, which is an
  improvement, not a weakening. Other tests each build their own `Interp`,
