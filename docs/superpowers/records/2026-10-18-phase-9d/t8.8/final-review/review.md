## Important findings

* **F1: Closed or unopened stdout streams expose a position.** `rust/crates/rexx-exec/src/dispatch/stream.rs:2341` enters the new descriptor shortcut without checking `unopened_standard`. With stdout redirected to a regular file, `.stdout~close` followed by a POSITION query reported through STDERR returns `1`, a write position, or the descriptor offset instead of the null string. The same issue affects `s = .stream~new('STDOUT')` before its first open, including `STDOUT:` aliases. `unopened_standard` at line 241 already represents this state, `close` at line 2432 sets UNKNOWN, and `oodocs/rexxref/en-US/streamclasses.xml:1382` explicitly excludes POSITION/SEEK from queries available on unopened streams. After validating options, return the null string for an unopened standard receiver before entering the descriptor branch. This is a task-introduced regression: the base fell through its missing OpenFile and returned the null string.

* **F2: Buffered stdout aliases lose their pending bytes in WRITE CHAR queries.** `rust/crates/rexx-exec/src/dispatch/stream.rs:2351` adds only `interp.out.len()` to the descriptor offset, although a program-created STDOUT stream buffers its own output in `StreamState.held`. On an initially empty redirected file, `s = .stream~new('STDOUT'); s~charout('abc')` followed by `s~query('position write char')` reported through STDERR therefore computes `1` instead of logical position `4`. The held bytes are appended at `stream.rs:1107`, and the new shortcut also accepts these buffered receivers because `owned_standard_output` checks only standard kind, descriptor ownership, and transient classification. Account for the queried receiver's pending bytes when computing its logical write position, preserving the distinct SYS descriptor contract. This is an incomplete claimed fix rather than a claim that the base already implemented the alias query correctly, and the current redirected-file regression covers only unbuffered `.stdout`.

* **F3: HASITEM reads a detached backing array after index equality reentry.** `rust/crates/rexx-exec/src/dispatch/hash/relation.rs:250` sends index equality, then line 254 reads `store.items` without validating the captured Store. Reuse the armed key from `tests/semantic_boundaries/reentry-relation-allat-equality.rex`, with `r~hasItem('new', q)` as the operation: its equality callback empties and repopulates the Relation, so the subsequent item read still addresses the old arrays. Without collection this compares the detached old value, and collection during the callback can sweep the old arrays and make `array_slots` refuse a valid collection operation as a non-array. Refresh and validate the store after callbacks, restarting with the cached hash before any subsequent slot read, as the neighboring corrected search/removal paths already do. The successful-index-callback stale read is task-introduced by moving index equality before the item load, while general traversal reentry limitations also existed in the original code and are not asserted fixed by this review.

These are source-derived findings, not claimed executed reproductions. F1 follows the explicit unopened-position contract, F2 follows the current write-position contract at `streamclasses.xml:956` together with the existing per-stream buffering implementation, and F3 violates backing-store lifetime and identity invariants independently of any oracle quirk. The new regressions should distinguish the opened `.stdout` positive case, unopened/closed aliases, buffered aliases, and HASITEM equality replacement under normal and collection-on-every-allocation execution. Existing scoped tests remain relevant, but do not cover these exact boundaries.
