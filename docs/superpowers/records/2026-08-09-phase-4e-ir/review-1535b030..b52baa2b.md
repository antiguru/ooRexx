## Findings

### Critical

**C1. A promoted construct loses its clause-exit boundary; a `CALL ON` handler queued by a delivered handler is delivered one clause too late.**

This is concern 4, and it is constructible.
Witness (`w.rex`):

```rexx
call on user zx name h
call on user zy name g
select
  when 1 = 1 then zq = raiser()
end
say 'after'
exit
raiser:
raise user zx return 'V'
h:
raise user zy return 1
g:
say 'G ran' sigl
return
```

| arm | stdout |
| --- | --- |
| oracle | `G ran 4` / `after` |
| tree-walker, release | `G ran 4` / `after` |
| **IR engine, release** | **`after` / `G ran 6`** |
| IR engine, debug | panics: `clause.rs:414` -- "a clause at line 6 began while a condition queued by this activation's clause at line 4 was still waiting" |

Both the output order and `SIGL` are wrong on the compiled stream, and the crate's own fourth-site tripwire fires on it in debug.

The mechanism is exactly the one the report describes and then dismisses.
`zq = raiser()` queues `zx`; the body clause's boundary delivers `h`; `h` does `raise user zy return 1`, which `caller_trap_for` matches against the *caller's* table and queues for the caller's activation (`run.rs:3386`, `activation: self.activations[len - 2].id`).
`in_clause` delivers at most one pending trap per boundary and does not loop, so `zy` is still pending when the body clause ends.
In the tree-walker the `SELECT`'s outer `in_stepped_clause` boundary is the next one and delivers `g` there.
In the compiled stream there is no such boundary, so `g` waits for `say 'after'`.

Verified pre-existing/introduced:

* at `1535b030` this program is `G ran 4` / `after` on **both** engines -- the `SELECT` instance is **introduced by this task**;
* the identical program written with `if 1 = 1 then zq = raiser()` already diverges at `1535b030` (`G ran 3` / `after` vs `after` / `G ran 4`) -- the `IF` instance is a **pre-existing Task 4b defect** of the same class, at the construct-exit boundary rather than the header boundary that Task 4b's Critical was about;
* the `OTHERWISE` path is a divergence too, in `SIGL` rather than in ordering: same program with `otherwise zq = raiser()` gives `G 5` on the tree-walker and `G 6` on the IR engine, and here it is the **tree-walker** that is wrong against the oracle's `G 6`;
* the same shape written over a `DO ... END` block fires the tripwire on both engines equally, so the "at most one delivery per boundary" half is a separate, pre-existing, engine-agnostic defect (see N1).

The report's four supporting statements for concern 4 are each individually true and the conclusion does not follow:

* "every body clause, every `WHEN` and the `OTHERWISE` marker each have a boundary of their own" -- true;
* "nothing runs between the last of them and where the outer boundary would sit" -- true;
* what is missing is that a boundary can *leave a new pending trap behind*, because the handler it runs can queue one for this activation and `in_clause` does not re-check.
  The last member boundary is then not the last boundary that has work.

This is the shape MEMORY records as "unreachability claims need running": a confident wrong claim from true premises, missing a second premise.
The corpus and the three `ootest` suites agreeing is exactly as much evidence as it was for the Task 4b Critical -- none, for this class.

**What would have settled it, and what should now:** one `InlineCase` of this shape in `BRANCH_CASES`.
A promotion opens *n* clause units where the tree-walker opens *n+1*; the missing one is the construct's own, and the only obligation it carries that a member clause does not already carry is delivery of a trap queued during a member clause's *boundary*.
That is a two-handler program, and it is the fourth entry the "boundaries, not shapes" axis was supposed to produce.
Note the crate already contains a detector: `in_clause`'s `debug_assert` fires on the witness under the ordinary debug test profile, so a single dual-engine case of this shape catches both the `SELECT` and the `IF` instance without anyone having to reason about it.

### Important

**I1. `SELECT`'s resume rule -- the very rule the second defect was about -- is written twice, and the report says nothing is.**

The report states: "Nothing about `SELECT`'s semantics is written twice."
Three things are:

* the `SelectResume` pairing for a matched `WHEN`, `{ done: targets.resume, left: targets.resume }`, appears in `run.rs`'s `Select` arm and again in `drive.rs`'s `when_frame`;
* the pairing for `OTHERWISE`, `{ done: otherwise_end, left: select_exit(len, end) }`, appears in `run.rs`'s `run_otherwise` and again in `drive.rs`'s `otherwise_frame`;
* the `indent_offset = 0` restore that closes an `OTHERWISE` dispatch appears in `run_otherwise` and again in `drive.rs`'s `leave_branch`;
* the case-value-to-text conversion and the `current_case_text` assignment appear in `run.rs`'s `Select` arm and again in the driver's `Op::SelectCaseText` arm.

`select_exit`, `otherwise_range`, `when_targets`, `select_parts`, `select_case`, `scan_when`, `leave_select`, `pop_search_frame` and `absorb` genuinely are shared, and the label search, 28.5, the indent rule and the `WHEN CASE` comparison genuinely do not exist twice -- the report is right about the hard parts.
But the *pairing* is the decision, not `select_exit`, and it is exactly what was wrong before this task.
The evidence is direct: reproducing the second defect required editing **both** `run.rs:4724` and `drive.rs:644`; a mutation of either alone would have left one engine correct and gone red as an engine divergence rather than as the semantic error it is.
A shared `when_resume(&targets)` / `otherwise_resume(len, end)` (and putting the `indent_offset` restore inside `leave_select` behind the branch kind) would make the drift impossible instead of merely tested.

### Not findings, checked and clean

* **The two clause-count tripwires from earlier tasks did not move.**
  `src/ir/drive/tests.rs` is a pure addition in this range (58 insertions, 0 deletions); the loop count stays 4, the block count 3 and the `IF` count 4, with their existing derivations untouched.
  The new `SELECT` count of 6 is derived from the stream and stated in the test: header clause + one clause per listed `WHEN` + the chosen branch's clauses + the clause after, with the `END` present on the `OTHERWISE` path and absent on the matched path, and both are the counts the compiled stream actually produces.
* **The deleted `OTHERWISE` redirect arm (M2 in the report) is redundant, not merely untested.**
  Every arrival at an `OTHERWISE` in the compiled stream goes through `Chunk::op_of`: `settle`'s `Absorbed::Resume` (`op_at`), `run_chunk`'s outer loop (`chunk.op_at(entry)`), and every scan patch that targets an `OTHERWISE`, which `compile` builds with `PatchKind::Resume` unconditionally (`no_match` is `(otherwise_index, PatchKind::Resume)`; no `PatchKind::Enter` patch can name an `OTHERWISE`).
  Fallthrough into `op_of[otherwise]` from the preceding instruction cannot happen because that op index *is* the preceding `WHEN` frame's `op_end`, so the frame closes first.
  I confirmed the layout on the F-EX1 program by dumping the chunk: the listed `WHEN`'s `false_target` is the absorbed `WHEN`'s `THEN` marker, so the absorbed escape's `Goto(otherwise)` genuinely leaves the frame's range, is forwarded by `leave_select`, is absorbed by the enclosing range as `Resume(otherwise)` and lands on `EnterOtherwise`.
  Task 4c (loops) and Task 7 (expression ops) add no new arrival mechanism -- both reach an instruction through `absorb`/`op_of` -- so the arm does not become reachable later.
* **`grant_procedure_permission` on branch-body `Generic` ops.** The driver grants at every top-level op, including instructions inside a `SELECT` branch, where the tree-walker's `run_bounded` does not.
  Unobservable: `first_instruction_pending` is always spent by the `SELECT`'s own `Clause` op before any branch instruction runs, and `procedure reached through a matched when` pins the 17.1.
* **`unsafe`, em-dashes in comments, `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`**: all clean.
  No count of a mutable in-repo aggregate in the new comments beyond M1.
* **Disclosed items re-measured and confirmed as stated:** the `SELECT` header's failure-site indent is two columns short of the oracle on *both* engines (`2 *-* select case raiser()` vs the oracle's `2 *-*   select case raiser()`), and `select / otherwise / end` is 7.1 rc 249 on the oracle and rc 120 here on both engines.
  Neither is this task's and both engines agree.

### N1. Context, not a finding against this task

`in_clause` delivers at most one pending trap per boundary.
`select case raiser()` whose handler queues a second condition trips the same `clause.rs:414` assertion on **both** engines at `1535b030` and at `b52baa2b`, and the oracle delivers both before the first `WHEN`.
The same holds for a `DO ... END` block.
That is a pre-existing, engine-agnostic defect and it is the *other* half of what makes C1 possible; fixing C1 by restoring the construct-exit boundary does not fix it, and fixing it (looping the delivery) would incidentally hide C1 on this particular witness.
Both want owners.
